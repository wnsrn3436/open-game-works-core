# contract tool

Read when the core agent makes or fixes the contract tool. The rules the contract tool checks are in [SKILL.md](SKILL.md).

## generation target

| generation target | location | contents |
|---|---|---|
| client | `client/generated/contract/` | messages and enums of the client type set, encode and decode, per `rpc` the constants of the request name and options (`silent`, `retry`, `sensitive`), per core `rpc` the `GameError` list written in `(ogw.core_errors)`, UserState kinds and their connection to the `UserStateCore` cache |
| server | `server/generated/contract/` | the runtime of the generated code `wire.ts` (wire format encode and decode, proto3 JSON conversion, validation), messages and enums of the server type set, encode and decode (encode puts the unknown fields that decode read back in unchanged), the `rpc` list, per `rpc` of `service Game` a handler type (its failure type accepts only the `GameError` values written in `(ogw.errors)` of that `rpc`), per core `rpc` the `GameError` list written in `(ogw.core_errors)`, field validators, UserState, server state, and game state kinds and their save mapping, the public kind list, proto3 JSON conversion of UserState and server state kinds, `ItemChange`, `ItemMail`, the contract version constant, the file `contract_version` that holds the contract version in one line, the (kind, from version) list written with `(ogw.converters)` and the converter list file `converters.json` that holds that list |
| client DEV | `client/dev/generated/contract/` | messages and enums of the DEV type set, encode and decode, per `rpc` the constants of the request name and options (`silent`, `retry`, `sensitive`), proto3 JSON encode and decode of UserState kinds |
| server DEV | `server/dev/generated/contract/` | messages and enums of the DEV type set, encode and decode, the `rpc` list, a handler type per `rpc` of `service Cheat` of `cheat.proto`, a field validator per `rpc`, proto3 JSON conversion of the request message per `rpc` |

- The encode of the server generated code writes an unpaired surrogate in a `string` field as U+FFFD and always outputs valid UTF-8. Decode does not treat invalid UTF-8 bytes as a decode failure; the `utf8` rule of the validator rejects them

- type set: a reachable type is a message or enum reached by following field types
  - base set: the messages and enums of the base proto that are not among the request messages and response messages of `service CoreCheat` and the types reachable from them, and the types reachable from those
  - client type set: the base set, the messages and enums of `service.proto`, `user_state.proto`, `error.proto`, `realtime.proto`, and the types reachable from them
  - server type set: the client type set, the messages and enums of `server_state.proto`, `game_state.proto`, and the types reachable from them
  - DEV type set: the messages and enums of the base proto that are not in the base set, and the messages and enums of `cheat.proto`
- converter list file `converters.json`: `[{"kind": "<kind message name>", "from_version": <integer>}, ...]`. The order is the kind order of `GameContract.KINDS`, and within the same kind, ascending order of from version. When there is no `(ogw.converters)`, it is `[]`
- `server/generated/contract/wire.ts` is imported only by server generated code. Core and content code do not import it
- The generated proto3 JSON conversion, when it encodes, uses the original proto names as field names and writes `int64` values as decimal strings
- Before generation, the contract tool checks all the rules of [SKILL.md](SKILL.md) that can be judged from the contract files and the base proto alone. e.g. writing rules, the contents each file can hold (the file that holds kinds, `service` and `rpc`, `GameError`, `RealtimeMessage`, module messages), the imports and field types of `cheat.proto`, the name format of `rpc`, message and kind, `int64 id = 1` of a list kind (the field named `id` has type `int64` and field number 1), `int64 key = 1` of a game state kind (the field named `key` has type `int64` and field number 1), `(ogw.public)` being only on kinds of `user_state.proto`, the targets and values of `(ogw.converters)`, the range of `GameError` values, the names in `(ogw.errors)` and `(ogw.core_errors)`, the `changes:` line of `rpc` comments and `(ogw.retry)`, field validation declarations, backward compatibility. When even one is violated, it writes no file

## CLI

The harness tool calls the contract tool of every core version with this CLI. The generated code that core tests use is made by `ogw core test` with the contract tool of `open-game-works-core-impl/`, for the core test data folder.

`node bin/contract-tool.js --game <dir> [--engine <engine>] --base-proto <dir> --core-settings <file> [--modules <file>] [--previous <dir>]`. `bin/contract-tool.js` is a path relative to the folder where `contract-tool.tgz` is unpacked.

`node bin/contract-tool.js --base-proto-only --base-proto <dir> --core-settings <file> --previous <dir>` compares only the base proto. It compares `proto/` of the `--previous` folder with `--base-proto` by the backward compatibility rules, and fills the `_key` options from `core-settings.json` of the `--previous` folder and from `--core-settings` respectively. It does not read `contract/` and `contract_version` of the `--previous` folder. It does not read the game contract, does no pre-generation check other than the base proto comparison, and writes no file. stdout and exit code are the same as in other runs. `ogw core release` uses it for the base proto comparison of the release condition

| argument | contents |
|---|---|
| `--game <dir>` | the root of a game repo or its worktree, a benchmark game folder, or the core test data folder `open-game-works-core-impl/test-data/`. Reads `contract/`, the data proto of `server/generated/data/game_data.proto`, and client core type names (set by `### generated code` of the per-engine implementation rules of [`client-core`](../client-core/SKILL.md)), and writes the generation targets under it. When `--game` is `test-data/` under the parent folder of the `--base-proto` folder, it is the core test data folder. For the core test data folder, the read paths and the generation target locations are changed by the same rule as the core test data generation target location that the data tool of [`data`](../data/SKILL.md) sets. When `contract/` or the client core folder is missing, it is treated as empty |
| `--engine <engine>` | the engine of the client generated code. Of the paths read and written, a path that starts with `client/` is a path under the logical folder of `## folder` of [`client-content`](../client-content/SKILL.md), and the contract tool reads and writes it at the actual path that `## project` of the per-engine rules of this engine sets. For a game repo and a benchmark game, it is the game settings `engine` value. When omitted, the tool does not write the client and client DEV generation targets and does not read client core type names. It is omitted only for the core test data folder |
| `--base-proto <dir>` | the base proto folder. `proto/` of the folder where `contract-tool.tgz` is unpacked, taken from the release of the game settings core version for a game repo and from the release that holds its `benchmark-<engine>.zip` for a benchmark game unpacked from a release; for a benchmark game inside `open-game-works-core-impl/` and for the core test data folder, `open-game-works-core-impl/proto/` |
| `--core-settings <file>` | the JSON of core settings values from which the numbers of base proto `_key` options are read. Its keys are core settings keys. For a game, the merged core settings values of that game that `ogw generate` made; when code is made in `open-game-works-core-impl/` without a game (core test), the core settings defaults of `open-game-works-core-impl/settings/core-settings.json`. When the key of a `_key` option is missing or its value is not an integer, the tool blocks with an error |
| `--modules <file>` | a JSON array of the names of the modules the game uses (`## module` of [`core`](../core/SKILL.md)). When given, the tool checks that the module messages those modules require to be defined exist |
| `--previous <dir>` | the folder of the last PROD build. Holds `contract/` (game contract), `proto/` (the base proto of the release of the core version that the game settings of the `prod-<version>` tag point to), `core-settings.json` (`core-settings.json` of that release overlaid with game settings `core` of that tag. The numbers of the `_key` options of the base proto of the last PROD build are read from here), `contract_version` (the contract version of that build in one line). When given, the tool checks backward compatibility and calculates the contract version. When not given, the contract version is 1 |

- A generation target folder is replaced as a whole
- stdout: one line per violation, `<file>:<line>:<column> ERROR <message>`
- exit code: `0` is success, `1` is that there are violations (no file is written), `2` is that an argument or input file is wrong or an input or output path cannot be read or written (the reason goes to stderr)
