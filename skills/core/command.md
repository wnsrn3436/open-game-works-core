## version and release

- There is one core version for client core, server core, contract tool, data tool and core settings together. The contract tool and the data tool make the generated code that core uses, so they are released together with core. The format is `<major>.<minor>.<patch>`
  - major: a change that breaks compatibility of the public API, behavior, hooks, events, core settings keys, system table schema, base proto, the code that the contract tool and the data tool generate, the CLI of the contract tool and the data tool, or the `core-spec.json` format
  - minor: an addition that keeps compatibility
  - patch: a bug fix that does not change the public API
- A release puts the tag `v<version>` on a main commit of `open-game-works-core-impl/` and publishes a GitHub release with that tag to the core release repository of harness settings
- The release assets are those of `client-<engine>.zip` (one per engine), `client-<engine>-plugins.zip` (one per engine that has a native plugin built by core), `benchmark-<engine>.zip` (one per engine), `server.tgz`, `contract-tool.tgz`, `data-tool.tgz`, `core-settings.json`, `core-settings.schema.json`, `core-settings-constraints.json`, `core-spec.json`, `licenses.json`, `manifest.json` that exist in that version. `manifest.json` is `{"version": "<core version>", "assets": {"<asset name>": "<SHA-256 lowercase hex>", ...}, "coreSchemaVersion": <integer>}`. `assets` has one entry per asset other than `manifest.json`. `coreSchemaVersion` is the highest core schema version that `storage` applies, the value of `open-game-works-core-impl/server/core/storage/core-schema-version` (one line with a decimal integer of 0 or more). When that file does not exist, it is 0. `core-settings.json` is `open-game-works-core-impl/settings/core-settings.json`, and the harness tool reads the core settings defaults of that version from this file. `contract-tool.tgz` and `data-tool.tgz` hold only their own `bin/<tool>.js` made by the build of `### create contract tool` and the base proto. `<tool>` is `contract-tool` or `data-tool`. The base proto is in `open-game-works-core-impl/proto/`, and in both tgz files it is at the same path `proto/`
- After a release is published, the assets of that version do not change. A fix is published as a new version
- Before the release, `ogw core release <version>` checks all release conditions below; when any is violated, it does not release and outputs every violated condition. The lead agent does not check the release conditions separately
  - There is a record that `ogw core test` passed every module of the targets with an implementation on the `open-game-works-core-impl/` main HEAD commit. The targets with an implementation are `server` when `open-game-works-core-impl/server/core/` exists, the native run and the browser run (`--web`) for each engine that has `open-game-works-core-impl/client/<engine>/engine.json`, and `tools` when there is a tool that has `open-game-works-core-impl/tools/<tool>/package.json`. The modules of `tools` are those tools. As an exception, a module that is `skipped` because the native run of an engine did not run the render pass due to a screen lock or a display that is off does not block, and the release output shows it as a `core test <target>: <module>: <reason>` line
  - `core-spec/` equals the result of running `ogw core spec` with the current harness specs
  - For each target with a review state of `## review and code check`, the result of the last round is `done`
  - The must-fix lists of `## review lists` have no items. Debt lists do not block the release. The release output has a `review debt <target>: <item count>` line for each debt list with items. The lead agent shows those lines to the human with a recommendation and asks whether to run the debt review of those targets (`ogw review run core <target> --debt`, or `ogw review spec core <module> --debt` for a spec debt list)
  - `ogw code check core` is `pass`. The release runs it
  - The values of `open-game-works-core-impl/settings/core-settings.json` satisfy the settings constraints whose `left` and `right` modules are both modules of targets with an implementation (`server`, engine). A key is `<module>.<name>`
  - For each item of `plugins` of `engine.json` whose name starts with `ogw-`, the plugin build results for all target platforms are at the path that the engine-specific implementation rules set
  - When there is a release lower than that version, the base proto of the highest of those releases and this base proto are compared with the backward compatibility rules of [`contract`](../contract/SKILL.md), and when there is a change that breaks compatibility, the major is higher than that release's. The comparison runs the contract tool of `open-game-works-core-impl/` with `--base-proto-only`. `--base-proto` is `open-game-works-core-impl/proto/`, `--core-settings` is `open-game-works-core-impl/settings/core-settings.json` (`{}` when it does not exist), and the `--previous` folder holds `proto/` of that release's `contract-tool.tgz` and that release's `core-settings.json`. When that release has no `core-settings.json`, `core-settings.json` of the `--previous` folder is `{}`
- When the release conditions pass, `ogw core release` makes `core-settings-constraints.json`, makes `client-<engine>-plugins.zip` from the plugin build results that the engine-specific implementation rules set, writes its release asset URL and SHA-256 into the items of `plugins` of `engine.json` whose name starts with `ogw-`, commits to main and then puts the tag. After the release, it deletes everything that `ogw review clear core` deletes (the review state of `## review and code check`, the input folders and review files of `## spec review`, the worktrees and branches `agent/<id>` that agent jobs no longer running left in `open-game-works-core-impl/`). Agent results left unmerged are discarded. Worktrees and branches it could not delete are output as `not removed: <path or branch>` lines

## core spec file

`core-spec.json` is the release asset that carries, as JSON, the parts of the specs that the harness tool and the data tool read. The harness tool reads modules, dependencies, lifecycle, settings, collected data, adapters and operation inputs from it, and the data tool reads core data from it.

- From the specs of the harness, `ogw core spec` writes, per module, the `<module>` object of that module to `open-game-works-core-impl/core-spec/<module name>.json`, and deletes the files whose name is not a module. When the folder the command ran in is inside a worktree under `worktrees/_core/`, it writes to that worktree. The modules and their spec files are the `module` and `spec` columns of the `## module` table of [`client-core`](../client-core/SKILL.md) and [`server-core`](../server-core/SKILL.md), and `side` is the skill that has that table. Specs are read from the working tree of the harness repo
- `ogw core test <server|engine> <module> --file <test file>` runs only one test file of `tests/` of that module. It is a run to narrow down a cause. It leaves no test record, and `ogw agent merge` does not count this run as the last `ogw core test`. It is not used for the browser run (`--web`) or `tools`
- `ogw core test` keeps the passing result of each module with a key, and for a module that has a passing result with the same key, it uses that result instead of running it again. The key is the target (`server`, engine and whether `--web`, `tools`), the folders of that module and of all modules reached by following `dependencies`, `devDependencies`, `optionalDependencies`, the folders of the modules reached by following `testing` (server) or `UnitTestCore` (client), `test-data/`, `core-spec/`, the git tree of the package and engine files of that target, and the tree of harness `tools/`. A run in a checkout with uncommitted changes and a `--file` run neither keep nor use results
- `ogw core test` runs `ogw core spec` when it starts. The core agent does not edit `core-spec/` by hand, and puts the changed files in the same commit as the implementation
- When `ogw core spec` and `ogw core test` run in the `open-game-works-core-impl/` main checkout on branch main, the tool, when it ends, commits to main all generated files that differ from HEAD and does not commit other changes. The generated files are `core-spec/`, `server/core/testing/dev/setting_types.ts`, the committed generation targets of the core test data build, per engine the `project.godot`, module list file, core settings file and core settings type file of the core project and the engine meta files (`.uid`, `.import`) of those files, and the files under `test-data/data/` that the data tool run aligning the core test data changed. Files under `test-data/data/` that already had uncommitted changes when the run started are not committed. `ogw core test` of an engine target imports the core project before the commit to make those meta files. `ogw core test` runs the tests on that commit
- When a spec violates `### tool-read form` of [SKILL.md](SKILL.md), `ogw core spec` writes no file, outputs the spec file:line and the reason for each violation, and fails. The violations are: a code span of a dependency line is a module name that does not exist. A table that a used table line or the `→` of a reserved name points to has no table definition in any module. The header or a cell of a table definition, enum table, invariant table, format argument table, settings table, settings constraint table or collected data table differs from its form. The `text` of a format argument table is not in a reserved name or table definition. The same settings constraint is in two specs
- When `open-game-works-core-impl/server/core/testing/` exists, `ogw core spec` also writes `open-game-works-core-impl/server/core/testing/dev/setting_types.ts`, the settings type table that `testing` checks settings overrides against: one entry `'<key>': '<type>'` of `export const SETTING_TYPES` per distinct `key` of the settings tables of all modules, in byte order of `key`. When two settings rows have the same `key` with different `type`, it writes no file, outputs both spec file:lines and fails
- `ogw core release` merges the files of `core-spec/` in byte order of module name and outputs `{"version": "<core version>", "modules": [<module>, ...]}` as `core-spec.json`
- `<module>` has all the fields below. A list field with nothing in it is an empty list. The elements of a list field are in the order they appear in the spec

| field | contents |
|---|---|
| `name` | The module name |
| `side` | `client` or `server` |
| `lifecycle` | `true` when the module has a lifecycle. `false` for server modules and for client modules with a lifecycle sentence |
| `dependencies` | The modules of dependency lines without a label or with the label `server dependency: `, minus the modules that only DEV code depends on |
| `optionalDependencies` | The modules of dependency lines with the label `optional dependency: `, minus the modules that only DEV code depends on |
| `devDependencies` | The modules that only DEV code depends on |
| `settings` | `{"key": "<key>", "type": "<type>", "source": "<source>", "owner": "<owner>"}` per row of the settings table. `key` is the text inside the code span of that row's `key` cell, and the rest are the text of the cells. `meaning` is not included |
| `settingsConstraints` | `{"left": "<left>", "factor": <factor>, "right": "<right>"}` per row of the settings constraint table |
| `tables` | `{"name": "<table>", "columns": [<column>, ...]}` per table definition. `<column>` is `{"description": "", "target": "<build target>", "type": "<type>", "name": "<column>"}` per row that is not a comment column |
| `usedTables` | The union of the table names below, minus the table definitions of this module. `<table>` of `ref<<table>.<column>>` in the types of table definitions, `<table>` of `` → row of `<table>` `` of reserved names, the tables of used table lines |
| `enums` | `{"type": "<type>", "elements": ["<element>", ...]}` per row of the enum table whose `element` does not start with `set by the game` |
| `invariants` | Per row of the invariant table, an object with the column names as keys and the text inside the code span of each cell as values. An empty cell is an empty string |
| `reserved` | `{"table": "<one of reserved_id, reserved_string, reserved_sound>", "id": "<ID name>", "requiredWhen": <condition>, "rowOf": <table>}` per ID name of the reserved names. `<condition>` is `{"path": "<path>", "value": <JSON value>}` when that ID name has a required condition, and `null` otherwise. `rowOf` is the table name string when there is `` → row of `<table>` ``, and `null` otherwise |
| `formatArguments` | `{"text": "<text>", "arguments": [{"name": "<name>", "kind": "<kind>"}, ...]}` per row of the format argument table. With `none`, `arguments` is an empty list |
| `collectedData` | `{"dataType": "<data type>", "description": "<description>", "source": "<source>", "purposes": ["<purpose>", ...], "linked": <bool>, "tracking": <bool>, "shared": <bool>, "optional": <bool>, "platforms": ["<platform>", ...], "condition": <condition>}` per row of the collected data table. `all` in `platforms` is `android`, `ios`, `web`, `windows`, `macos`, `linux`. `<condition>` is `null` for `none`, and otherwise `{"path": "<path>", "value": <JSON value>}`. A row whose `data type` is `none` has empty lists for `purposes` and `platforms`, `false` for the four bools, and `null` for `condition` |
| `adapters` | `real adapter` of the adapter table |
| `operations` | `{"name": "<operation>", "inputs": ["<kind>", ...]}` per operation of the operation table. `inputs` has one entry per input in input order: `translationKey` for an input that receives a translation key, `other` for the rest. When the `input` cell is `none`, it is an empty list |

- When the target is `server` or an engine, `ogw core test` checks `core-spec/` after `ogw core spec`, and when any of the following is violated, it fails without running tests
  - The file name equals `name`. In a run without a module given, the modules with an implementation equal the modules with a file. The implementation of a server module is a module folder that has the entry file set by `## folder` of [`server-core`](../server-core/SKILL.md)
  - The other core modules that module code references are in `dependencies` or `optionalDependencies`. DEV code can also reference the modules of `devDependencies`
  - Following `dependencies` does not come back to the same module
  - For each name in `adapters` of any module, some module has a `collectedData` row whose `source` is that name
  - `source` of `collectedData` is `module` or a name in `adapters` of some module
  - Of `left` and `right` of `settingsConstraints` of the modules with an implementation, the keys of modules with an implementation are in `core-settings.json`. The module of a key is the name before the first `.` of the key
  - In `settings` of the modules with an implementation, the `key` of each row whose `source` is `core` is in `core-settings.json`, and the set of `key` of the rows whose `owner` is `human` equals the set of keys of modules with an implementation among the keys that have `"x-owner": "human"` in `core-settings.schema.json`
- When a core test uses data, that data is data into which core data was put by passing the data tool, as `--core-spec`, a file that merges `core-spec/` the same way as `ogw core release`

## license manifest

`licenses.json` lists the licenses of the third-party components that go into the client. The core agent edits `components` of `open-game-works-core-impl/licenses.json` in the commit that changes the engine version, `plugins` of `engine.json` or the third-party code put into core code, then runs `ogw core licenses` and puts the result in the same commit. `ogw core release` publishes that file as a release asset.

- The format is `{"components": [<component>, ...], "texts": {"<SPDX license ID>": "<full license text>", ...}}`

| field | contents |
|---|---|
| `name` | The component name |
| `version` | The component version. The empty string when there is none |
| `license` | The SPDX license expression |
| `url` | The source URL |
| `notice` | The original text of the copyright and notices that the distribution requires to be displayed. The empty string when there is none |
| `platforms` | The list of platforms the component goes into |
| `modules` | The list of names of the core modules that use the component. An empty list for a component that goes into every game (e.g. the engine) |

- `components` has one entry for the engine, for each third-party component in the engine, for each plugin of `engine.json` `plugins` and each SDK in a plugin, and for each piece of third-party code put into core code. A plugin whose name starts with `ogw-` is code that core wrote, so it has no component, and each SDK in that plugin has a component. The values are copied from the license files and copyright files of that distribution
- `texts` holds the full text published by SPDX for each SPDX license ID in the `license` expressions of `components`, each SPDX exception ID after `WITH`, and the SPDX license ID of each license that the resource rights of [`resource`](../resource/SKILL.md) allow. An ID in a `license` expression that starts with `LicenseRef-` or `DocumentRef-` is not an SPDX license ID, so it is not in `texts`, and the full text of that license is written in `notice` of that component. `ogw core licenses` fills it, and the core agent does not write it by hand
- The core test of an engine target checks that, for each plugin of `plugins` of `engine.json` whose name does not start with `ogw-`, there is a component whose `name` is that plugin name, that no component has the same name as a plugin whose name starts with `ogw-`, and that `texts` has all the SPDX license IDs above
- license manifest of the game: `ogw generate` writes it to `client/generated/licenses.json` in the same format. `components` has the components of the core release `licenses.json` whose `modules` is an empty list or has a module the game uses, in the order of the core release, followed by the game resource components. `texts` is `texts` of the core release
- game resource component: one per group, made by grouping the rows of `resource/resources.csv` whose `attribution` is not an empty cell into rows with the same `attribution`, `license` and `source`. `name` is the resource keys of the group in byte order joined by `, `, `version` is the empty string, `license` is `license`, `url` is `source`, `notice` is `attribution`, `platforms` is game settings `buildPlatforms`, `modules` is an empty list. The groups are in byte order of `name`

## command

The lead agent of a core command calls the core agent with `ogw agent core --input <file>`, checks the result, and then releases with `ogw core release <version>`. The first line of the input file is `command: <command>`, where `<command>` is the name of the command the lead agent received (`create contract tool`, `create server core`, `create client core`, `update core`). The target is written from the second line on. `<command>` of the input that `ogw review wait` writes is `review fix`. When the first line is not in this form, `ogw agent core` fails without starting an agent. When the harness is used for the first time, the command order is `update env`, `create contract tool`, `create server core`, `create client core`, `update env`. When the earlier core command has no release, the later core command does not start. The first `update env` gets the programs and images of harness settings `tools` that core tests use, and the last `update env` measures `maxConcurrentInstances` with the benchmark game that `create client core` put in the release. The lead agent of `create server core`, `create client core` and `update core` runs `ogw env check --for <create-server-core|create-client-core|update-core>` when it starts; when it fails, the lead agent stops and tells the human its output. That check checks the items of harness settings `tools` that must be on this host when that command starts: `tools.postgresql` for `create server core`, `tools.chromium` for `create client core`, and `tools.postgresql`, `tools.chromium`, `tools.gdtoolkit` for `update core`.

`ogw agent core` starts each core agent in a worktree with a branch `agent/<id>` made from the main HEAD of `open-game-works-core-impl/`. When the lead agent assigns a module or a tool (`contract-tool`, `data-tool`) to a core agent, it passes that name with `--module`. When the name is none of a tool, a module of the `## module` table of the `client-core` and `server-core` SKILL.md, and a module of `core-spec/` of `open-game-works-core-impl/` main, `ogw agent core` fails without starting a job. When a core agent ends, the lead agent checks the report and merges it into main with `ogw agent merge <id>...`. `ogw agent merge` does not merge, and outputs as `no core test`, a core agent that changed files outside `records/` and whose run log next to the report, `<report file name without extension>-runs.json`, has no last `ogw core test` item, or whose last item has a non-zero exit code, a test count of 0, or a pass count less than the test count. Also, when the type check of `ogw code check core` on that agent's branch `agent/<id>` reports a failure that is not in the type check of main HEAD, it does not merge and outputs `type check` and the failure lines. The type check result of main is made only once per commit. When the TypeScript or engine part of the branch's type check stopped before checking and that part covers files the branch changed, it does not merge and outputs `type check` and the reason it stopped. Exceptions are set by [`ogw` `## agent merge`](../../tools/ogw.md). Such an agent is called again with the same input. When several core agents were called in parallel, the lead agent merges them at once after all of them end, passing all ids. The harness tool sets the merge order. Agents assigned a tool are merged before agents assigned a module. When an id fails to merge, the lead agent calls that agent again from the current main HEAD with the same input. The core tests the lead agent runs run on the merged main.

### `create contract tool`

1. The core agent makes the contract tool and the data tool in TypeScript, following [`contract`](../contract/SKILL.md) and [`data`](../data/SKILL.md). For each tool, the folder `open-game-works-core-impl/tools/<tool>/` is one npm package
   - It has `package.json` and `package-lock.json`. `npm run build` bundles the tool and all its runtime dependencies into one file, `bin/<tool>.js`. That file runs with `node bin/<tool>.js` and reads no other file of the same folder
   - Tests are `*.test.ts` under `tests/` and run with vitest. vitest is in `devDependencies`
   - `bin/` and `node_modules/` are not committed. `open-game-works-core-impl/.gitignore` excludes both
   - Before using a tool, the harness tool runs `npm ci` and `npm run build` in that folder once per tool per command run
2. The core agent writes the parts of the base proto that `contract` sets to `open-game-works-core-impl/proto/`: all of `ogw/options.proto`, and from `ogw/core.proto`, `ServerError`, the type `BanDetail` of its field `ban` (set by [`routing`](../server-core/modules/routing.md)), `UserStateDelta`, `UserStateEntry`, and `ResponseEnvelope` without `item_changes` and `item_mails`. Step 4 of `create server core` adds the two left-out fields together with the module specs that set their field types
3. The only generation target is the server (TypeScript). Step 3 of `create client core: <engine>` adds the generation targets of an engine
4. The tests of the two tools include contracts and CSVs that give an error for each writing rules violation, backward compatibility violation pairs, base proto violation pairs of `--base-proto-only`, the encode and decode round trip of the server generation result, and generation of the base proto of `open-game-works-core-impl/proto/` without violations. `ogw core test tools` runs `vitest run --reporter=json` in the tool folder for each module (`contract-tool`, `data-tool`). A test that does not pass, a test file that failed to run, and a run with no tests are failures
5. `## review and code check` is done for the contract tool and the data tool

### `create server core`, `create client core: <engine>`

1. In `create client core`, when any of `skills/client-core/engines/<engine>.md`, `skills/client-content/engines/<engine>.md`, `skills/build/engines/<engine>.md` does not exist, the lead agent first calls the core agent with an input that names the absolute harness paths of those files as the target. When the core agent ends, the lead agent shows the written files to the human for confirmation. The lead agent commits to the harness repo when the human orders it
2. In `create client core`, the core agent writes `open-game-works-core-impl/client/<engine>/engine.json`, and the lead agent gets that engine and its programs with `ogw env install-engines`. When the engine is Godot and harness settings has no `tools.gdtoolkit`, the lead agent shows the human the change proposal `tools.gdtoolkit` that `ogw env propose` output; when the human accepts it, the lead agent applies it with `ogw env propose --apply tools.gdtoolkit`, commits, and gets it with `ogw generation install --background`. The core agents from step 3 on are called after that
3. In `create client core`, when the contract tool and the data tool do not generate code for that engine, the core agent adds the generation targets of that engine to both tools and writes the client core classes that the generated code inherits or uses, as `### generated code` of the engine-specific implementation rules says. e.g. `ContractMessage`, `ContractRequest`, `ContractKind` of Godot. It then adds the encode and decode round trip of that engine's generation result to the tests of step 4 of `create contract tool`, and makes `ogw core test tools` pass with the engine received in step 2. The contract and data that the round trip test uses are in `open-game-works-core-impl/tools/tests/game/` in the game repo structure (`contract/`, `data/`, game settings `settings.json`). `ogw core test tools` runs the two tools with that engine on a copy of that folder. The data tool of that copy runs without `--binary`, issues ID values and writes all generation targets. `ogw core test tools` does not run the round trip test of that engine until the client core of that engine passes (`ogw` `## agent merge`): the round trip test compiles the whole client core of that engine and uses the GUT hook of `UnitTestCore`. The result of a tool whose round trip test did not run is `skipped`, and the output shows that engine and the reason. Step 6 runs `skipped` modules again, so the round trip test runs after the core test of that engine passes. The engine-specific implementation rules set the location and the run of the round trip test files
4. In `create server core`, one core agent first adds to `open-game-works-core-impl/proto/ogw/core.proto` the base proto that `create contract tool` did not write, from all module specs and `## base proto` of [`server-core`](../server-core/SKILL.md), and adds `item_changes` and `item_mails` to `ResponseEnvelope`. Next it runs the contract tool without `--engine` on the core test data folder `open-game-works-core-impl/test-data/` to make the server generated code. Then it adds the tests below to the tests of step 4 of `create contract tool` and makes `ogw core test tools` pass. One is a data tool test in which an `array<{item_id: ref<item.id>, amount: long}>` column is built as `repeated` of `ItemAmount`; it checks that an `amount` whose absolute value is 2^53−1 or less goes into `amount`, an `amount` above that goes into `big_amount`, and an `amount` that is not a big integer is `value_type`. The other is a proto3 JSON conversion round trip test of `ItemChange` and `ItemMail` of the server generated code. The core agents of step 5 do not edit the base proto, and write what to change in the spec change proposals of their reports
5. After `## spec review`, the modules are assigned to several core agents. A module is assigned after all modules reached by following its `dependencies` are merged into main, and in `create server core`, the modules outside `testing`, `routing` and the modules reached by following their `dependencies` are assigned after `testing` and `routing` are merged. In `create client core`, `UnitTestCore` and the modules reached by following its `dependencies` are the base of client core tests, so they are assigned together without waiting for dependency order, and the other modules are assigned together after those modules are all merged. Client core tests compile only when every client module exists (`BootstrapCore` calls every module), so while the core test of that engine has never passed all client modules on main, a core agent writes core tests but does not run them, and step 6 runs those core tests. Modules that can be assigned are assigned in parallel. A core agent writes the implementation and core tests looking only at the spec of its own module, the specs of the modules it depends on, and the specs of the modules its own spec names in backticks. When it cannot write from the specs of other modules alone, it does not guess, and writes a spec change proposal in its report. A core agent puts the data checks of `## data` of its own spec into `checks/<module name>.ts` of the data tool source, and writes, per rule, a data tool test in which that check gives an ERROR, in the same commit as the implementation
6. `ogw core test server` (`create server core`) or `ogw core test <engine>`, `ogw core test <engine> --web`, `ogw core test tools` (`create client core`) run without a module. The tool sets the order and parallel runs. Core tests do not replace the modules they depend on with fakes. A test whose result is `fail` is fixed by the core agent assigned the module of the spec that writes the behavior the test checks. After the fix is merged, the tests run again with the modules whose result is `fail` or `skipped` passed
7. `## review and code check` is done per module. When `ogw job status` shows the core test result of a module as `pass`, it starts right away without waiting for other modules
8. `create client core` makes the benchmark game of that engine in `open-game-works-core-impl/benchmark/<engine>/` in the game repo structure and puts it into the release as `benchmark-<engine>.zip`. The benchmark game uses only core modules and screen elements drawn in code. Its resources are only scenes, prefabs and the placeholder resources core requires (e.g. reserved sound `[ui_button_click]`, `language` font, `app_icon/main`, `splash/main`), and there are no final resources of the resource sub-agent. The `auto` step of `client/dev/bot/scenario.json` repeats scene transitions, opening UI and server requests without stopping. `ogw instance measure` of `update env` measures the number of concurrent instances with this game
9. Releases with `ogw core release <version>`

### `update core`

1. Reads the core proposal file. When the human gives a request instead of a file, takes that request as a core proposal, sets `## target`, `## kind`, `## problem`, `## proposal`, and judges it the same way. When the human points to a core proposal file without giving its path, looks for it among the files whose first line is `status: proposed` in each `games/<game>/records/core-proposals/`. The format is `### core proposal` of the `game-design` skill. When `kind` is `feature` or `schema` and the target feature is not a feature that AGENTS.md `## purpose` puts in core, does not apply it and asks the human. Then decides the specs to change. When the proposal is a behavior that only one game needs, first checks whether a hook or settings can solve it
2. Edits the specs and makes `ogw docs check` pass. Does `## spec review` for each module whose spec was edited
3. Edits the implementation and core tests. Aligns every engine that has a client core implementation to the same spec. For the data checks of a changed `## data`, the check and tests of that module in the data tool are edited in the same commit. When the change modifies `engine.json`, the lead agent first merges a core agent result that changed only `engine.json`. Next it gets that engine and its programs with `ogw env install-engines` and then assigns the rest to core agents. Then it does `## review and code check` with `--since` for each module and tool that `ogw core review-targets --since <main commit when the command started>` outputs. The tool outputs the modules and tools with files changed since that commit, and adds the modules that depend directly or indirectly on a module whose public surface (`index.ts`, `dev/index.ts` of a server module, the module class, DEV class and `events/` of a client module, the `core-spec/` file of the module, the files whose paths the `server-core` skill, the server module specs and the engine-specific implementation rules write) changed. A change inside a module whose public surface stays the same does not make review targets of the modules that use that module
4. Decides the version and releases
5. When core proposal files were applied, runs `ogw core proposal released <game> <proposal file> <released version>` for each of those files. When that game has a run that is not closed, the tool defers the marking and does it when `ogw loop end` closes that run. The core version of the game is not changed. The core version of a game that uses core is raised in `update game` of that game

## spec review

Before the lead agent assigns the implementation of a module or an implementation to fix to a core agent, it runs `ogw review spec core <module> <--since <commit>|--full|--debt>` for each module whose spec is new or changed. In `update core` it gives `--since <harness repo HEAD when the command started>`, and in `create server core`, `create client core` and when the human requests the spec review of all modules, it gives `--full`. `--debt` is given when the human decided on a debt review, and is accepted only when the spec debt list of that module has items. The tool writes the input, starts one review agent and outputs the job id. The input has the definition documents of that module (the same as the definition documents of the target in `## review and code check`; the modules it depends on are read from the specs of the harness working tree, not from `core-spec/` of main), `## spec changes`, `## debt` and `## must fix`. `## spec changes` is the diff file of the module spec changed from that commit to the working tree with `--since`, an empty diff file with `--debt`, and `none` with `--full` or when the `--since` commit has no module spec file (a new module). When the module spec did not change after `--since`, the run is accepted only when the spec must-fix list of that module has items, and the tool gives an empty diff file. That review answers only the must-fix items. `## must fix` is all items of the spec must-fix list (`## review lists`) of that module, and `## debt` is all items of the spec debt list of that module when `## spec changes` is `none` or with `--debt`, and `none` otherwise. `ogw agent wait <id>` outputs the review file path and the lines of the spec review list edits made from that review file. When the review file does not follow its format, it does not edit the list and outputs the reason with exit code 1. In that case the spec review is run again. Every finding of the review file has `spec change` `yes`. The lead agent asks the human about each finding and each item of the `review must fix added:` and `review must fix raised:` lines with a recommendation, edits the spec as the human decided, makes `ogw docs check` pass, and assigns that module. For each module of a spec must-fix list that holds such an item, it runs `ogw review spec core <module> --since <harness repo HEAD before the fix>` again to check that the item was deleted. When the checking review answers that item as `open` or outputs a new must-fix item, the lead agent asks the human again with that review's evidence and a recommendation, and fixes and checks in the same order. An item that the human decided not to fix yet stays in the must-fix list and blocks `ogw core release`. The lead agent tells the human about it. Spec review does not count rounds. `ogw review clear core` deletes the input folders and review files of spec review

## review and code check

The lead agent of a core command does this per target. A target is one core module, the contract tool (`contract-tool`) or the data tool (`data-tool`). `ogw review next` and `ogw review wait` do the round counting, writing the review agent input, merging the review file and judging the result. The review state is the round and the result of the last round that these two commands keep per target. The lead agent runs `ogw review run core <target>` for each target. In `update core` it adds `--since <main commit when the command started>`. The review scope of round 1 then becomes the changes since that commit instead of the whole target. When that commit has none of the target's folders (`server/core/<module>/`, `client/<engine>/core/<module folder>/`, `tools/<tool>/`) (a new module, a new tool), it is the whole target. When the human requests a review of the whole target, it adds `--full` instead of `--since`, and when the human decides on a debt review of the target, it adds `--debt`. Only a round that reviews the whole target writes `low` findings. The tool repeats 1 and 2 below until it stops.

1. Starts a round with `ogw review next core <target>`. The tool writes the review agent input and starts the review agent and `ogw code check core` together with `--background`. Both read the main commit at the start of the round. When the result of the previous round is `fix` or `escalate`, or the round before a round started with `--continue` is `limit`, and that round's `open` findings include a finding whose `spec change` is `no` and whose aspect is `correctness`, `spec` or `security`, the tool gives the code check `--fix-base <commit that started the previous round>` to add `fix test proof`. When the `fix test proof` of the previous round is `fail` and the round that proof proves had such a finding, it gives that round's `--fix-base` again. When the proof of the same `--fix-base` is `fail` in two rounds, it does not give it again: when the code before the fix of that finding already behaved correctly (the aspect is behavior but there was no test), no test fails on that base. The second `fail` stays in the code check result of that round. The fix of a `test evidence` finding adds a test to code that already behaves correctly, so the test cannot fail on the code before the fix. Whether that test catches the defect is checked by the review agent changing the code (mutation)
2. Waits with `ogw review wait core <target>`. The tool merges the review file into main, edits the review lists as `## review lists` says, and outputs the result, the list of findings whose `spec change` is `yes`, the lines of `## out of scope` of the review file whose severity is `critical` or `high` (`out of scope:`), the lines of review list edits (`review debt added:`, `review debt removed:`, `review must fix added:`, `review must fix raised:`, `review must fix removed:`), and game impact lines (`game impact:`)
   - game impact: the findings and `## out of scope` lines of a core review whose location is a file under a game repo (`games/`). A core review does not fix games, so the tool does not count those findings as `open` findings, does not add those lines to the review lists, and outputs them only as `game impact:` lines. When the command ends, the lead agent reports each such line to the human as something that game fixes when it upgrades to this core version
   - `done`: there is no `open` finding and the code check has no `fail`. Stops
   - Type check and lint failures in files outside the target's folders (`server/core/<module>/`, `client/<engine>/core/<module folder>/`, `tools/<tool>/`) do not count as a code check `fail` when deciding the result. The tool outputs those failures as `code check fail outside target:` lines
   - `fix`: calls `ogw agent core --module <target>` with the core agent input file the tool wrote (target, review file, code check result, a `- open finding:` line per `open` finding with the `spec change` the tool counted). When the core agent ends, merges with `ogw agent merge`. When the merge fails, calls it once more from the current main HEAD with the same input as `## command` says, and when it still fails to merge, stops with `not merged`. After the merge, when the target is a module, runs the core tests of the modules with an implementation among the modules that `ogw core dependents <target>` outputs. When the merged core agent job did not change files outside `records/`, does not run core tests. Server modules run with `ogw core test server`, and client modules run with `ogw core test <engine>` and `ogw core test <engine> --web` for each engine with an implementation. When the target is a tool, runs `ogw core test tools`. When a test of the target is `fail` or the run stops before the tests, stops with `test fail`. When only tests of other modules are `fail`, the tool runs those modules again in a worktree of main right before the fix was merged (the first parent of the merge commit; when that commit is not found, the commit that started the round). This is because the fixes of several modules are merged into main in parallel, and a failure made by another merge after the round started is not to be counted as a failure of this fix. When it is `fail` there too, it is a failure that existed before the fix. When it passes there, and main changed files outside `records/` after that merge commit, it runs again in a worktree of that merge commit too, and when it passes there, it is a failure made by a later merge. These two failures do not stop the run and are output as `pre-existing test fail:` lines in the job output. Other failures are failures made by the fix, so it stops with `test fail`. When it does not stop, goes to 1
   - `escalate`: the first chain did not converge. Does the same as `fix` with the escalation input the tool wrote. The escalation input has the review files and commit ranges of all rounds of that chain
   - `blocked`: all remaining findings are findings whose `spec change` is `yes`. Stops
   - When a finding written with `spec change` `yes` in a round before the round started with `--respec` is still `open` in a later round, the tool counts that finding as a finding whose `spec change` is `no`. The definition has already changed, and what is left is a code fix
   - `limit`: a chain that is not the first chain did not converge. Stops
   - `invalid`: goes to 1. Stops at the second `invalid` in a row

- A chain is the rounds that continue from round 1, from a round after `escalate`, or from a round started with `--continue`, `--respec` or `--reopen`. A chain not converging means one of the following. The result is `escalate` for the first chain and `limit` otherwise
  - The round count of the chain reached harness settings `reviewRounds` and the result is not `done`
  - A finding whose `spec change` is `no` is still `open` after two fixes in that chain
- `fix test proof`: runs the tests on the target code of the `--fix-base` commit, with the target's test files changed from that commit to the round start commit laid over it. `ogw review next` gives the code check the round start commit as `--commit` and the review target as `--target` together. The target's test files are the files under `server/core/<module>/tests/`, `client/<engine>/core/<module folder>/tests/`, `tools/<tool>/tests/`. The tests run with `ogw core test` on the target only (an engine without `--web`). When one or more are `fail`, the result is `pass`. It means that a fixed test checks the fixed behavior only when it fails on the code before the fix. When all are `pass`, the result is `fail`. When there is no changed test file, or the core test stops before the tests or before starting the test runner (vitest, GUT) (e.g. dependency installation failure, no vitest), the result is `unknown` and the reason is output. For a `fail` after the runner starts, a crash or a timeout is also `fail`
- When the target's code outside its test files (outside `tests/` in `server/core/<module>/`, `client/<engine>/core/<module folder>/`, `tools/<tool>/`; `tools/src/` for harness `tools/`) did not change from the `--fix-base` commit to the round start commit, `fix test proof` is `unknown`. This is because with a fix that edited only tests (e.g. a `test evidence` finding), the code before the fix equals the code after it, so no test can fail on it
- The type check and lint of `ogw code check core` do not read files under `benchmark/`. The benchmark game is a game repo, and its server code compiles only together with the server core of a core release. The other checks (dependency, secret) also read `benchmark/`
- `ogw code check` uses the `node_modules/` of that checkout for each package folder of the code it checks. When the checkout has none (a tool package in a core agent worktree), it uses the `node_modules/` of the main checkout when the `package-lock.json` of that package equals the one in the `open-game-works-core-impl/` main checkout. The check does not put links in the checkout: when a package has to use it that way, the check puts the checkout's files in the check's work folder, links there and checks. A link in the checkout that goes to the `node_modules/` of the main checkout (left by an earlier check) does not count as the checkout's own. While it checks, `ogw code check core` is a reader of the build lock of each tool folder of the main checkout, so a tool build does not change `node_modules/` in the meantime
- Each time `ogw review run` finishes a step, when harness `tools/` differs from when the job started (the `tools` tree of harness repo HEAD), it continues `ogw review run core <target>` in a new process of the changed code and outputs its result. The new process takes over the count of consecutive `invalid` results that the job counted and the `pre-existing test fail:` lines that the job collected. A long-running job does not keep running on the harness code from when it started
- `ogw review run` continues from the review state. When the last round has not been judged, it starts from 2. When the result of the last round is `fix` or `escalate`, it starts from that result of 2, but when a core agent job called with that input after the round was judged (after the review agent job of that round ended) ended as `done` and was merged, it starts from the core test; when it ended as `done` but was not merged, from the merge; when it is running, from waiting for that job. A job that ended in a state other than `done` has no report, so it is not merged, and even when merged it does not count as a fix of that round. When there are only such jobs, it starts from calling the core agent again. When the result of the last round is `done`, `blocked` or `limit`, it starts no round and stops with that result
- `--restart` deletes the review state and starts from round 1. When the definition documents of the target did not change after the last round started, the tool refuses it
- `--respec` keeps the review state and starts a round of a new chain. The review scope of that round is the changes since the commit that started the last round, and input `## spec changes` gets the diff file of the definition documents changed since the harness commit at the start of the last round. The review agent compares the target code and tests that the definitions changed by that diff reach, regardless of the scope. When the definition documents did not change after the last round started, or the last round did not record a harness commit, the tool refuses it (then use `--restart`)
- `--continue` is accepted only when the result of the last round is `limit`. It starts the first round of a new chain. The review scope of that round is the changes since the commit that started the `limit` round
- `--reopen` is accepted only when the result of the last round is `done` and either the target's folders (`server/core/<module>/`, `client/<engine>/core/<module folder>/`, `tools/<tool>/`, harness `tools/`) or `core-spec/<module>.json` changed since the commit that started that round, or the target's must-fix list (`## review lists`) has items. It starts the first round of a new chain. The review scope of that round is the changes since the commit that started the `done` round
- `--full` and `--debt` are accepted only when there is no review state or the result of the last round is `done`, and they start a new review. After `done`, it is the first round of a new chain. The review scope of a `--full` round is the whole target. The review scope of a `--debt` round is the items of the target's debt list, and its commit range is from the commit that started that round to the same commit (no changes). `--debt` is accepted only when the target's debt list has items. Neither is accepted together with `--since`, `--restart`, `--respec`, `--continue`, `--reopen`, or with the other
- The tool records `--since`, `--continue`, `--respec`, `--reopen`, `--full`, `--debt` in the review state. `--since` is also used for the round 1 that starts again after round 1 is deleted as `invalid`, and `--continue`, `--respec`, `--reopen`, `--full`, `--debt` are used until the round started with them is judged with a result other than `invalid`. A rerun of `ogw review next` or `ogw review run` does not need that option again
- When an `ogw review run` job of the same target is running, a new job does nothing and fails
- The review agent jobs, core agent jobs and core test jobs that all `ogw review run` jobs on this host run together are at most harness settings `reviewRunConcurrency`. When there is no free slot, a job waits until a slot frees up
- When it stops, the job output has `result: <done|blocked|limit|invalid|not merged|test fail>` and the last judged round. With `invalid`, it also outputs the `review job not merged` line that `ogw review wait` output in the last `invalid` round, or, when there is no such line, a line saying that the review file is missing or does not follow its format, with its path. With other results, it outputs the `open finding` lines and `code check fail` lines of the last `ogw review wait` output, and also the reason the merge failed with `not merged`, and the `fail` modules and tests with `test fail`. It also outputs the `out of scope` lines, `game impact` lines and review list edit lines of all judged rounds
- `ogw review status <core|tool>` outputs, for each target with a review state, the last round, its result (`running` before judgement), the ids of the `open` findings whose `spec change` is `yes` in the last judged round, and the id of the running `ogw review run` job

The lead agent does the following for each stopped result and finding.

- A finding whose `spec change` is `yes`: the lead agent asks the human about each finding with a recommendation. Such a finding is not passed to a core agent. When the human edits the spec, that target continues with `ogw review run core <target> --respec`. When an `ogw review run` job of that target is running, the lead agent ends that job first and then does this
- `limit`: the lead agent asks the human about the remaining `open` findings, the `fail` code checks and the review file paths of the two chains, with a recommendation. When the human decides how to fix them, the lead agent assigns that fix to a core agent, merges it, and runs `ogw review run core <target> --continue`
- `done`: when the command later changes the code of that target (a fix the human decided, a fix of another finding), that target is reviewed again with `ogw review run core <target> --reopen`
- `test fail`: fixes and merges the same way as a core test failure in `## command`, then runs `ogw review run core <target>` again
- `not merged`, `invalid`: removes the cause that the job output gives, then runs `ogw review run core <target>` again
- To run `ogw review run core <target>` again or continue it after merging a core agent job, the lead agent does not wait on the job directly but runs `ogw agent merge <id> --when-done --then "review run core <target> <option>" --background`. `<option>` is the option that the result set above (`--continue`, `--respec`, `--reopen`), left out when there is none. When that job failed to merge, the lead agent calls that agent again as `## command` says. When it merged but there is a `then not started` line, the lead agent runs that `review run` directly with `--background`
- `out of scope` lines (severity `critical`, `high`): as a problem of the module or tool the file belongs to, the lead agent assigns it to a core agent the same way as a core test failure in `## command` and fixes it right away. When the same line comes from several targets, it is assigned only once. That item is in the must-fix list, and the next review round of that module or tool checks that it was fixed and deletes it. When no review of that module or tool is running, the lead agent runs `ogw review run core <that target>` after the fix, giving `--since <main commit before assigning>` when there is no review state and `--reopen` when the last round is `done`
- `review must fix added:` lines with `(was D<n>)`: an item that was in the debt list rose to severity `critical` or `high` and moved to the must-fix list. The lead agent tells the human and fixes it the same way as an `out of scope` line
- `review debt added:` lines: not fixed in that review. Written in the report to the human
- `code check fail outside target:` lines: as a failure of the module or tool the file belongs to, the lead agent finds the cause and fixes it the same way as a core test failure in `## command`. When the same line comes from several targets, it is assigned only once. The review of that target does not wait for it
- `pre-existing test fail:` lines: as a failure of that module, the lead agent finds the cause and fixes it the same way as a core test failure in `## command`. The review of that target does not wait for it

## review lists

A review list keeps, per target, the problems that a review found outside its scope. There are two kinds.

| list | item | meaning | review scope | release |
|---|---|---|---|---|
| debt list | severity `medium` | Deferred problems | In the scope of the debt review (`--debt`) and of reviews of the whole target (`--full`, a target that did not exist at the `--since` commit, round 1 without `--since`). Other reviews do not put debt items in their scope | Does not block |
| must-fix list | severity `critical`, `high` | Problems to fix right away | In the scope of every review of the target | Blocks when it has items |

- The file of the debt list is `open-game-works-core-impl/records/review-debt/<target>.json`, and that of the must-fix list is `open-game-works-core-impl/records/review-must-fix/<target>.json`. For the lists of a spec review, the target is `spec <module>` and the file is `spec-<module>.json`
- The format of both is `{"target": "<target>", "nextId": <integer>, "items": [<item>, ...]}`. A debt list item is `{"id": "D<n>", "location": "<file:line>", "problem": "<problem and evidence>", "foundBy": "<target> round <round>"}`, and a must-fix list item is `{"id": "M<n>", "severity": "<critical|high>", "location", "problem", "foundBy"}`. `foundBy` of an item that a spec review added is `spec <module>`. `<n>` is `nextId` at the time of adding, and the number of a deleted item is not used again
- Only the tool writes review lists. The tool commits the changed lists to `open-game-works-core-impl/` main
- Adding: when `ogw review wait` judges a round with a result other than `invalid`, it adds an item for each line of `## out of scope` of the review file. `medium` goes to the debt list, `critical` and `high` to the must-fix list. When the location of a line is an absolute path under the review agent's worktree or checkout, it is rewritten as a path relative to the checkout. When the file of a line is under the folder of a module or tool (`server/core/<module>/`, `client/<engine>/core/<module folder>/`, `core-spec/<module>.json`, `tools/<tool>/`), the item goes to the list of that module or tool, and otherwise to the list of the review target. For a spec review, `ogw agent wait` does the same with the review file of that job, and adds the item to the spec list of another module when the file of the line is that module's spec, and to the spec list of the target module otherwise
- Same location: when it is in the must-fix list of that target, nothing is added, and when the new line is `critical` and the item is `high`, the item is raised to `critical` (`review must fix raised:`). When it is in the debt list and the new line is `medium`, nothing is added. When it is in the debt list and the new line is `critical` or `high`, that item is deleted from the debt list and added to the must-fix list (`review debt removed:` and `review must fix added:` with `(was D<n>)`)
- Deleting: at the same time, the items that are `fixed` or `withdrawn` in `## debt` and `## must fix` of the review file are deleted from that list of the target
- Scope: `ogw review next` writes all items of the target's must-fix list in input `## must fix`. In input `## debt`, only for a review that puts the debt list in its scope, it writes the items that were in the debt list when that review started. A review starts at round 1 and at a round started with `--reopen`, `--full` or `--debt`. Debt items added while that review runs are not in that review's scope
- When the rows of `## debt` and `## must fix` of the review file do not match the items of the input one to one, or an `open` row does not point to an `open` finding in that review file, that round is `invalid`

## test

- Each `## test` item of a spec has one or more core tests. Core tests are in `open-game-works-core-impl/` and are not copied into games
- The core test data folder `open-game-works-core-impl/test-data/` holds, in the same structure as a game repo root, `data/` (the structure of game repo `data/`), `contract/` (the game contract that core tests use), a game settings `settings.json` that passes the game settings schema, and the banned word list `records/setup/banned-words/` that core tests use. `contract/` has the UserState kinds, the `rpc`s of `service Game` and `service Cheat`, and `GameError` needed by the `## test` items for which a server core test has to use a game contract, and `data/` has the core table rows those items need. `service Game` has `rpc RunCoreTest` (`changes: content`) with an empty request and an empty response, and a server core test calls the module operations that need ctx in the `RunCoreTest` handler that its own `register` registered. `GameError` has `GAME_ERROR_CORE_TEST` (1000) that hooks return, and `service.proto` writes it in `(ogw.core_errors)` for each core `rpc` that calls a content hook. The ID registry is not in this folder. `ogw core test` builds the core test data with the data tool before the tests. Data tool arguments, the ID registry and generation targets follow `## CLI`, `## ID registry` and `## processing` of the data tool reference `tool.md` of the [`data`](../data/SKILL.md) skill
- Client core runs its tests per engine. Server core tests run on both SQLite and PostgreSQL. A `## test` item that starts with `On PostgreSQL` runs only on PostgreSQL. The file location, run, input and result of server core tests are in `### test run` of [`testing`](../server-core/modules/testing.md)
- A module with an external service is tested with the fake adapter. The real adapters and sandbox adapters of server core are put into the test server of `testing` as the real adapter list, and are tested without the external service with the key source set by `set_key_source` and the secret test values made by `start_test_server`
- core test fixture: an input and expected value file that client core tests and server core tests both read. It is in `open-game-works-core-impl/fixtures/<name>.json`, and the name is kebab-case. The format is `{"cases": [{"name": "<case>", "input": <JSON value>, "expected": <JSON value>}, ...]}`, with one or more cases. The JSON format of `input` and `expected` is set by `## test` of the spec that names that fixture. For a value whose key name the spec does not write, the core agent that first writes the fixture sets a snake_case key, and later implementations follow the keys of the fixture file. The client reads it with `read_core_fixture` in `UnitTestCore`, and the server with `read_core_fixture` in `testing`. Values that the spec does not set otherwise are written as below
  - An integer is a JSON integer. An integer whose absolute value can be more than 2^53−1 and a big integer are decimal strings
  - NaN and infinities of real numbers are the strings `NaN`, `Infinity`, `-Infinity`
  - An enum value is an element name (`## spec` of [SKILL.md](SKILL.md)) string, and a missing value is `null`
  - A UserState row is an object with the field names as keys
- A case of a core test fixture does not hold table rows. The rows that a case uses are put only once in `data/` of the core test data, and `input` and `expected` of a case point to rows and ID values by their ID name strings. e.g. `"[item_recovery_basic]"`. ID value 0 is written as the number `0`. Client core tests read those rows from the core test data that `DataCore` loaded, and server core tests read them with `load_data` in `testing`, and ID names are converted to ID values with the DEV accessors of the data tool
- After building the core test data, `ogw core test` collects the strings whose whole value is an ID name from `input` and `expected` of all core test fixtures. When such an ID name is in no table `id` column of the core test data and is not the ID name of a `requirement` row that the data tool made, it reports the fixture name and the ID name and fails without running tests
