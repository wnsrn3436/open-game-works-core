## engine version

- The core release sets the Godot version. `open-game-works-core-impl/client/godot/engine.json` goes into the root of `client-godot.zip`

  | field | contents |
  |---|---|
  | `godot` | The leading part of the `godot --version` output up to the version number and status. e.g. `4.5.1.stable` of the output `4.5.1.stable.official.<hash>` |
  | `downloads` | Distributions of the Godot editor and the export templates. Per item `platform` (`macos-arm64`, `linux-x64`, `windows-x64`, `any` for the export templates), `url`, `sha256` |
  | `gut` | Distribution of the test framework GUT. The fields are `version`, `url`, `sha256` |
  | `plugins` | One item per native plugin. The fields are `name` (plugin name), `version`, `platforms` (list of target platforms, from `android`, `ios`, `macos`, `windows`, `linux`), `url` (distribution URL), `sha256` (distribution SHA-256) |
  | `buildTools` | Host programs that the export and signing of a platform build need. Per item `platform` (build target platform), `hosts` (hosts that need the program, from `macos-arm64`, `linux-x64`, `windows-x64`), `name`, `version`, `versionCommand` (command that prints the version; the output must start with `version`), `downloads` (only for programs that can be downloaded; the item format is the same as `downloads`) |

- The `url` of the items of `gut` and `plugins` whose name does not start with `ogw-` is a zip file, and the paths in the zip are relative to the Godot project root. e.g. `addons/gut/plugin.cfg`. When the zip root has only one folder and that folder contains one of `addons/`, `ios/`, `android/` (e.g. `Gut-9.7.1/addons/gut/plugin.cfg` of a GitHub tag archive), the inside of that folder is taken as relative to the project root. The harness tool compares the SHA-256 of the downloaded zip with `sha256` and stops when they differ. When they are equal, it extracts the zip into the project root at those paths
- The core agent writes the items of `downloads`, the `downloads` of `buildTools`, `gut`, and the `plugins` whose name does not start with `ogw-` up to their `url`, and runs `ogw core pin-engine godot`. For each of those items the tool downloads the file at `url` and writes `sha256`. `ogw core release` writes the URL and SHA-256 of the plugin items whose name starts with `ogw-`
- Before a dev run, test, or build, the harness tool checks that `godot --version` starts with the `godot` value, and stops when it does not. The export templates are also of the same version
- The harness tool puts the downloaded Godot editor in self-contained mode. It puts the `_sc_` file and `editor_data/export_templates/<godot value>/` (export templates) in the folder that has the executable, and on macOS in the folder that has `Godot.app`. It writes no file inside the signed `Godot.app`
- Raising the Godot version is a major or minor change of `update core`
- The only language is GDScript. C# and GDExtension are not used as core code. A native SDK comes in only as a plugin of `plugins`
- Native plugins that core modules use

  | plugin | target platform | module | contents |
  |---|---|---|---|
  | `ogw-secure-storage` | `android`, `ios`, `macos`, `windows`, `linux` | `AuthCore` | login token storage. On Android it is app-private storage encrypted with an Android Keystore key and excluded from Auto Backup. On iOS and macOS it is a Keychain item readable only on this device, on Windows Credential Manager, on Linux Secret Service |
  | `ogw-apple-signin` | `ios`, `macos` | `AuthCore` | Sign in with Apple (AuthenticationServices) of the `login-apple` real adapter |
  | `ogw-google-signin` | `android`, `ios` | `AuthCore` | `login-google` real adapter. Android Credential Manager, iOS Google Sign-In SDK |
  | `webrtc-native` | `android`, `ios`, `macos`, `windows`, `linux` | `RealtimeCore` | Godot WebRTC GDExtension. The browser runtime uses browser WebRTC |
  | `ogw-native-ui` | `android`, `ios`, `macos` | `NativeUiCore` | store review request window (Google Play In-App Review API, `SKStoreReviewController`) and share window (Android Sharesheet, `UIActivityViewController`, `NSSharingServicePicker`) |
  | `ogw-tracking` | `ios` | `AuthCore` | reading the tracking permission state of App Tracking Transparency and requesting tracking permission |
  | `ogw-iap-apple` | `ios`, `macos` | `PaymentCore` | store adapter of store `APPLE`. StoreKit 2 |
  | `ogw-iap-google` | `android` | `PaymentCore` | store adapter of store `GOOGLE`. Google Play Billing Library |
  | `ogw-ads-admob` | `android`, `ios` | `AdCore` | `admob` adapter. Google Mobile Ads SDK and Google UMP SDK |
  | `ogw-push-fcm` | `android` | `PushCore` | FCM push adapter. Firebase Cloud Messaging |
  | `ogw-push-apns` | `ios` | `PushCore` | APNs push adapter. Remote notification registration and receiving |
  | `ogw-notification` | `android`, `ios` | `PushCore` | notification adapter. On Android the notification permission and notifications posted by delayed work of `WorkManager`, on iOS `UNUserNotificationCenter` |

- A plugin whose name starts with `ogw-` is a plugin without a distribution. The core agent writes its source and builds it
  - The source is in `open-game-works-core-impl/client/godot/plugins/<plugin>/`
  - The build result is put in `plugins/<plugin>/dist/<platform>/` per target platform of the plugin and committed. The paths inside are relative to the Godot project root: for android the `.aar` and export plugin of Godot Android plugin v2 under `addons/<plugin>/`, for macos, windows, linux the `.gdextension` and library under `addons/<plugin>/`, for ios the `.gdip` and `.xcframework` under `ios/plugins/<plugin>/`
  - Build method: for android `./gradlew assembleRelease` in the plugin's Gradle project, for ios `xcodebuild archive` and `xcodebuild -create-xcframework`, for macos, windows, linux `scons platform=<platform> target=template_release` with godot-cpp of the same branch as the `godot` version. ios and macos are built on a Mac host, windows on a Windows host, linux on a Linux host
  - `ogw core release` puts `dist/<platform>/` of each plugin into a zip as `<plugin>/<platform>/` and makes the core release asset `client-godot-plugins.zip`. `ogw generate` and `ogw build run` put the contents of `<plugin>/<platform>/` of that platform into the game's `client/` at those paths. How `ogw build run` enables android and ios plugins is set by `engines/godot.md` `## export` of the `build` skill
- Interface of the `ogw-` plugin singletons. For a long-running operation, `start_*` returns an operation ID (0 when it cannot start), and the adapter reads the result each frame. When the adapter ends the wait before the result (time limit, `release`), it makes the cancel call, and the plugin discards the result of that operation. The module's `release` calls the adapter's `stop()` (`NativeUiAdapter`, `SocialAdapter`, `StoreAdapter`, `PushAdapter`, `NotificationAdapter`, the tracking adapter of `AuthCore`) and `release()` (`AdsAdapter`), which end all waits
  - `OgwIapApple`, `OgwIapGoogle`: `start_connect()`, `start_query_prices(skus)`, `start_buy(sku, product_type, account_token)`, `start_list_unfinished()`, `start_list_owned()`, `start_finish(sku, transaction_id, data, product_type)`, `start_open_subscription_management()`, `take_result(id) -> PackedStringArray` (an empty array before it ends, `[status, ...]` once when it ends), `cancel(id)`, `take_events() -> PackedStringArray` (`disconnected`, or `purchase` with sku, transaction, data)
  - `OgwNativeUi`: `request_review() -> bool`, `start_share(text, png) -> int`, `take_share_result(id) -> PackedInt32Array` (an empty array, then `[0]` closed or `[1]` failed), `cancel_share(id)`
  - `OgwPushFcm`, `OgwPushApns`: `start_token_request()`, `token_state(id)` (0 in progress, 1 ended), `take_token(id)`, `cancel_token_request(id)`, `take_launch_push()`, `next_event()`, `event_token()`, `event_message_id()`
  - `OgwNotification`: `start_read_permission()`, `start_request_permission()`, `permission_state(id)` (−1 in progress, 0, 1, 2), `cancel_permission(id)`, `schedule_local(id, title, body, delay_ms) -> bool`, `cancel_local(id)`, `cancel_all_local()`
  - `OgwAppleSignIn`: `start_sign_in()`, `take_result(id)`(`[status, identity token, authorization code]`), `cancel(id)`. `OgwGoogleSignIn`: `start_sign_in(client_id)`, `take_result(id)`(`[status, ID token]`), `cancel(id)`. `OgwTracking`: `get_status() -> int`, `start_request()`, `take_result(id) -> PackedInt32Array`, `cancel(id)`
  - `OgwSecureStorage`: `start_read(name)`, `start_write(name, text)`, `start_remove(name)`, `take_result(id)`(`[status, text]`), `cancel(id)`
  - `OgwAdsAdmob`: `request_consent()`, `is_privacy_options_required() -> bool`, `show_privacy_options()`, `initialize(personalized, child, below_consent_age)`, `load_ad(type, unit_id, personalized, child, below_consent_age)`, `present(type, unit_id, user_id, custom_data)`, `open_banner(unit_id, personalized, child, below_consent_age)`, `close_banner()`, `discard_ads()`, `take_result(id)`, `cancel(id)`
  - The module's `init` passes the adapter time limits: `StoreAdapter.call_timeout_ms` (`PaymentCore.storeCallTimeoutMs`), `PushAdapter.token_timeout_ms` (`PushCore.deviceTokenTimeoutMs`), `AdsAdapter.call_timeout_ms` (`AdCore.sdkCallTimeoutMs`), `TokenStorage.call_timeout_ms` (`AuthCore.storageCallTimeoutMs`), `NotificationAdapter.permission_read_timeout_ms` (`PushCore.permissionReadTimeoutMs`)
- When an adapter not in the table needs a native SDK, the core agent makes an `ogw-<adapter key>` plugin and adds it to this table
- When an `ogw-` plugin that targets ios calls an Apple required reason API, the core agent puts `PrivacyInfo.xcprivacy` in that plugin and writes the API category and reason

## folder

`open-game-works-core-impl/client/godot/` is itself a Godot project.

- `project.godot` is a generated file that `ogw core test` writes when it starts. Its contents are the settings that the harness tool writes in the game project's `project.godot` minus the app name, icon, splash, main scene, orientation, and viewport size (renderer, import, export, GDScript warnings, core actions), plus `application/config/name` `ogw-core` and `physics/common/enable_object_picking=false` (core modules do not use physics object picking; picking creates the root viewport's 2D physics space at the first mouse event in the window)
- The Web export is `variant/thread_support=true`. A Web export without threads (Godot 4.7.2) leaks one `Group` per `WorkerThreadPool` group task (the whole body of `wait_for_group_task_completion` is inside `THREADS_ENABLED`), and a game that steps a physics space grows memory every physics frame and prints `ERROR: Pages in use exist at exit in PagedAllocator` at exit. An export with threads frees the groups (measured). Check again when the engine version is raised
- The harness tool writes `audio/general/default_playback_type.web=0` (`Stream`) in `project.godot`. The browser runtime also plays through the engine mixer and runs the bus effects (`Master` limiter)
- The module list file `generated/core_modules.gd` of the core project is also a generated file that `ogw core test` writes when it starts. Its contents are the module list of `## module`, and the modules are chosen from the client modules of `core-spec/` by that rule
- The core settings file `generated/core_settings.json` and the core settings type file `generated/core_settings_types.json` of the core project are also generated files that `ogw core test` writes when it starts. Their contents are made the same way as those files that the harness tool writes in a game, from `settings/core-settings.json` and the game settings of the core test data (`test-data/settings.json` filled with the game settings schema defaults)
- `addons/`, `.godot/`, and `build/`, which the core test data binary build writes, are folders that the harness tool fills at test time, so they are not committed. The core project's `.gitignore` (`client/godot/.gitignore`) excludes the three

```

  engine.json
  project.godot              written by the harness tool
  core/<module folder>/      one module
    <module folder>.gd       module class
    adapters/                external service adapter
    dev/                     DEV code of that module
    tests/                   core tests. Not put in a release
  core/core_settings.gd      core settings reader. Not a module
  core/web/ogw-shell.html  HTML shell of the Web export (`html/custom_html_shell`). Godot 4.7.2 `godot.html` with only the page reopen for cross-origin isolation fixed. Not put in the pck
  core/web/service-worker.js service worker of the Web export. Godot 4.7.2 `godot.service.worker.js` with the null body status and status 0 responses fixed. Keeps the placeholders that the Godot exporter fills as they are. The harness tool replaces the exported `index.service.worker.js` with this file, filled with the placeholder values copied from the same lines of the exported file. When there is not exactly one matching line, the export fails. Not put in the pck
  core/core_script_errors.gd `class_name CoreScriptErrors`. Detector of GDScript runtime errors during hook calls. Not a module
  core/core_build_info.gd    `class_name CoreBuildInfo`. The build info `platform` and app storage root that `BootstrapCore` set, and `has_dev_code`. Not a module
```

- `<module folder>` is the snake_case of the module name. e.g. `UICore` → `core/ui_core/`, `LocalDataCore` → `core/local_data_core/`
- `client-godot.zip` holds `core/` without `tests/`, and `engine.json`. `ogw generate` puts the zip's `core/` into the game's `client/core/`, and the path in the game is `res://core/<module folder>/`. The static check `core diff` compares `client/core/` with the zip's `core/`
- `ogw generate` (GUT and the plugins whose `platforms` has this host OS) and `ogw build run` (the plugins whose `platforms` has the build platform) put `client/addons/`, `client/android/`, `client/ios/plugins/` in by `gut` and `plugins` of `engine.json`, and these are not committed

## module

- A module is a static class. It is declared as `class_name <Module>` in `core/<module folder>/<module folder>.gd` (`core/<module folder>/dev/<module folder>.gd` for `QACore` and `UnitTestCore`, whose whole module is DEV code); operations are `static func` and state is `static var`. No instance of a module class is created
- Autoload is not used. `project.godot` has no `[autoload]`
- A module that needs engine callbacks, child nodes, engine signals, or `EventCore` subscriptions creates one core node. The core node is `<module folder>_node.gd` (`extends Node`) in the module folder, and `init` attaches it as a child of `(Engine.get_main_loop() as SceneTree).root`
- `BootstrapCore` has no `init` and no `release`. Its core node is created at the first `start_boot` or `shutdown` it receives, attached to root, and kept until the process ends. The reverse-order `release` of the modules and `shutdown` do not detach this core node. `BootstrapCore` reads the keys of `## settings` with `CoreSettings` in `InitModules` 1 of each boot. Its subscription callbacks are instance methods of this core node
- When state is split into several objects, `RefCounted` classes without `class_name` are put in the module folder, and the module class references them with `preload()` constants. The path is an absolute path starting with `res://core/<module folder>/`
- An adapter is `adapters/<name>_adapter.gd`, which extends the module's adapter base class (`extends RefCounted`). A fake adapter is DEV code, so it is in `dev/adapters/`. `BootstrapCore` chooses and passes the adapters. Adapter and fake adapter files declare `class_name <Name>Adapter` (PascalCase of `<name>`), and `BootstrapCore` creates them by that name
- Core settings are in `core_settings.json` (`res://generated/core_settings.json`), which the harness tool writes in the logical folder `client/generated/` with the `core` of game settings merged in. The items whose `source` in spec `## settings` is `game` are also in the same file, keyed by the game settings path. In `init`, a module reads the keys written in `## settings` of its module spec with `CoreSettings`. When a key is missing or its type differs from the schema, it leaves an error log and `init` fails. When `static var _test_values: Dictionary` has the key, `CoreSettings` returns that value before the file value. Only the `UnitTestCore` operations `set_test_settings`, `set_invalid_test_settings` and the test setup write `_test_values`
- The core settings type file is `res://generated/core_settings_types.json`, which the harness tool writes next to `core_settings.json`. It is a JSON object that has, for each row of spec `## settings` of all prepared modules (`## module` of the `core` skill) (in the core project, all modules of `core-spec/`), the row's key (for a key with `<ENV>`, the key replaced per environment as in `core_settings.json`) as key and the row's `type` string as it is as value. Only `UnitTestCore` reads it. `set_test_settings` compares a value with the type in this file, not with the value in `core_settings.json`. `set_test_settings` and `set_invalid_test_settings` treat a key not in this file as a missing key
- `CoreSettings` has, per type of the settings table, `static func has_<kind>(key: String) -> bool` (the key exists and its value is that type) and `static func get_<kind>(key: String)`. `<kind>` and the returned type are: for `boolean` `bool` (`bool`), for `integer` `int` (`int`), for `number` `float` (`float`), for `string` `string` (`String`), for `array<integer>` `int_array` (`PackedInt64Array`), for `array<string>` `string_array` (`PackedStringArray`), for `object` and `array<object>` `value` (`Dictionary` or `Array` as the JSON value is). An `object` whose values are all strings is also read with `string_map` (`Dictionary[String, String]`). `has_key(key)` is whether the key exists, regardless of type
- The build info file is `res://generated/build_info.json`, which the build tool writes. Its keys are the field names of `BuildInfo` of `BootstrapCore`, and a DEV build adds `dev_access`. `update_trust_keys` is an array of objects with string `key_id`, `public_key`; `adapters` is an object whose values are strings; `ad_units` is an object with the decimal integer string of a placement ID value as key and the ad unit ID string as value; the other fields and `dev_access` are strings. A missing `dev_access` is the empty string. When this file does not exist, it is a dev run
- The game's license manifest is `res://generated/licenses.json`, which the harness tool writes. `UICore` reads it in `open_licenses`
- A launch value is the value in the launch value file that the command line user argument (after `--`) `--launch-values=<path>` points to. The launch value file is a JSON object keyed by launch value name. The path is found with `OS.get_cmdline_user_args()` and the file is read with `FileAccess`. Launch values are not taken on the command line
- When a DEV export has `res://generated/launch_values.json`, a launch value not in the launch value file takes the value in that file. Its format is the same as the launch value file
- The only module that reads the build info file and launch values is `BootstrapCore`. `BootstrapCore` puts the `platform` of the `BuildInfo` it set in `InitModules` 1 into the core static value `CoreBuildInfo.platform`. Other core modules read the platform from `CoreBuildInfo.platform` and do not decide it with `OS.get_name()`. As an exception, implementations that use `JavaScriptBridge` and browser APIs are chosen by whether it is the browser runtime (`OS.get_name()` is `Web`). When a dev run emulates `OGW_PLATFORM` `web`, it is not the browser runtime, so the implementation of the running OS is used instead of that implementation. Before `BootstrapCore` sets it and after `shutdown`, `CoreBuildInfo.platform` is the platform of the running OS
- `BootstrapCore` puts the app storage root it set in `InitModules` 1 into `CoreBuildInfo.storage_root` (`String`; `user://` or `user://instances/<instance_id>/`). `LogCore`, `LocalDataCore`, `QACore` open app storage files at `CoreBuildInfo.storage_root` joined with the path and do not use `user://` directly. Before `BootstrapCore` sets it and after `shutdown`, `CoreBuildInfo.storage_root` is `user://`
- `CoreBuildInfo.has_dev_code` (`bool`) is the result of `ResourceLoader.exists()` on the DEV entry path constant of `BootstrapCore`, set once when `CoreBuildInfo` is first read. Where a spec splits behavior between builds with DEV code and STG·PROD builds, the core module chooses by this value
- Resource key constants are `const <constant name>: String`, one per resource key, in `class_name ResourceKey` (`extends RefCounted`) of `res://generated/resource_key.gd`, which the harness tool generates. `## resource key` of [`resource`](../../resource/SKILL.md) sets the constant names
- The module list is `static func modules() -> Array[CoreModuleEntry]` of `class_name CoreModules` (`extends RefCounted`) in `res://generated/core_modules.gd`, which the harness tool generates. `CoreModuleEntry` is `class_name CoreModuleEntry` (`extends RefCounted`) in `core/bootstrap_core/core_module_entry.gd` and has the typed fields `name: String`, `init: Callable`, `release: Callable`, `is_initialized: Callable`. Each `Callable` is a reference to a static func of the module class. e.g. `UICore.init`. When `boot.gd` omits the module list, `BootstrapCore` uses this
- The DEV entry creates the `QACore` item that the `QACore` addition of `BootstrapCore` `## DEV` adds

## API

| spec | GDScript |
|---|---|
| operation | `static func` of the same name. e.g. `open_panel` → `UICore.open_panel()`. GDScript names of operations and adapter operations whose name collides with a GDScript keyword, a global function, or an `Object` method: `ResourceCore` `preload` → `preload_resources()`, `AdCore` `preload` → `preload_ad()`, `load` in the `AdCore` ads adapter → `load_ad()`, `UserStateCore` `get` → `get_by_id()`, `connect` in the `PaymentCore` store adapter → `connect_store()`, `disconnect` in the `RealtimeCore` transport → `disconnect_all()`. The `LocalDataCore` operations `get_value`, `get_array`, `set_value`, `set_array`, which take a value type as input, are `<operation>_<type>` per type. `<type>` and the value types are `int` (`int`, `PackedInt64Array` for arrays), `float` (`float`, `PackedFloat64Array`), `bool` (`bool`, `Array[bool]`), `string` (`String`, `PackedStringArray`). e.g. `get_value_int(kind, key, default: int) -> int`, `set_array_string(kind, key, values: PackedStringArray)` |
| DEV operation (spec `## DEV`) | `static func` of the same name in `class_name <Module>Dev` (`extends RefCounted`) of `core/<module folder>/dev/<module folder>_dev.gd`. e.g. `InputCore.inject_device_input` → `InputCoreDev.inject_device_input()`. For `QACore` and `UnitTestCore` it is a `static func` of the module class |
| type that the spec names. e.g. `SystemPopupParam` | `class_name` of the same name, `extends RefCounted`. Fields are typed `var` |
| type of the base proto. e.g. `ItemAmount` | `CoreContract.<name>`, which the contract tool generates. e.g. `CoreContract.ItemAmount` |
| state value, result enum | `enum` in the module class. The type name is PascalCase, members are CONSTANT_CASE. e.g. `Connecting` → `RealtimeCore.MatchState.CONNECTING` |
| ID value | `int` |
| timestamp, duration | `int`(ms) |
| ratio | `int`(permille) |
| big integer | `String` |
| resource key, translation key | `String` |
| list | `Array[T]` or the Packed array of a value type |
| bytes | `PackedByteArray` |
| async operation | `static func` waited on with `await`. The caller receives it with `var ok: bool = await SceneCore.change_scene(key, param)` |
| callback | `Callable` argument. Omitted is `Callable()` |

Failure values are returned as the types below.

| spec failure value | GDScript |
|---|---|
| success flag | `bool` |
| result | `RefCounted` class whose name is the spec's result type name or `<Operation PascalCase>Result`. Its fields are the fields the spec writes. A result for which the spec writes a success flag as a field has that field as `ok: bool`. A result that splits success and failure with a status enum field (e.g. `LoginResult`, `CutsceneResult`) has no `ok`. `null` is not returned |
| fallback value | the type of that value |
| failure element of the result enum | that `enum` member |

- A module class has no public `static func`, public `static var`, or signal that is not in the spec. Names starting with `_` are not used outside the module class, that module's `<Module>Dev`, and that module's core tests
- An enum argument also accepts an `int` outside the members, so the module checks that it is a member and otherwise handles it as out-of-range input
- The `DataCore` derived container operations: `make_index(table: String, columns: PackedStringArray) -> DataIndex`, `make_group(table: String, columns: PackedStringArray) -> DataGroup`, `get_row(index: DataIndex, key: PackedInt64Array) -> RefCounted`, `has_row(index: DataIndex, key: PackedInt64Array) -> bool`, `get_rows(group: DataGroup, key: PackedInt64Array) -> Array[RefCounted]`, `has_rows(group: DataGroup, key: PackedInt64Array) -> bool`. `table` is the table name, `columns` are the key column names, `key` is the key values. The caller converts the result of `get_row` and the elements of the `get_rows` list with `as GameData.<Table>Row`

- Methods of `ContractMessage` (`extends RefCounted`). Message classes override them

The return type is `int` for `ReservedId`, `String` for `ReservedString` and `ReservedSound`, and for `GameSetting` the GDScript field type in the data type table above for the row's `data_type`. e.g. `ReservedId.tutorial_reward()`
- The load entry point is `GameData.load_tables(files: Dictionary[String, PackedByteArray]) -> bool`, and `GameData.clear() -> void` empties the containers and accessors. `DataCore` calls them in `load` and `release`
- The DEV accessors are `static func find_id_value(id_name: String) -> int`, `find_id_name(id_value: int) -> String`, `set_setting_<accessor name>(value: <type>) -> void` per `GameSetting` key, and `clear_settings() -> void`, which deletes all test values, in `class_name GameDataDev`. The `GameSetting` accessor of a key with a test value set returns the test value

- Client core type names are all `class_name`s that the `.gd` files of the client core folder declare. ## hook

- A hook for which the spec defines no registration operation has one `static func register_<hook>(hook: Callable) -> bool` per hook. `<hook>` is the snake_case of the spec hook name. e.g. `NetworkCore.register_error_display()`. A hook that the spec says is registered per target takes the target as the first argument. e.g. `UserStateCore.register_after_update(kind, hook)`
- A hook for which the spec defines a registration operation is registered with that operation. e.g. `RequirementCore.register_judge`, `BadgeCore.register_evaluator`, `ShortcutCore.register_param_builder`
- A hook is a reference to a static func. e.g. `NetworkCore.register_error_display(ContentBoot.error_display)`. An owner hook is a reference to a static func or to a `Node` instance method, and for an instance method that `Node` is the owner. e.g. `TutorialCore.register_can_start_tutorial(_can_start_tutorial)`. A lambda, a `Callable` with `bind()`, an instance method for a hook that is not an owner hook, and an instance method of an object that is not a `Node` give `false` and an error log
- The owner destruction judgement is `is_instance_id_valid(hook.get_object_id())`. The module judges it when it registers an owner hook and before it calls it, and deletes the registration when the owner is destroyed
- The return type of a hook whose output is one of `true` and `false` (success flag, pass flag; e.g. `can_start_tutorial`, `build_derived`, the judge hook of `RequirementCore`) is `bool`. e.g. `func _can_start_tutorial(tutorial_id: int) -> bool`. When the value a hook returns is not a `bool`, the module leaves an error log and handles it as the module spec defines for a malformed output of that hook, when it does (e.g. for the `RequirementCore` judge hook, the failure value of that `evaluate`), and otherwise as `false`
- The return type of any other hook with an output is a `RefCounted` class that the module defines. When a hook returns a value that is not that class, or `null`, it is handled as a malformed output
- A function stopped by a GDScript runtime error returns `false` when it is `-> bool`, and `null` otherwise (Godot 4.7.2). So for each hook call a core module calls `CoreScriptErrors.begin() -> int` before it and `CoreScriptErrors.end(mark: int) -> bool` after it, and when `end` is `true` handles that hook call as a hook throw of the spec (failure value and error log). At the first `begin`, `CoreScriptErrors` adds one Logger with `OS.add_logger` and keeps it until the process ends. The Logger counts only `ERROR_TYPE_SCRIPT` of the main thread. `end` returns whether errors were counted after `begin` and resets the count to `mark`, so the error of a hook called inside another hook belongs to the inner call. An error in the callback of an event that the hook's code published synchronously occurs while that hook runs, so it is that hook's throw. `begin` and `end` do not allocate memory. Event callbacks are not handled this way: when a callback stops, the other subscribers still receive the event and EventCore leaves no log
- The output class of a validation hook has the field `error_code: int`. 0 is `pass`
- The content entry of `BootstrapCore` is an object that extends `class_name ContentEntry` (`extends RefCounted`) of `core/bootstrap_core/content_entry.gd`. It overrides `func content_init() -> bool`, `func content_release() -> void`, `func select_first_scene() -> String`. The default `select_first_scene` returns the game settings `firstScene` value
- Hooks do not use `await`

## event

- The event base type is `class_name EventBase`, `extends RefCounted` of `core/event_core/event_base.gd`. An event type is `extends EventBase` and does not extend another event type
- An event type is given as a `Script` value. e.g. `EventCore.subscribe(SceneStartedEvent, _on_scene_started)`
- Publishing is getting the event with `var event := EventCore.acquire(SceneStartedEvent) as SceneStartedEvent`, filling its fields, then `EventCore.publish(event)`. For a depth that has no object, `acquire` creates one with `new()` of that `Script`
- A callback is a reference to an instance method that takes the event type as its one argument. e.g. `func _on_scene_started(event: SceneStartedEvent) -> void`
- A module's subscription callbacks are instance methods of that module's core node. The module's `release` calls `EventCore.unsubscribe_all` (core node) before it detaches the core node
- The subscriber judgement is `Callable.get_object_id()`, and the destruction judgement is `is_instance_id_valid()`
- When a GDScript runtime error occurs in a callback, only that callback stops and `Callable.call()` returns, so EventCore continues delivery to the remaining subscriptions. A callback returns no result, so EventCore cannot know of a failure and leaves no `error` log for a callback failure. The failure remains as a `SCRIPT ERROR:` line in the engine output
- A core event is in `core/<module folder>/events/<snake_case of the event type name>.gd`. A content event is in the feature folder that defines it or in `client/common/`
- Core has no public signals. Notifications to content are published through EventCore. Engine signals are connected only inside core nodes
- Signals are connected and disconnected with `Signal.connect()`, `Signal.disconnect()`. For a connection that returns `Error`, the result is checked

## lifecycle

| spec | GDScript |
|---|---|
| `init` | `static func init() -> bool` |
| `release` | `static func release() -> void` |
| init check | `static func is_initialized() -> bool`. Returns `static var _is_initialized` without a log |

- `release` resets every `static var`, except the state that the spec says is kept after `release`, to the initial value of its declaration, and replaces state objects with new objects
- `release` disconnects the core node's engine signal connections, detaches it with `root.remove_child()`, then calls `queue_free()`
- When app exit or tree teardown calls the core node's `_exit_tree()` outside `release`, it does the same cleanup as `release` but does not call `remove_child()`
- App exit is handled by the core node of `BootstrapCore`, which receives `NOTIFICATION_WM_CLOSE_REQUEST`
- Cancelling async operations: each `init` creates a new session object (`RefCounted`). An operation keeps the session in a local variable when it starts and, each time it returns from an `await`, checks that it equals the module's session. When it differs, the operation returns the failure value and does not call the callback
- `release` emits the signals that async operations `await`, so that they resume
- Work deferred with `call_deferred()`, `Timer`, `SceneTreeTimer` carries the session of the time of deferral, and when it runs it does nothing if the session has changed

## GDScript

Core code and content code both follow it. The harness tool writes the warnings below in `project.godot` as errors (`2`): `untyped_declaration`, `inference_on_variant`, `unsafe_property_access`, `unsafe_method_access`, `unsafe_cast`, `unsafe_call_argument`.

- type check (`ogw code check` and the static check `type check`): after `godot --headless --path <project> --import`, one Godot process loads the script of each `.gd` file (the same load and validity check as `--check-only`) and ends without errors. A script that depends on a script that failed earlier does not report the error of that dependency again. When that process does not end without errors, each file is checked again with `godot --headless --path <project> --check-only --script <file>` to find which file causes it. Not ending without errors means an error line that belongs to no script's load (before the first script, between two scripts, after the last script), a non-zero exit code, or exceeding the time limit. The warnings above are errors, so a type rule violation is also a failure
- Test code and DEV code read the members of a fake adapter through a `preload()` constant of that file, not through `class_name`. In Godot 4.7.2, when a file that uses the base adapter type by name reads members of a derived adapter class by global name, the `ContractMessage`, `ContractRequest`, generated `CoreContract`, `GameData` scripts remain until exit and the type check fails with `resources still in use at exit` (upstream godotengine/godot#122022, closed as not planned). Check again when the engine version is raised
- lint (`ogw code check` and the static check `lint`): only the naming rules below are checked, with `gdlint` of harness settings `tools.gdtoolkit`. The other gdlint rules are turned off

- Every variable, argument, and return value has its type written. `:=` is used only when the type is determined
- The `Variant` annotation and untyped `Array`, `Dictionary` are not used. `Array[T]`, `Dictionary[K, V]` are used
  - Exception: an input boundary function, a function that moves a `Variant` received from a file, the network, a platform SDK, or an engine API into typed values. The line right above its `func` line holds only `# ogw:input_boundary`. The `Variant` annotation and untyped `Array`, `Dictionary` are used only in the arguments and body of that function (including local variables, `is`, `as`, constructors) and not in its return type. Only in core code
- A list of a value type is a Packed array: `PackedByteArray`, `PackedInt32Array`, `PackedInt64Array`, `PackedFloat32Array`, `PackedFloat64Array`, `PackedStringArray`, `PackedVector2Array`, `PackedVector3Array`, `PackedColorArray`
- APIs that call by a name string are not used

  | forbidden | instead |
  |---|---|
  | `call()`, `callv()`, `call_deferred()` (Object) | direct method call, `Callable.call_deferred()` |
  | `get()`, `set()`, `set_deferred()`, `get_indexed()`, `set_indexed()` | direct typed property access |
  | `emit_signal()`, `connect()`, `disconnect()`, `is_connected()` (Object) | the method of the same name of `Signal` |
  | `has_method()`, `has_signal()` | `is` type check |

  - Exception: method calls on a native plugin singleton obtained with `Engine.get_singleton()`. That line gets `@warning_ignore("unsafe_method_access")`. Only in core adapters

## frame code

frame code: `_process()`, `_physics_process()`, `_input()`, `_unhandled_input()`, `_gui_input()`, `_integrate_forces()`, the methods connected to `SceneTree.process_frame`, `SceneTree.physics_frame`, and the core functions these call.

Frame code of core does none of the following.

- Creating an `Array`, `Dictionary`, or Packed array: literal, constructor, `duplicate()`, functions that return a new array (`keys()`, `values()`, `get_children()`, `split()`)
- Changing a collection size: `append()`, `push_back()`, `insert()`, `remove_at()`, `erase()`, `clear()`, `resize()`, adding a `Dictionary` key
- Creating a `Callable`: lambda, method reference, `bind()`
- Creating a `String`: `+`, `%`, `str()`, `String.num()`, `format()`
- Finding a node: `get_node()`, `$`, `%`, `find_child()`
- `await`
- Calling an async operation (`## API`). Frame code starts an async operation with `call_deferred()` of a `Callable` created in `init` or `_ready()`

- As an exception, on a path that runs only when a `LogCore.log_warn` or `LogCore.log_error` call is written, frame code creates the message `String` of that call and adds the one `Dictionary` key that records that this log was written, so that the log is written once per cause
- A reused collection is sized once to its maximum size with `resize()` outside frame code, and the count in use is kept in an `int` field. Emptying it sets only the count to 0
- An operation that returns a result list fills the buffer the caller gave from index 0 and returns the number filled. It does not change the buffer size. On overflow it fills only up to the buffer size and leaves an error log. The buffer of a list of enum values is `PackedInt32Array`. e.g. `AuthCore.list_linked_providers` (`LoginProvider` values)
- A `Callable` is created in `init` or `_ready()` and kept in a field

| `bgm` | `.ogg` | `AudioStream` | Ogg Vorbis |

The placeholder resources that `ogw resource placeholder` makes are below.

- `rig`: a `.glb` that holds a `Skeleton3D` with one bone
- `material`: a `StandardMaterial3D` with default values
- `sprite_animation`: a `SpriteFrames` with, per `animations` of `spec`, an animation of one frame. The frame is a single-color image of `spec` `size` held inside the `.tres`, and the length and looping of an animation are `animations` of `spec`
- `rig_animation_2d`: under root node `Node2D`, a `Skeleton2D` with one `Bone2D` at the root node origin, a single-color rectangle `Polygon2D` of `spec` `size` whose center is that origin as a child of that `Bone2D`, and an `AnimationPlayer` with, per `animations` of `spec`, an animation without tracks whose length and looping are those values

## engine meta file

- `.uid`, `.import` files are committed. `.godot/` is not committed
- At each commit, `ogw meta sync <game|core> --staged` of the pre-commit hook syncs the meta files: it runs `godot --headless --path <project> --import` only when the staged files include an engine resource, deletes `.uid`, `.import` whose source file does not exist, for a meta file whose source has a staged change stages that change when the source is in the index and removes the meta file from the index when the source is not in the index, and reverts the changes of meta files whose source has no staged change. Agents do not sync meta files by hand
- An engine resource is a file with a staged change (addition, modification, rename, deletion) that is visible to the Godot project: a file that is under `client/` or `resource/` for a game, or under `open-game-works-core-impl/client/godot/` for core, that is not under `.godot/`, `addons/`, `android/`, `ios/plugins/`, `plugins/`, whose extension is not `.uid`, `.import`, and, for core, that is not `open-game-works-core-impl/client/godot/engine.json`. Godot does not read `engine.json`, and a commit that changes the Godot version must pass the hook even when that version is not on this host
- The harness tool writes `editor/import/use_multiple_threads=false` in `project.godot`
- When `resource/resources.csv` exists, `ogw generate` writes `resource/resources.csv.import` as a file with only one line `importer="skip"` in the `[remap]` section. It is the file that Skip of the Godot import dock saves, and Godot does not import its source or put it in an export. Only the harness tool reads the resource list file. `ogw meta sync` does not sync this file

## DEV code

- A module's DEV code is in `core/<module folder>/dev/`. `QACore` and `UnitTestCore` have the whole module in `core/<module folder>/dev/`
- Module state that DEV operations change (e.g. forced failure, test clock) is kept in a `static var` starting with `_` of the module class, and `<Module>Dev` reads and writes it. A `Callable` that can still remain in a `static var` when the scene tree is deleted (e.g. state set while the module is not initialized, state of a module without a core node) is not a lambda unless it is defined in the same script. The received object is kept and read with a static function of the DEV class. Reason: when the engine frees that `static var` at shutdown and that lambda is the last reference to its own script, destroying the lambda deletes the script first and locks the mutex of the deleted script, and Godot 4.7 terminates abnormally
- The test clock is `class_name DevTestClock` (`extends RefCounted`, `var monotonic_ms: int`, `var device_time_ms: int`) of `core/log_core/dev/dev_test_clock.gd`. `LogCoreDev`, `TimeCoreDev`, `UnitTestCore` share it
- Core code outside DEV code and core tests does not reference a `class_name` or path under `dev/`. The one exception is the DEV entry path constant `res://core/bootstrap_core/dev/bootstrap_core_dev.gd` that `BootstrapCore` and `CoreBuildInfo` use
- At the start of `InitModules`, `BootstrapCore` looks for the DEV entry with `ResourceLoader.exists()` and, when it exists, loads it with `load()` and uses it. An STG·PROD build has no such file, so it has no DEV behavior
- The `load()` calls with a path constant are two: the `load()` with which `BootstrapCore` loads the DEV entry and the `load()` with which the DEV entry loads the DEV registration list. These two are all the `load()` calls outside `ResourceCore`, and they are the exception to the resource loading rules. A path constant is a `const` declaration, and the argument of the two `load()` calls is that constant's name (including `<class>.<constant>`). A string literal is not passed to `load()` directly
- The DEV entry is `BootstrapCoreDev` of that file and handles all of `## DEV` of `BootstrapCore`. When `shutdown` is received before a `start_boot` call, the DEV entry is looked for at that time
- The type of the `BootTestReplacements` argument of `start_boot` is `RefCounted`, and its default is `null`. The value is `class_name BootTestReplacements` (`extends RefCounted`) of `core/bootstrap_core/dev/boot_test_replacements.gd`, and `BootstrapCore` only passes that value to the DEV entry
- The DEV registration list is `res://dev/generated/dev_registration.gd`, which the harness tool generates. This file, without `class_name`, extends `class_name DevRegistrationList` (`extends RefCounted`, an empty `func register_all() -> void`) of `core/bootstrap_core/dev/dev_registration_list.gd` and overrides `register_all()`. After `build_derived_containers` of `ContentInit`, the DEV entry casts `new()` of the `GDScript` loaded with `load()` from the path constant `res://dev/generated/dev_registration.gd` to `DevRegistrationList` and calls `register_all()`.

## test

- A native run collects every `test_*.gd` under `res://core` as a test file, so only GUT test files have names starting with `test_`. Test support files and DEV code do not start with `test_`
- The test framework is GUT. Before the tests, `ogw core test` puts `gut` of `engine.json` and the `plugins` whose `platforms` has this host OS into the core project. Neither is committed
- A core test is `core/<module folder>/tests/test_<topic>.gd` and is `extends UnitTestCase`. A render test is `tests/test_render_<topic>.gd`. Test support classes are in `tests/support/`, and test resources in `tests/resources/`
- A core test that initializes `ResourceCore` with `init` first calls `ResourceCoreDev.set_test_key_list(keys: Dictionary[String, String], variants: Dictionary[String, int] = {})`. `keys` has resource keys as keys and the paths of test resources under `res://core/<module folder>/tests/resources/` as values. Without test resources it is an empty `Dictionary`. `variants` is the variant count of keys with 2 or more variants, and the variant file paths of such a key follow the rule of the resource key list file. A key not in `variants` has 1 variant
- `UnitTestCase` is `class_name UnitTestCase`, `extends GutTest` of `core/unit_test_core/dev/unit_test_case.gd`. `before_each()` does the test setup of `UnitTestCore`, and `after_each()` judges unchecked error logs and `UnitTestCore.testTimeLimitMs`. A test that overrides `before_each()`, `after_each()` calls `super()` first. In the headless pass of core tests, `should_skip_script()` of `UnitTestCase` returns the skip reason `render test` for a test file whose file name starts with `test_render_`
- The GUT pre-run hook `core/unit_test_core/dev/gut_pre_run.gd` and post-run hook `core/unit_test_core/dev/gut_post_run.gd` extend `GutHookScript`. The pre-run hook reads the run ID (`ogw_run_id`), the test host URL (`ogw_test_host`), the shared fixture folder of regression tests (`ogw_shared_fixture_dir`), and the core fixture folder of core tests (`ogw_core_fixture_dir`) from the test run config, initializes `UnitTestCore` with `init`, starts an engine timer of `UnitTestCore.runTimeLimitMs`, and sets the `CanvasLayer` that holds the GUT runner GUI (`GutLayer` of `addons/gut/gui/GutRunner.tscn`, `layer` 128) to `visible = false`. The post-run hook sends the result made from the GUT results to the test host, calls `release` on `UnitTestCore`, sends `PUT /released`, and sets the exit code with `set_exit_code()`. When the timer ends first, it sends the result made from the results so far and a run failure to the test host and ends with exit code 1
- The boot duration of `unit-test-core` is 60 s: the process of a native run and the result wait of a browser run last up to `UnitTestCore.runTimeLimitMs` plus 60 s
- test run config: the JSON object that gives the hooks the values that the harness tool sets per run. The keys are `ogw_run_id`, `ogw_test_host`, and, only those present in that run, `ogw_core_fixture_dir`, `ogw_shared_fixture_dir`, and the values are strings. In a native run the tool writes that object to a file per run and gives the file with GUT's `-gconfig=<absolute path of that file>`, and the hook reads the file of the `-gconfig=` value of the engine command line. GUT does not read unknown keys of the config file and rejects unknown options on the command line. In a browser run the test host opens `/app/index.html` with a URL that carries the keys and values of that object as the URL query, and the hook reads the page URL query with `JavaScriptBridge`
- `ogw core test godot [<module>]` runs the headless pass of the native run in `open-game-works-core-impl/client/godot/`, and when the run targets include `test_render_*.gd`, it then runs the render pass. Only one render pass runs at a time on this host: its window uses focus and screen mode, so when two render windows are up together, the macOS screen mode switch and the focus wait fail. The run targets are given with `-gdir` (folder) and `-gtest` (file), and when `<module>` is given, the `-gdir` value is `res://core/<module folder>`. The run ID, test host URL, and core fixture folder (absolute path of `open-game-works-core-impl/fixtures/`) are given through the test run config. The two passes get different run IDs, and the tool writes a result file per pass. When either fails, the core test fails. The render pass opens a window without `--headless`, and fails on a host that cannot open a window. On macOS, when the screen is locked or the main display is off, the render pass is not run: its window does not finish the screen mode switch. The result of that module is then `skipped` when the headless pass did not fail, and the reason is `render pass not run: the macOS screen is locked or the display sleeps`

  ```
  godot --headless --path <project> -s addons/gut/gut_cmdln.gd -gdir=res://core -ginclude_subdirs -gprefix=test_ -gsuffix=.gd -gpre_run_script=res://core/unit_test_core/dev/gut_pre_run.gd -gpost_run_script=res://core/unit_test_core/dev/gut_post_run.gd -gexit -gconfig=<test run config file>
  ```

- browser run: `ogw core test godot --web [<module>]` makes the core project into a DEV export of the Web preset (`variant/thread_support=true`, `progressive_web_app/enabled=true`, `progressive_web_app/ensure_cross_origin_isolation_headers=true`, `html/custom_html_shell` set to `res://core/web/ogw-shell.html`, `script_export_mode=0`: GUT finds test scripts and hook scripts by `.gd` path), replaces the exported `index.service.worker.js` with `core/web/service-worker.js`, and the test host of `UnitTestCore` serves that export under `/app/` with the same Content-Type as the web artifact deployment ([`ogw` `## deploy`](../../../tools/ogw.md); browsers check the MIME type of module scripts and audio worklets), and the test host does not send COOP·COEP: as in the web artifact deployment, the service worker adds the cross-origin isolation headers, and the web shell reopens the page once after the service worker becomes active. That page also has the same URL. The tool starts the headless browser of harness settings `tools.chromium` with `--autoplay-policy=no-user-gesture-required` (the audio context runs even without a user gesture) and a DevTools port on `127.0.0.1`, and opens `/app/index.html` of the test host. The tool attaches to that page target with DevTools and puts the test host's `POST /input` into that page. When it attaches, it grants `clipboardSanitizedWrite` to the test host origin with `Browser.grantPermissions`: a headless browser cannot ask for the clipboard write permission and leaves it at `prompt`. A browser that a human uses writes without asking when there is user activation. The official Web export template is built without path override and does not accept `-s` and a scene path on the command line, so the main scene of the core project copy being exported is `res://ogw_web_runner.tscn`, which the tool puts in, and this scene starts the GUT command line runner (`addons/gut/cli/gut_cli.gd`) that `addons/gut/gut_cmdln.gd` starts. The arguments of the headless pass command line above without `--headless`, `--path <project>`, `-s addons/gut/gut_cmdln.gd`, `-gconfig` are written in `GODOT_CONFIG.args`, which the exported `index.html` passes to the engine. The `ogw_core_fixture_dir` value of the test run config is `res://core_fixtures`. Before the export, the tool copies the files of `open-game-works-core-impl/fixtures/` to `core_fixtures/` of the core project and puts `core_fixtures/*.json`, `generated/*` (generated files that the core project reads; e.g. the core settings file), `build/data/*` (core test data build result), `addons/gut/*.txt` (templates that GUT reads when it makes doubles) in the non-resource export filter of the Web preset. In `addons/` of the exported copy only GUT is kept, and `.godot/extension_list.cfg` is deleted (`plugins` has no plugin that targets the browser runtime). `core_fixtures/` is not committed. For a browser run, the tool applies the result rules of `UnitTestCore` instead of the exit code, and treats the browser console output as the engine output. So that it also sees the `release` output after the post-run hook sends the result, after receiving the result the tool waits to receive `PUT /released` and keeps reading until the line `UnitTestCore released run <that run ID>` appears in the console output (at most 5 s), then judges. It waits for both because the request and the console come through two channels with no order between them. When 5 s pass before that line appears, it judges with the output read so far
- GUT's error tracker fails a test on the engine errors received in the test that are not marked as handled. `check_script_errors` also marks the script runtime errors it received as handled in GUT
- The test failure messages that `UnitTestCore` writes and the messages that test code writes do not contain `ERROR:` or `leaked at exit`. The harness tool counts these strings as engine errors wherever they are in a line
- A core test or client regression test fails when the result file has a `fail` test or a run failure, when the exit code is not 0, when the number of `SCRIPT ERROR:` lines in the engine output differs from the sum of `checked_script_errors` of the result, or when there is an `ERROR:` or `leaked at exit` line. The lines that the engine appends after a `SCRIPT ERROR:` line (`at:`, GDScript backtrace) belong to that line. A failure of a run whose result file did not arrive gets the last 20 lines of the engine output attached, and for a browser run also the last 20 lines of the browser output
- Godot round trip of `ogw core test tools`: the tool copies `open-game-works-core-impl/tools/tests/game/` to a temporary folder, and copies `open-game-works-core-impl/client/godot/`, with the pre-test preparation (putting in GUT and plugins, `--import`) done, to `client/` of that copy. It runs the contract tool and the data tool on that copy with `--engine godot` to write the Godot generated code to `client/generated/` and `client/dev/generated/`, and copies the test files of `open-game-works-core-impl/tools/tests/godot/` to `client/tool_tests/`. In that `client/` it runs the headless pass command line with the `-gdir` value changed to `res://tool_tests` and the `-gprefix` value changed to `test_contract_` when the module is `contract-tool` and to `test_data_` when it is `data-tool`, and the judgement is the same as for core tests. So round trip test file names are `test_contract_<topic>.gd` or `test_data_<topic>.gd`
- Test of an operation that the spec says does not allocate memory: the test code that calls that operation is run 100 times as warm-up, then `Performance.get_monitor(Performance.OBJECT_COUNT)` and `Performance.get_monitor(Performance.MEMORY_STATIC)` are read, the same code is run 1000 more times, and they are read again. It passes when neither value is larger than its value at the first read. The two monitors are the number of live objects and the memory in use, so this test catches only allocations that the operation leaves behind, and not allocations made and freed inside the operation. Such allocations are judged by whether the operation's code follows the `## frame code` rules. The measured section runs after `LogCore.release` so that logs do not pile up in LogCore. The test code of the measured section follows the frame code rules
- A test of a record slot count upper limit that the spec sets measures it with `size()` of the `static var` collection starting with `_` of the module class that holds that record
- Passing an object that is not a `Node` to `ResourceCore.get_owner_scope` gives a released scope and an `error` log, and `get_children()` of a `Node` that got an owner scope has no watcher
- Each module with a lifecycle has a lifecycle test: `is_initialized()` before and after `init` and after `release`; after `release`, every `static var` except the state that the spec says is kept is at its initial value and the core node is not in the tree; no `ERROR:` and no `leaked at exit` even when destroyed through `_exit_tree()`
- Before core tests, the static check of the harness tool checks the `.gd` files of `core/` (including DEV code and core tests) against the rules below. When any one is violated, the core test fails
  - `## GDScript`: the `Variant` annotation and untyped `Array`, `Dictionary` outside the arguments and body of an input boundary function, `# ogw:input_boundary` not on the line right above a `func` line, the APIs of the forbidden table, `assert`, `OS.is_debug_build()`, `OS.has_feature()`, `create_tween()` and `Tween.tween_property()` outside `TweenCore`, `uid://` strings, `@warning_ignore("unsafe_method_access")` outside `adapters/` and `dev/adapters/`
  - `## frame code`: node finding (`get_node()`, `$`, `%`, `find_child()`) and `await` in frame code
  - `## resource loading`: engine resource load functions outside `ResourceCore` (except `preload()` constants of a `.gd` in the same module folder and the two path constant `load()` calls of `## DEV code`), `PackedScene.instantiate()` in a module outside the list, files outside core tests that are not `.gd`, `.uid`
  - `## DEV code`: `class_name`s under `dev/` (including generated DEV classes) and `dev/` path strings in code outside DEV code and core tests. The DEV entry path constant of `BootstrapCore` and `CoreBuildInfo` is the exception
  - `## API`: references to members starting with `_` of a class in another module folder (`<Class>._<name>`)
  - calls of the engine random functions of the `UtilCore` row of `## engine behavior`
  - the `LogCore` row of `## engine behavior`: a `log_debug` reference that is not the one-line statement `LogCore.log_debug(...)`
  - data changes outside `DataCore` and generated code: the assignments and method calls that the static check `data mutation` blocks, and calls of `GameData.load_tables()`, `GameData.clear()`
