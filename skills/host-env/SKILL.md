# host env

`update env` is a command outside the loop. Harness settings are edited only with the revisions that a human accepted.

## procedure

1. Check the host with `ogw env check`
   - When a program among `buildTools` whose `hosts` has this host and that has no `downloads` is not on this host or has a different version, tell the human the program and version to install
2. With `ogw env install-engines --background`, get the engines and the programs among `buildTools` of `engine.json` whose `hosts` has this host and that have `downloads`. Start it together with step 3
3. With `ogw generation install --background`, get harness settings `tools` and the `pins` of `resourceGeneration`. A method that it could not fetch is left as failed. An `external-service` method without `provider` has nothing to get; check that its `secret` is in the host secret store, and when it is not, tell the human to put in a non-empty value with `ogw secret set --harness <secret name>`. To fetch only one method again, use `ogw generation install <method> --background`
4. When the job of step 3 ends, run the standard test task of each method stage by stage with `ogw generation measure [--allow <method,...>] --background`. `--allow` is the `external-service` methods whose calls the human allowed. To measure only a few methods again, use `ogw generation measure <method>... [--allow <method,...>] --background`
   - For an `external-service` method, first tell the human the cost of one test call, and pass only the allowed methods with `--allow`
   - For a method with `provider`, tell the human the billing of its calls from step 1 before asking: `subscription` uses the usage of that subscription, `per-call` bills each call to that key, and for `unknown` the human has to check the login. Call only the allowed methods
5. When the jobs of steps 2 and 4 end, measure the number of instances that can be started concurrently with `ogw instance measure --background`
   - Before it starts, tell the human the accesses that the sandbox blocked in step 4 and the files that differ from the pinned information in step 3
   - Before it starts, show the human the current harness settings `instanceMeasureLimit` of this host (`ogw settings get harness instanceMeasureLimit`) and its meaning, and ask whether to change it, and write an accepted value with `ogw settings set harness instanceMeasureLimit <value>`. A host with more CPU cores and memory can be given a larger value; the measurement may start that many instances that render the screen together, so a value well above what the host can run makes the measurement long and the host slow while it runs
6. With `ogw env propose`, get the revisions and notices that compare the results of steps 1 to 5 with harness settings. The tool gives, per revision, an id, the harness settings path, the current value, the new value and the reason, and the notices below. It gives no revision or notice for a step without a result.
   - notice `no-benchmark`: there is no target measured in step 5. `update env` has to run again after `create client core`
   - notice `no-loop`: the smallest of the target values measured in step 5 is less than 2. This host cannot run the loop
   - notice `no-method`: the list of resource types that the methods of harness settings `resourceGeneration` cannot make
   - notice `docker`: Docker or `docker buildx` is missing, or the GitHub CLI login has no `write:packages` scope. It has to be installed, or logged in with `gh auth refresh --scopes write:packages`
   - notice `udp`: the list of android devices that UDP does not reach. The check `device performance` of a realtime game becomes `unknown`, so the devices have to be on the same LAN as the host
   - notice `agent-cli`: the agent CLIs that did not finish in an empty folder, the settings that use each (the roles of harness settings `agents`, the items of `loop.judgePanel`, `loop.confirmJudge`, `loop.confirmFallback`), and their error output
   - notice `agent-login-token`: the agent CLI of play, of judge, of an item of `loop.judgePanel`, of `loop.confirmJudge` or of `loop.confirmFallback` is Claude Code, and the harness secret `claude-code-oauth-token` is not in the host secret store (`missing`), or the value cannot be an HTTP `Authorization: Bearer` header value or Claude Code failed authentication in the check of step 1 (`invalid`), or the check failed for another reason (`unverified`; the error is given with it). For `missing` and `invalid`, a human has to make a long-lived token with `claude setup-token` and put it in as one line with `ogw secret set --harness claude-code-oauth-token`. For `unverified`, a human has to check that error. Without this secret, `ogw loop start` and `ogw build start` do not start
   - notice `pin-secret`: the hf pin `secret` values that are not in the host secret store, and the repository of each pin. A human has to accept the license on the page of that repository on Hugging Face and put in the access token of that account with `ogw secret set --harness <secret name>`. When `update env` runs again after that, step 3 fetches that method, and step 6 gives the `sha256:<method>` revision
   - notice `provider-cli`: the provider CLIs that are not installed or not logged in, or whose billing in step 1 is `per-call`, or `unknown` while logged in, and the methods that use them. For a CLI that is not installed or not logged in, a human has to install it and log in. For `per-call`, it names the login that makes the calls use the subscription instead (`codex login` with ChatGPT, `grok login`). For `unknown`, a human has to check how that login bills the calls
7. Decide the revisions that the tool does not give
   - a failed method: a revision that removes it, or a revision that fixes `pins`
   - when `tools.chromium` is missing or could not be fetched: a revision that adds the pinned information of Chrome for Testing `chrome-headless-shell` for the OS of this host
   - a method outside `catalog` whose `license` is missing or `unknown`: a revision that fills `license` by `## resource rights` of [`resource`](../resource/SKILL.md) and the license references that `ogw settings describe harness resourceGeneration.0.license` prints. For a method with pins and without `provider`, it holds the model card license of its pins. For a method with `provider`, it is the license reference of the output terms of that provider, not the license of the code that its pins fetch
   - each setting that notice `agent-cli` names: a revision that changes that setting to another model or effort of the same CLI when the error output says that CLI rejects the model or effort, and otherwise to another CLI
8. Ask the human which method makes the images of the games that have no image yet (harness settings `imageMethod`). The choices are `flux2-klein` and the methods with `provider` whose `resourceTypes` has `image`, among those that have an `ok` stage in the results of step 4. Give a recommendation and these points:
   - a method with `provider` draws better images and in the same style as the sprite animations that the same provider makes, and uses the usage of that subscription. When the usage limit is reached, `flux2-klein` makes a temporary image when it has an `ok` stage, and the next `update game` makes it again; without `flux2-klein`, the work waits until it can call again
   - `flux2-klein` is free, has no usage limit and runs offline, and draws lower quality images
   - the method of a game is fixed by its first image, so a change applies only to games without images
   Write the answer with `ogw settings set harness imageMethod <method name>`
9. preference settings: show the human, per path below, the current value (`ogw settings get harness <path>`) and its meaning (the description of `ogw settings describe harness <path>`), ask which to change, and write the accepted values with `ogw settings set harness <path> <JSON value>`
   - `humanLanguage`
   - `agents.<role>` of each role: model and effort. A larger model and a higher effort give higher quality, and take longer and use more of the subscription usage
   - `loopStop.repeatedDefect`, `loopStop.oscillation`, `loopStop.plateau`, `loopStop.successJudges`
   - `loop.funIterations`, `loop.judgeVotes`, `loop.judgePanel`, `loop.confirmJudge`, `loop.confirmFallback`, `loop.variants`, `loop.playTimeLimitMs`, `loop.playBudgetMs`, `loop.judgeInstanceBudgetMs`, `loop.judgeTimeLimitMs`. The items of `loop.judgePanel` can mix Claude Code models and efforts. An item, `loop.confirmJudge` or `loop.confirmFallback` with `cli` `codex` only when step 1 found the `codex` CLI logged in. `loop.confirmJudge` judges only the `better` of a fun iteration and the success confirmation, so a model of another family than `agents.content` there checks those decisions with less of its usage than as an item of `loop.judgePanel`. `loop.judgeVotes` at least twice the number of `loop.judgePanel` items, so that every item judges
10. Show the human the measurement results, the revisions and notices of step 6, and the revisions of step 7. Apply the revisions of step 6 that the human accepted with `ogw env propose --apply <id,...>` and those of step 7 with `ogw settings set harness`, then commit `settings.json` when it changed. `--apply` writes, per revision, only the parts where the current value and the new value differ, so revisions with the same path are also applied together. When revisions whose differing parts overlap are given together, it writes nothing and fails. In that case apply them one at a time, and run `ogw env propose` again after each one
11. After the human has seen them, delete the folders that `ogw generation measure` printed as `output` per stage. Keep the file it printed as `result`, which later measure runs and `ogw env propose` read
