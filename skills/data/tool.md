# data tool

Read when the core agent makes or fixes the data tool. The rules of what the data tool checks and makes are in [SKILL.md](SKILL.md).

## ID registry

- The data tool does not switch the current branch, and reads and writes the file of the `id-registry` branch directly with git
- When the data tool meets a new ID name, it takes the file lock `ogw-id-registry.lock` in the git common dir (`git rev-parse --git-common-dir`) of that game repo. So all worktrees of the same game repo share one lock. The lock is one file: a temporary file whose content (one line owner pid, one line token) is fully written is put in place under the name `ogw-id-registry.lock` with one hard link. When the lock already exists, the link fails, and because a placed lock holds the pid from the start, a run that ended while placing it does not leave a lock without a pid. When the owner process has ended, another run takes over that lock: the run that will take over places `ogw-id-registry.lock.takeover` in the same way so that only one run takes over, checks again that the content of the lock is unchanged, then deletes the lock, places its own lock, and deletes the claim. When the owner of the claim has ended, the claim is also taken over by the same rule. A lock whose content cannot be read is not taken over. A run that ended after writing the temporary file and before the link leaves `ogw-id-registry.lock.<pid>-<token>`, and a run that was placing a claim leaves `ogw-id-registry.lock.takeover.<pid>-<token>` (including names with more `.takeover` added). Such a file does not block the lock, and the run that took the lock deletes such files whose owner pid has ended. The owner pid is the pid in the file content when it equals the pid in the name. A file whose content cannot be read, that is not owner content, or whose two pids differ is kept. The limit for waiting for the lock is 600000 ms, and the lock is checked again every 100 ms: the lock is held for one issuing (measured about 0.1 s), so a wait longer than that means a stopped holder, not a queue. Issuing is done up to 5 times inside the lock, reading the registry again when it changed
- After taking the lock, the data tool reads the file of the `id-registry` branch again, and issues the ID names that are not in it one by one in byte order of ID name. The ID value is the remainder of the first 8 bytes of SHA-256(UTF-8 ID name), read as an unsigned big-endian integer, divided by 2147483647, plus 1. When another ID name already uses that value, it adds 1 at a time to find an unused value, and goes back to 1 when it exceeds 2147483647. When there is no unused value at all, it issues nothing and fails. The reason it does not issue sequentially: so that a user cannot guess other IDs, and so that content code that does arithmetic on an ID value (`id + 1`) is wrong right away and gets caught. The mappings issued in one data tool run are made into one commit, and the `id-registry` branch is moved by passing the commit it read again to `git update-ref` as the expected value. When that fails because the branch moved in the meantime, it reads again and issues. Then it releases the lock
- Data outside a game repo uses one `id_registry.json` file as its ID registry. The harness tool passes that file path with `--id-registry`, and the data tool reads and writes that file instead of the `id-registry` branch. The file format, issue order, and ID values are the same as for `id_registry.json` of the `id-registry` branch
  - core test data: on every run, `ogw core test` makes an `id_registry.json` holding only `{}` in a newly made temporary folder and passes it, and deletes that folder when the run ends. It is not committed. So the same core test data gets the same ID values on every run. As an exception to binary build, the binary build of core test data issues ID values into this file and writes all generation targets
  - benchmark game inside `open-game-works-core-impl/`: the committed `open-game-works-core-impl/benchmark/<engine>/id_registry.json`. Issuing is done after taking the file lock `ogw-id-registry.lock` in the git common dir of `open-game-works-core-impl/` and reading the file again. Issued mappings are not changed or deleted
  - benchmark game unpacked from a release: `id_registry.json` at the root of the unpacked folder. Only binary builds are done, so nothing is issued
  - The data tool writes the new `id_registry.json` to `id_registry.json.<pid>-<token>` next to it and renames it to that file. A run that ended after writing and before the rename leaves that file. A run that takes the lock and issues into that `id_registry.json` deletes such files whose pid in the name has ended and whose content reads as an ID registry. A file whose content cannot be read or does not read as an ID registry is kept
- When the ID registry it read is not a JSON object, a key is not in ID name format, a value is not an `int32` integer of 1 or more, or two ID names have the same ID value, the data tool outputs `structure` for that `id_registry.json` and issues nothing

## core data

- The data tool reads core data, the required conditions and target tables of reserved IDs, and the format arguments of texts to which core gives values from `core-spec.json` of the release of that core version. `core-spec.json` is a file that carries `## dependency` and `## data` of the core specs, and its format is `## core spec file` of `command.md` of the `core` skill

## processing

For core test data, `ogw core test` calls the data tool of `open-game-works-core-impl/`. `ogw core test server` calls it without `--engine`, and `ogw core test <engine>` calls it with that engine. It is first called without `--binary` to align the core test data by putting in core data, making `banned_word` rows, and aligning translations, and is then called as a binary build. This is because core test data that parallel core agents merged may not be aligned.

processing order: put in core data → make `banned_word` rows → align translations → check (stops on error) → issue ID values → replace ID names and enum elements with values → split columns and rows per build target → generate data proto and code → generate binaries

- The generation target location of core test data is the path made by changing the location in the `## data tool` table of [SKILL.md](SKILL.md) to the actual path as the `--engine` description says, and then replacing the leading `client/` with `open-game-works-core-impl/client/<engine>/` and `server/` with `open-game-works-core-impl/server/`. `<engine>` is the `--engine` value
- file names: a table binary is `<table>.bin` (`<table>` is the table name), and a translation binary is `translation_<code>.bin`. `<code>` is `code` of the `language` table in lowercase. `data_version`, `client_data_version`, `compat_client_data_version` hold the data version in one line
- A table binary is the bytes of the data proto message `<Table>Table` of that build target encoded as protobuf binary. `<Table>Table` has only one field, field 1 `repeated <Table>Row rows`. The value of a `tstring` field is the built translation key
- A translation binary is one per build target and language, and is the bytes of the fixed message `Translation` that the data tool puts in the data proto, encoded as protobuf binary. `Translation` has field 1 `repeated TranslationEntry entries`, and `TranslationEntry` has field 1 `string key` and field 2 `string text`. `entries` has one entry per built translation key that the `tstring` columns in that build target made, in byte order of key. `text` is the translation of that language
- The load entry point receives the bytes per table binary file name (`<table>.bin`) and fills all containers and accessors. When even one table binary of that build target is missing from the input or cannot be decoded, it fills nothing and fails
- The generated code of the server build target also has a load entry point for the translation binary. Its format is `## generated code` of [`server-core`](../server-core/SKILL.md)
- Data proto and code generation and binary generation are done after adding the tables, enums, and reserved rows of `--core-spec` that are not in data, as `## data tool` of [SKILL.md](SKILL.md) says. The table binary of a table without rows is empty bytes
- The only tables whose rows are split per build target are `game_setting`, `reserved_id`, the `requirement` that the data tool makes, and `remote_config_key`. The build target of a row is set by `## data` of the `remote-config` spec of [`server-core`](../server-core/SKILL.md) for `remote_config_key`, and by [SKILL.md](SKILL.md) for the others
- `compat_client_data_version` is the value of `client/build/data/data_version` of the `--previous` folder. When there is no `--previous`, or its protocol hash equals the protocol hash of `client_data_version`, the file is not made

## data proto

- The data proto is one file `game_data.proto` per build target, in the data proto location of the `## data tool` table of [SKILL.md](SKILL.md). The first line is `syntax = "proto3";`, and the next line is `package ogw.data;`. When `ogw.core.ItemAmount` is used, `import "ogw/core.proto";` is on the line after that
- The declaration order is data enums, the vector messages `Vector2Int`, `Vector3Int`, `Vector4Int`, `Vector2`, `Vector3`, `Vector4`, `Translation`, `TranslationEntry`, `TableNames`, and the messages per table. Data enums are in byte order of `type`, and tables in byte order of table name. The messages of one table are in the order `<Table>Row`, the `<Table><Column>Item` or `<Table><Column>List` of each column in column order, `<Table>Table`
- A data enum is an `enum` whose name is `type`. A value name is `<TYPE>_<ELEMENT>`. `<TYPE>` is `type` and `<ELEMENT>` is `element`, written in UPPER_SNAKE. The first value is `<TYPE>_NONE = 0`, and the rest are in ascending order of `value`. e.g. `REQUIREMENT_TYPE_ITEM_COUNT`
- The fields of `<Table>Row` are the columns in that build target. A field name is the column name, and field numbers start at 1 in the header order of those columns. The column description (header row 1) is the comment above that field
- The fields of `<Table><Column>Item` are the fields of the bundle list. A field name is the name of that field, and field numbers start at 1 in the order written in the header
- `TableNames` is a fixed message with one field per table of that build target. A field is `bool <table name>`, and field numbers start at 1 in byte order of table name. Because the table name cannot be made back from `<Table>`, the contract tool reads table names from these field names

## CLI

The harness tool calls the data tool of every core version with this CLI.

`node bin/data-tool.js --game <dir> [--engine <engine>] --base-proto <dir> --game-settings <file> --core-spec <file> --modules <file> [--binary] [--strict] [--previous <dir>] [--id-registry <file>]`. `bin/data-tool.js` is a path relative to the folder where `data-tool.tgz` is unpacked.

| argument | contents |
|---|---|
| `--game <dir>` | the root of a game repo or its worktree, a benchmark game folder, or the core test data folder `open-game-works-core-impl/test-data/`. Reads `data/`, `resource/resources.csv`, `records/setup/banned-words/`, the game contract in `contract/`, and client core type names (set by `### generated code` of the per-engine implementation rules of [`client-core`](../client-core/SKILL.md)), aligns `data/`, and writes the generation targets to the locations of the `## data tool` table of [SKILL.md](SKILL.md), relative to this folder. When `--game` is `test-data/` under the parent folder of the `--base-proto` folder, it is the core test data folder, and the tool writes to the generation target locations of core test data. The core test data folder has no `resource/`, and its `records/` has only `records/setup/banned-words/`; the data tool reads it as having no resources. When `contract/` or the client core folder is missing, it is treated as empty. When there is no `--id-registry`, the ID registry is read and written with the git of this folder |
| `--engine <engine>` | the engine of the client generated code. Of the paths read and written, a path that starts with `client/` is a path under the logical folder of `## folder` of [`client-content`](../client-content/SKILL.md), and the data tool reads and writes it at the actual path that `## project` of the per-engine rules of this engine sets. For a game repo and a benchmark game, it is the game settings `engine` value. It is omitted only for the core test data folder. When omitted, the tool does not write the generation targets whose location starts with `client/` and does not read client core type names. `client_data_version` is written with the same value as when those generation targets are written |
| `--base-proto <dir>` | the base proto folder. Used for the import of `ItemAmount` and for the base proto name check of `reserved_name`. `proto/` of the folder where `data-tool.tgz` is unpacked, taken from the release of the game settings core version for a game repo and from the release that holds its `benchmark-<engine>.zip` for a benchmark game unpacked from a release; for a benchmark game inside `open-game-works-core-impl/` and for the core test data folder, `open-game-works-core-impl/proto/` |
| `--game-settings <file>` | the JSON of game settings with the `default` values of the game settings schema filled in. `sourceLanguage`, `supportedLanguages`, and the paths that the required conditions of reserved IDs point to are read from here. For core test data, it is the JSON of `open-game-works-core-impl/test-data/settings.json` with `default` filled in |
| `--core-spec <file>` | `core-spec.json` of the release of the core version of game settings |
| `--modules <file>` | a JSON array of the names of the modules the game uses (`## module` of the `core` skill). For core test data, all module names of `open-game-works-core-impl/core-spec/` |
| `--binary` | binary build |
| `--strict` | the data check of build. Outputs `resource_missing` as ERROR |
| `--previous <dir>` | a folder where the PROD data tag (`## data version` of [SKILL.md](SKILL.md)) is checked out and a binary build has been finished with the data tool of the core version of that tag. When given, the tool does the checks that compare with the data of the PROD data tag (`protocol_change`, `prod_change`) and writes `compat_client_data_version`. When a file that those checks read (table, `data/simulation_tables.csv`, `resource/resources.csv`) is not UTF-8 RFC 4180 or cannot be read because its header is short, it is a `structure` ERROR of that file. `<file>` is the path of that file inside the `--previous` folder. Other data problems output no line |
| `--id-registry <file>` | the `id_registry.json` file that data outside a game repo uses as its ID registry. When given, the tool reads and writes this file instead of the `id-registry` branch. The values for core test data, a benchmark game inside `open-game-works-core-impl/`, and a benchmark game unpacked from a release are set by `## ID registry` |

- A generation target folder is replaced as a whole: files that are not in this result are deleted, and only files whose bytes differ are written
- stdout: data check result lines
- exit code: `0` is that there is no ERROR line, `1` is that there is an ERROR line or the binary build failed, `2` is that an argument or input file is wrong, or that an input, an output path, the ID registry, or its lock cannot be read or written (including when the lock wait limit has passed). The reason is one line on stderr. When it is not `0`, no generation target is written. The generation target folders of that run are either all changed or all unchanged

## hash

- `current_hash` of a translation file: the first 16 characters of the SHA-256 lowercase hex of the UTF-8 made by putting, after the source text of the translation input, the matching glossary rows in byte order of `source`, joining for each row U+000A, `source`, U+0009, and that language cell
- `source_hash` of the glossary: the first 16 characters of the UTF-8 SHA-256 lowercase hex of `source` of that row
- hash input of a data version: the UTF-8 bytes made by concatenating, in ascending byte order of file name, one line per file that joins `<file name> <SHA-256 lowercase hex of the file>` and LF
- protocol hash: the SHA-256 of the hash input made from the generated data proto files of that build target (the `.proto` files under `client/generated/data/` or `server/generated/data/`. The file name is the path relative to that folder). The file SHA-256 in this hash input is calculated from the file content without proto comments
- data hash: the SHA-256 of the hash input made from the table binaries (`<table>.bin`) of that build target
