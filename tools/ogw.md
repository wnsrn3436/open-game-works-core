## update harness tool

- The requested behavior is first defined in the skill read by the agent that uses that behavior, or in this document; then `ogw` is fixed per that definition and tests are added
- An error that `ogw` catches is either the one error the definition expects there, checked by its code or class (e.g. a file that may be absent: `isNotFound`, `whenNotFound`), with every other error thrown again, or a failure that becomes the result the definition gives for it (`unknown` with the reason, a failure line with the error message). A failure the definition does not name is not turned into a value (absent, empty, 0, `pass`): the command fails with the error. Only a cleanup whose failure cannot change a result (e.g. removing a temporary folder after the result is written) drops its error, through `ignoreCleanupError`
- When there is no definition or the documents differ from each other, nothing is fixed and the human is asked
- The work ends only when the tests of `ogw`, `ogw docs check` and the review and code check below pass
- review and code check: a target is one `ogw` command. The targets are the fixed commands and the commands that call them. Each target is handled the same as `## review and code check` of [core command](../skills/core/command.md); the only differences are below
  - The lead agent runs 1 and 2 itself with `ogw review next` and `ogw review wait` instead of `ogw review run`
  - The first argument of `ogw review next` and `ogw review wait` is `tool`. The code check that `ogw review next` starts alongside is `ogw code check tool`
  - `ogw review next` gets the document that defines that command with `--definition`. Round 1 must get `--since <harness repo HEAD at the start of the command>`. From round 2 on, `--since` is not used
  - The commit that the review agent and the code check read is the HEAD of the harness repo, not main. The lead agent runs the whole test suite of `tools/` (`npx vitest run` in `tools/`), makes it pass, and commits the changes in `tools/` before each `ogw review next`. When `tools/` has uncommitted changes, `ogw review next` does not start a round
  - When the result is `fix` or `escalate`, the lead agent fixes, not the core agent. On `escalate`, it reads the chain of the escalation input that `ogw review wait` output the same way as the escalation of [core agent](../agents/core.md), and fixes. When the human decides how to fix at `limit`, the lead agent fixes and runs `ogw review next tool <target> --continue`. When the code of a target changes after it ended with `done`, it runs `ogw review next tool <target> --reopen`. Review files are not committed. When the command ends, it runs `ogw review clear tool`
  - The review lists (debt list, must-fix list) are `records/review-debt/<target>.json` and `records/review-must-fix/<target>.json` of the harness repo (a space in `<target>` becomes `-`); their format, adding, deleting and range are the same as `## review lists` of [core command](../skills/core/command.md). The tool adds every line of `## out of scope` of the review file to the list of the review target and commits the changed list to the current branch of the harness repo. There is no `--full`. Since round 1 has `--since`, the only review whose range includes the debt list is the `--debt` review
  - The lead agent fixes `out of scope` lines (severity `critical`, `high`) and `review must fix added:` lines with `(was D<n>)` right away. Those items go into `## must fix` of the next round's input, and whether they were fixed is checked. When the last round is `done`, it runs `--reopen` after fixing
  - When the command ends, the lead agent reports the item count of each debt list of the harness repo to the human and asks, with a recommendation, whether to run the debt review of those targets (`ogw review next tool <target> --debt`)
  - The target test files of `fix test proof` are the files under `tools/test/`; the changed `*.test.ts` among them run with `vitest run`. When `tools/package.json` or `tools/package-lock.json` of the fix base differs from the current working tree, `npm ci` in that worktree gets the dependencies of the fix base. When one or more test files fail or do not load, the result is `pass`. A file that loads but has no tests does not count as a failure. When no test ran (a skipped test did not run), the result is `unknown`

## help

- `ogw <command> --help` prints the usage of that command and ends with exit code 0
- command group: leading words of command names that are not the name of a command. e.g. `settings` of `ogw settings get`, `ogw settings set`. `ogw <command group> --help` prints the usages of the commands whose names start with those words and ends with exit code 0. `ogw <command group>` with no other argument prints them on stderr and ends with exit code 1

## agent

- `ogw agent` starts an agent with the per-role agent CLI, model and effort of harness settings, in a mode that does not ask for approval. For Claude Code this is `--permission-mode bypassPermissions`; for Codex, `--dangerously-bypass-approvals-and-sandbox` and `--skip-git-repo-check`. `--skip-git-repo-check` is given because the play agent and the judge agent start in a folder that is not a git repository. A judge agent that `ogw loop evaluate`, `ogw loop variants` or `ogw judge calibrate` calls starts with the agent CLI, model and effort that `## loop evaluate` gives that judge, which the job keeps.
- The agent CLI prints its usage as JSON on stdout: Claude Code gets `--output-format json` and prints one result object when it ends; Codex gets `--json` and prints one JSON event per line. Its stdout and stderr go to `<id>.cli.log`. The failure content of a job is the lines `failed: <reason>` and `output: <result file path or none>` and the last 100 lines of `<id>.cli.log`, in which each result object of Claude Code (`### usage`) whose `result` is a string is replaced with that text
- Claude Code of every role but play and judge gets the environment variable `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` with 3600000 (1 hour). In print mode Claude Code stops the background tasks (e.g. helper agents of the `Agent` tool) that still run this long after the last turn, 10 minutes by default. A stopped helper agent sends no completion notice, so with the default a content agent that waits for a helper agent still writing after 10 minutes waits for one that no longer runs. Play and judge keep the default, so that a background task left running ends before their time limit. Codex has no such wait to set: `codex exec` ends when the turn of the agent ends, and the helper agents of its multi-agent tools end with it, so [content](../agents/content.md) waits for every helper agent before it ends
- The prompt is the text of `agents/<role>.md` with the `../` of each link target starting with `../` replaced by the absolute path of the harness repo `open-game-works-core/` and `/`. For roles other than play, judge and seed, the `## purpose`, `## terms`, `## repo`, `## layer`, `## environment` and `## rules` sections of `AGENTS.md` are put before it, in this order. A section runs from its heading line up to before the next `##` heading line. When any of the six headings is missing from `AGENTS.md`, the agent is not started and the command fails
- At the end of the prompt go the `## ogw agent` heading line, a blank line, and the lines `- input: <absolute path of the input file passed to the agent>` and `- output: <absolute path of the result file>`; for an agent started in a run, the lines `- run: <run name>` and `- iteration: <current iteration number>` are added. Core, review, seed and a judge agent of `ogw judge calibrate` have no `run` and `iteration` lines. The folder of the result file is made before the agent CLI starts
- An agent of the roles `content`, `translation`, `server-hardening` and `client-hardening` runs in a sandbox that blocks only the other games and the seeds of the regression suite: reading and writing the folders under harness settings `paths.games` other than its game, the folders under `paths.worktrees` other than its game, `_core` and `_harness`, the regress repo (`paths.regress`), `regress/` of the harness repo and of each side worktree under `worktrees/_harness/` (`## regress`), and the admission folders `admit-*` under `regress/` of `<dataDir>` (`### admission` of `## regress`), whose check files of seeded commits are named by seed. The list is taken when the agent starts, so a game made later is not in it. With no such folder there is no sandbox. The processes the agent starts (`ogw` commands, instances) are in the same sandbox, and the rest of the host stays open to them: this sandbox does not block the ways out that the play and judge sandbox blocks. It runs with `sandbox-exec` on macOS and `bwrap` on Linux, and on other OSes these agents start without it. The `resource` role does not run in it: `ogw generation run` runs local models in a sandbox of their own, and macOS does not start a sandbox inside another
- The play agent and the judge agent start in a newly created empty folder. The agent CLI uses its default config folder as it is (for Claude Code `CLAUDE_CONFIG_DIR`, for Codex `CODEX_HOME`, when set; otherwise `~/.claude`, `~/.codex`) and starts with the human's login (Claude Code on macOS keeps it in the Keychain). Claude Code also gets `--no-session-persistence` and Codex `--ephemeral`, so that it leaves no session file. That CLI process and all its child processes run in the agent sandbox, which blocks the items below. The sandbox runs only on macOS (`sandbox-exec`) and Linux (`bwrap`); on other OSes the play agent and the judge agent cannot be started and the command fails. The roles of the item above run as it says, the seed agent as the item after this one says, and other roles start without a sandbox
  - Writes anywhere except these folders and files: the folder the agent started in, the OS temp folder (the folder the environment variable `TMPDIR` points to; when it is not set, the OS default temp folder) and `/tmp`, `/dev`, that agent's `<id>.cli.log` and broker folder, the login files of the two agent CLIs (for Claude Code `.credentials.json` in the default config folder and `~/Library/Keychains/` on macOS; for Codex `auth.json` in the default config folder), and on macOS `installation_id` in the default config folder of Codex, which Codex opens for writing when it starts and without which it does not start (on Linux the agent CLI writes that file in the empty folder that hides the config folder of Codex). Examples of blocked writes: `~/.gitconfig`, `~/.config/`, shell startup files, `~/.claude.json`, and in the default config folder of the two agent CLIs `settings.json`, `CLAUDE.md`, `AGENTS.md`, `config.toml`, `hooks/`, `skills/`, `agents/`, `plugins/`, `shell-snapshots/`, `session-env/`, and of Codex `tmp/` (its PATH aliases, whose folders other Codex processes put on the `PATH` of their shell commands), `shell_snapshots/`, `cache/` and `models_cache.json`; Codex starts without them. A path that another item blocks is blocked even inside these folders
  - Reads and writes of these paths: under harness settings `paths.games` and `paths.worktrees`, under the git common dir of the harness repo (it holds the instance record folder (`## runner`), the jobs folder, `ogw-secret-files/` and `ogw-temp/`), and the places in the default config folder of the two agent CLIs that hold other agents' session records (conversations, prompt history, logs, memory, file snapshots, plans, todos). `agent-logs/` of the jobs folder holds `<id>.cli.log`, `<id>.stdout` and `<id>.stderr` per `ogw agent` job. That agent's own `<id>.cli.log` and broker folder are not blocked. The places that hold session records are, for Claude Code, under `projects/`, `file-history/`, `todos/`, `plans/`, `debug/` and `history.jsonl`; for Codex, under `sessions/`, `archived_sessions/`, `log/` and `history.jsonl`, the `state_<n>.sqlite`, `logs_<n>.sqlite`, `memories_<n>.sqlite`, `thread_history_<n>.sqlite`, `goals_<n>.sqlite`, `queue_<n>.sqlite` that exist when the agent starts, and their `-wal` and `-shm` files. On Linux the whole default config folder of Codex is hidden behind an empty folder, and `auth.json` is shown again read-write and `config.toml` read-only
  - Reads and writes of entries directly under the OS temp folder and `/tmp` whose names start with `ogw-play-`, `ogw-judge-` or `ogw-seed-`, other than the folder that agent started in. On Linux the OS temp folder and `/tmp` are hidden behind empty folders and only the folder that agent started in is shown again, so what the sandbox writes elsewhere in those two folders is not visible outside the sandbox or in other sandboxes
  - macOS: reads and writes under the Claude Code temp root `/tmp/claude-<uid>/` (`<uid>` is the uid of the human's login), except the folder whose name is the absolute path of the folder that agent started in with every character other than ASCII letters, digits and `-` replaced by `-`. On Linux this is already blocked, because `/tmp` is hidden behind an empty folder
  - Writes of these paths: under the harness repo `open-game-works-core/`, `open-game-works-core-impl/` and `open-game-works-core-releases/`
  - Reads, writes and connections of the Docker daemon socket: `/var/run/docker.sock`, `/run/docker.sock`, `$XDG_RUNTIME_DIR/docker.sock`, the `unix://` path that the environment variable `DOCKER_HOST` or a Docker context in `contexts/meta/` of the Docker config folder (`DOCKER_CONFIG` when set, otherwise `~/.docker`) points to, under `run/` of the Docker config folder and of `~/.docker`, under `~/.colima/` and under `~/.orbstack/`
  - Reads, writes and connections of the SSH agent and tmux sockets: the socket that `SSH_AUTH_SOCK` points to, the socket that `TMUX` points to and its folder, under `tmux-<uid>/` of `TMUX_TMPDIR` and of `/tmp`
  - Reads and writes of the secret store (`## secret store`) folder: under the Linux secret store folder, and on macOS under that folder and under `~/Library/Keychains/ogw/`
  - Linux: reads, writes and connections of the ways to start a process outside the sandbox (systemd user units, Podman) and of user services: under `XDG_RUNTIME_DIR` and `/run/user/<uid>`, the `unix:path=` socket of `DBUS_SESSION_BUS_ADDRESS`, and the D-Bus system bus sockets `/run/dbus/system_bus_socket` and `/var/run/dbus/system_bus_socket`. A session bus that listens on a `unix:abstract=` socket and the abstract unix sockets of other services are reachable even inside the sandbox
  - The agent CLI does not get `DOCKER_HOST`, `DOCKER_CONTEXT`, `SSH_AUTH_SOCK`, `TMUX`, `TMUX_PANE`, `DBUS_SESSION_BUS_ADDRESS` or `XDG_RUNTIME_DIR`, and gets `tmp/` of the folder that agent started in as `TMPDIR`
  - When the agent CLI is Claude Code and the secret store of this host has the harness secret `claude-code-oauth-token`, its value is passed to the agent CLI as the environment variable `CLAUDE_CODE_OAUTH_TOKEN`. It is not passed to the broker. It is a long-lived token that needs no refresh (`claude setup-token`), so that the CLI does not refresh its login inside the sandbox
  - macOS: network connections to the address of this host (`localhost`), and unix socket connections other than the broker socket and the DNS socket `/var/run/mDNSResponder`. On Linux the network namespace is not split, because with a split namespace the agent CLI cannot reach the internet. So on Linux the TCP ports and abstract unix sockets of this host are not blocked
  - macOS: the ways to start a process outside the sandbox. These are running `/bin/launchctl`, `/usr/bin/open` and `/usr/bin/osascript`, lookups of mach services whose names start with `com.apple.coreservices.` (LaunchServices, AppleEvents) and of `com.apple.coreservicesd`, sending AppleEvents, and sending signals to processes outside the sandbox. LaunchServices can leave the app process of a blocked launch stopped outside the sandbox, and `SIGCONT` makes that process run outside the sandbox
  - Linux: other processes. The sandbox runs in a new PID namespace with the `/proc` of that namespace
  - On macOS a blocked path that does not exist is not created. On Linux each blocked path that does not exist is created as an empty folder or empty file, except that the Docker daemon socket, the SSH agent and tmux sockets and their folders, and the sockets and folders of user services are blocked only when they exist
- The seed agent (`### seed agent` of `## regress`) starts as the play agent and the judge agent do, with the same flags, login, environment and agent sandbox, with these differences. It starts in the folder `ogw-seed-*` that `ogw regress refresh` made for it (`## temp folder`), which holds its input, and its result file is `result.md` there. It has no broker: its CLI gets no `OGW_BROKER_SOCKET`, and `ogw` does not run in it. Its agent sandbox also blocks reads and writes under the harness repos (the one that `OGW_HARNESS_ROOT` or the location of the code names, and the one the code runs from), the regress repo (`paths.regress`) and `regress/` of `<dataDir>` (`### regress run`), each when it exists: its definition is in its prompt and its seed in its folder, so it reads no harness file and no other seed. `ogw agent seed` on the command line fails: only `ogw regress refresh` starts it
- session of a job: the session of the agent CLI that a job of a role that has fix rounds (`### result format`) runs in, kept by its session id in the job record. A new session of Claude Code starts with `--session-id <new UUID>`, and its session id is that UUID. The session id of a new session of Codex is the `thread_id` of the line whose `type` is `thread.started` in the output of the first run of the job; a Codex job whose first run printed none has no session. A run continues the session of a session id with `--resume <session id>` for Claude Code, and for Codex as `codex exec resume` with the options of `codex exec`, the session id and `-`. When the content agent continues the session of the content agent of the previous iteration, its first run continues the session of the last content agent job of the previous iteration that is not a variant agent (`## loop variants`), and the job keeps that session id. It does so only when that job has a session id and the session file of that session id is in the default config folder of the agent CLI of the job (Claude Code: `projects/<project folder>/<session id>.jsonl`; Codex: a file under `sessions/` whose name starts with `rollout-` and holds the session id); otherwise the job starts a new session. A variant agent and a job of `ogw agent retry` start a new session. A variant agent works in a worktree `worktrees/<game>/agent-<id>/` on branch `agent/<id>`, made from the HEAD of the work branch, as a resource agent does
- `ogw agent` puts the harness `tools/bin` at the front of the environment variable `PATH` of the agent CLI. The agent's shell calls `ogw` by name
- `ogw` inside the agent sandbox does not run a command itself; it passes the command to that agent's broker. The broker is a unix socket server that the `ogw agent` job opens outside the sandbox before starting the agent CLI and closes when the CLI ends. The socket is `brokers/<job id>/s` of the jobs folder, and that folder is a 0700 folder that only the owner writes. The socket path is passed to the agent CLI as the environment variable `OGW_BROKER_SOCKET`
  - When `OGW_BROKER_SOCKET` is set, `ogw` sends argv, cwd and `OGW_AGENT_KEY` to the broker, sends stdin when the command reads stdin, and outputs the stdout, stderr and exit code the broker returns as they are. A command that reads stdin line by line as it comes (`ogw step --stream`) gets each chunk of stdin when `ogw` reads it, and its output comes back as the command writes it
  - When the received key is not the key of that job, the broker does not run the command and returns a failure. Even when the key matches, when the command of the received argv is not a broker command, it does not run it and returns a failure (exit code 1) saying that the command is not a command of the play agent and the judge agent. The command of argv is the command with the longest name among the commands whose name words equal the leading words of argv. Broker commands are the commands that the documents the play agent and the judge agent read ([`play`](../agents/play.md), [`judge`](../agents/judge.md), [instance](../skills/game-loop/instance.md)) have those agents use, and the commands that wait for jobs: `ogw input`, `ogw capture`, `ogw log`, `ogw telemetry`, `ogw telemetry compare`, `ogw step-mode`, `ogw step`, `ogw frames`, `ogw instance release`, `ogw instance wait`, `ogw job status`, `ogw job wait`. The `--help` of those commands also runs
  - When the key matches and the command is a broker command, the broker runs that command as that agent. The environment is that of the `ogw agent` job without `OGW_JOB_ID` and the variables not passed to the agent CLI, plus that agent's `OGW_AGENT_KEY` and the `TMPDIR` the agent CLI gets; the cwd is the received cwd. That process and all its child processes run in the broker sandbox. The broker sandbox is the same as the agent sandbox, except that in the git common dir it blocks only the instance record folder, `agent-logs/` and `brokers/` of the jobs folder, `ogw-secret-files/` and `ogw-temp/`; it does not block writes to the jobs folder; of connections it blocks only the Docker daemon, the SSH agent, tmux sockets and the user services of Linux; and on Linux it does not split the PID namespace
  - The calls of `ogw input`, `ogw capture`, `ogw log`, `ogw telemetry` (not `ogw telemetry compare`), `ogw step-mode`, `ogw step` and `ogw frames` without `--background` run one at a time in one process the broker keeps in the broker sandbox (the broker worker), started at the first such call, with the same environment, the received cwd and the same output and exit code. A call that comes while the broker worker runs one, and every other call, starts a process of its own. When the caller of the call it runs goes away, the broker kills the broker worker, and the next such call starts a new one
  - When the broker closes, it ends the commands it was running, and ends the jobs that agent started that are still `running` and records them as `failed`
- `ogw agent` passes `<job id>.<nonce>` to the agent CLI as the environment variable `OGW_AGENT_KEY` and records only the SHA-256 of the nonce in the job record. The nonce is 32 secure random bytes made new for each job. The processes of an agent are the processes that have that agent's CLI process as an ancestor and the processes that have that agent's `OGW_AGENT_KEY`. The agent found through ancestors comes first
- Job records and file locks record, with a pid, the PID namespace of the process that recorded that pid (on Linux the inode of `/proc/self/ns/pid`, on other OSes none). When it differs from the PID namespace of the calling process, that pid is not used to record a job as `failed`, to kill, or to release a lock
- For each pid of the supervisor, the command process and the agent CLI, the job record also records the start time of that process (the value of `ps -o lstart=` run with `LC_ALL=C`, `TZ=UTC`). When the process of a pid is alive and its start time differs from the recorded value, cannot be read, or is not recorded, the pid is treated as reused by another process and no signal is sent. The supervisor is treated as absent only when the start time of its live pid differs from the recorded value; when the start time cannot be read or is not recorded, it is treated as present. This keeps a read made where `ps` cannot run (the macOS sandbox) from recording a job whose process is alive as `failed`. When the process of a pid does not exist, signals go only to the process group of that pid, because POSIX does not give out a process group's ID again as a pid while the group still has members. On Windows the start time is not read and signals go to the process tree
- Job records, file locks, slots and reader items also record the host boot id. What was recorded in another boot is treated as ended, regardless of pid
- The input file of the play agent and the judge agent is the JSON that [`play`](../agents/play.md) and [`judge`](../agents/judge.md) define. Before the agent starts, the files that the path fields below point to are copied into `input/` of the folder the agent starts in, under the names below. Then only those field values of the input are replaced with the absolute paths of the copied files, the result is written as `input/input.json`, and that file is passed. Other fields are not changed. Missing fields and `null` fields are skipped. When the input is not JSON or the file of a path field does not exist, the agent is not started and the command fails

  | role | path field | copied name |
  |---|---|---|
  | play | `playGuide` | `play-guide.md` |
  | judge | `A.playGuide` | `play-guide-A.md` |
  | judge | `B.playGuide` | `play-guide-B.md` |
  | judge | `telemetry` | `telemetry.md` |
  | judge | `video` of `reference.moments` | `reference-video-<k>` followed by the extension of the original file. `<k>` is the order in which that file first appears in `moments`, starting from 1. The same file is copied once |
- The `ogw` commands that the play agent and the judge agent use handle instances only through the automation channel and do not read under `paths.games` and `paths.worktrees`
- `ogw command` does not send the command and fails when either of these two holds: the calling process is a process of a running play agent or judge agent; the target instance is in the input of a running play agent or judge agent (`instance`, `A.instance`, `B.instance`, `A` and `B` of `fixtures`)
- The `output` and captures of the play agent and the judge agent are inside the folder the agent started in. When the agent ends, the result file is moved to the result file path, with each capture path in it (absolute, or relative as `captures/` or `./captures/`) changed to the moved path, and `captures/` of that folder to `records/loops/<run>/evidence/<role>-<iteration>-<k>/` (for a judge agent of `ogw loop variants`, to `records/loops/<run>/evidence/judge-<iteration>-v<k>-<j>/` beside its result file `records/loops/<run>/judge-<iteration>-v<k>-<j>.md`; for a judge agent of `ogw judge calibrate`, to `builds/calibration/<unix ms>/judge-<pair>-<k>/` beside its result file `records/calibration/<unix ms>/judge-<pair>-<k>.md`), the capture paths in the result file are replaced with the moved paths, and then that folder is deleted. A judge agent of `ogw judge calibrate` starts without a run; `ogw agent` on the command line starts a play or judge agent only in the open run
- `ogw agent` writes a run log for each agent it starts. Each time an `ogw` command runs in a process of the agent, one `{"command": "<command line of the arguments joined by spaces>", "startedAt": <unix ms>, "exitCode": <integer or null>, "summary": <summary or null>}` is added to the run log. A command started with `--background` is recorded as that one job, and `exitCode` and `summary` are the values when the job ended. A job still running when the agent ends has `exitCode` `null`. `summary` is `{"tests": <test count>, "passed": <passed count>}` for `ogw core test`, `{"glossaryMissing": ["<`glossary_missing` line>", ...]}` for `ogw data`, `{"checks": [{"name": "<check name>", "result": "<pass|fail|unknown>"}, ...]}` for `ogw check` (one per check name; a check with several platform profile items is the result combined by the rule of `## check`), and `null` for other commands. For the translation role, after the agent ends, the commit the worktree was made from is compared with the HEAD of branch `agent/<id>`, and for each language the number of rows of `data/translations/<language>.csv` whose `text` changed and the number of rows of `data/glossary.csv` whose cell of that language changed are added to the run log as `{"translation": {"<language>": {"text": <row count>, "glossary": <row count>}}}`. The run log is JSON `{"runs": [...]}` with those items and the `usage` of `### usage` added, written to `run-logs/<job id>.json` of the jobs folder and not committed. For the core agent and a review agent that targets core, the result file is committed to the branch of the worktree after the agent ends, so that it stays at the same path in `open-game-works-core-impl/` after `ogw agent merge` deletes the worktree. Other changes are not committed
- The git that the `ogw agent` job runs after the agent CLI ends does not read the global config and the system config (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`) and runs with `core.fsmonitor=false` and `core.hooksPath=/dev/null`, which take precedence over the repo config. The author and committer of the commits that git makes are the values git determined, before the agent CLI started, in the checkout the result file goes to
- The tool returns the job id. The agent writes its result only to `output`
- When a sub-agent ends without leaving a result file at `output`, or with format errors left in it (`### result format`), that work is a failure
- `ogw agent content` and `ogw agent translation` with `--seed-run <records>:<n>` start outside a run, only in a game with the regression mark (`### regression state` of `## regress`), with a new session: the content agent works in the game repo checkout with the result file `records/loops/<records>/content-<n>.md`, and a translation sub-agent in its worktree with the result file `records/loops/<records>/translation-<language>-<unix ms>.md`. Their prompts have the lines `- run: <records>` and `- iteration: <n>`, their jobs keep `<records>` and `<n>` as their run and iteration, and the result file is checked as in a run (`### result format`). The game must have no open run
- `ogw agent retry <id>` reassigns the work to a new sub-agent of the same role, giving it the input of that job, the previous result file and the failure content. It refuses the job of a variant agent and of a seed agent
- In a fun iteration whose previous iteration is a fun iteration of the same run, `ogw agent content` continues the session of the content agent of the previous iteration that was not a variant agent, so that the agent does not read the code again. ### usage

When the last run of the agent CLI of the job ends, `ogw agent` reads the usage of the job from `<id>.cli.log`, which holds the output of every run in order, and writes it as `usage` in the `meta` of the job record and at the top level of the run log: `{"cli": "<claude-code or codex>", "model": "<model>", "effort": "<effort>", "inputTokens": <integer or null>, "cachedTokens": <integer or null>, "outputTokens": <integer or null>, "costUsd": <number or null>, "costUnknown": <reason or null>, "turns": <integer or null>}`. `cli`, `model` and `effort` are those the job ran with. `inputTokens` counts every input token of the models, `cachedTokens` included; `cachedTokens` counts the input tokens read from the prompt cache. When the last run printed no usage line below (it was stopped, or ended before printing it), `inputTokens`, `cachedTokens`, `outputTokens` and `costUsd` are `null`, when a run printed none, `turns` is `null`, and the job does not fail for it. `costUnknown` is `null` when `costUsd` is a number, and otherwise the reason the cost is unknown: `codex prints no money cost` for a Codex job, `no usage line` when the last run printed no usage line with a cost, and `session before the job unknown` when the difference of a continued session below cannot be made. `ogw` has no price table to price tokens, since prices change.

- Claude Code: the last line of the output of a run that is a JSON object whose `type` is `result` (the result object of the run). The tokens are summed over the models of its `modelUsage`, which has every model of the session, helper agents included: `inputTokens` from `inputTokens`, `cacheCreationInputTokens` and `cacheReadInputTokens`, `cachedTokens` from `cacheReadInputTokens`, `outputTokens` from `outputTokens`. `costUsd` is `total_cost_usd`, which Claude Code prices at list price whatever the login, and `turns` is the sum of `num_turns` of the result objects of the runs
- A job with a session (`## agent`) also keeps the tokens and `costUsd` of the usage line of its last run as `sessionUsage` in the `meta` of the job record. A usage line has the totals of the whole session, so each token count and `costUsd` of `usage` is the value of the usage line of the last run minus that of the session before the first run: the `sessionUsage` of the job of the same session id that started last before this job when the first run continues a session, and 0 otherwise; it is `null` when either value is missing or the difference is negative
- Codex: the `usage` of the last line of the output of the last run that is a JSON object whose `type` is `turn.completed`: `inputTokens` from `input_tokens`, `cachedTokens` from `cached_input_tokens`, `outputTokens` from `output_tokens`. It has the totals of the whole session. Codex prints no money cost and no turn count, so `costUsd` and `turns` are `null`

## agent merge

For each id, `ogw agent merge` merges the files below row by row against the commit the worktree was made from, and merges other files with git merge. After merging, it runs `ogw data <game>`, commits the result together, and deletes the worktree and branch `agent/<id>`. When a conflict occurs or `ogw data` fails, that id is not merged and the worktree and branch `agent/<id>` are kept. When a file to merge row by row cannot be read as UTF-8 CSV on either side, or its header lacks the column that matches rows (`key`, `source` and `id_name` in the list below), that id is not merged, with reason `data`, the same as when `ogw data` fails.

- `resource/resources.csv`: rows are matched by `key`. When both sides changed the row of the same `key` to different contents, it is a conflict
- `data/translations/<language>.csv`: rows are matched by `key`. Row additions and deletions and `source` come from the branch the worktree was made from; `text` and `source_hash` come from the changes of the sub-agent. Sub-agent changes to keys that that branch deleted are discarded. When both sides changed `text` or `source_hash` of the same key, it is a conflict
- `data/glossary.csv`: rows are matched by the pair of `source` and `id_name`. Row additions and deletions, `source`, `id_name` and `note` come from the branch the worktree was made from; `<language>` cells come from the changes of the sub-agent. Sub-agent changes to rows that that branch deleted or whose `source` it changed are discarded. When both sides changed the same cell to different values, it is a conflict
- Edit scope of a role: server hardening `server/`, client hardening `client/`, translation `data/translations/` and `data/glossary.csv`, resource `resource/`, and for each of these roles its result file. The paths that branch `agent/<id>` changed since the commit the worktree was made from (a rename counts as a deletion and an addition) are compared with the edit scope of the role of that job. When a server hardening or client hardening job changed a path outside it, that id is not merged, with reason `outside scope`, and the worktree and branch `agent/<id>` are kept. The changes of a translation or resource job to paths outside it are discarded: those paths keep the contents of the branch the merge goes into
- The worktree of the core agent is merged with git merge, without the row-by-row merging above and without `ogw data`
- A core agent job is merged after other `ogw agent merge` runs that change the main checkout of `open-game-works-core-impl/` and `ogw core spec` runs that commit generated files to main (`## core spec and core test`) have ended, and after the `ogw core test` runs in the main checkout have all ended, module tests included. While a merge waits, an `ogw core spec` or `ogw core test` newly started in that checkout waits for that merge to end. `ogw core test` runs in the main checkout run one at a time only while they commit generated files; their module tests run together
- engine whose client core passed: an engine that has `client/<engine>/engine.json` and for which, going through the core test records of target `<engine>` for commits that main has in record order, at some record the latest result of every client module in `core-spec/` of that record's commit was `pass`, or `unknown` with the reason `screen locked`, whose headless pass passed. This term stands for an engine whose client core compiles. The core test that a job must have to merge, and the release, still need `pass`. Before that, the client core tests of that engine do not compile (`### create server core, create client core: <engine>` 5 of the `core` command)
- The passing `ogw core test` (`## command` of the `core` command) that `ogw agent merge` requires of a core agent job is not required when every `--module` is a client module (`side` is `client` in `core-spec/<module>.json` of branch `agent/<id>`, or in `core-spec/<module>.json` of main when that branch does not have it) and the engines of the files under `client/<engine>/` that the job changed include an engine whose client core has not passed. It is also not required when every file that a job without `--module` changed outside `records/` is under `client/<engine>/` of an engine whose client core has not passed (an engine whose `client/<engine>/engine.json` that branch added included) (e.g. `engine.json` of `### create server core, create client core: <engine>` 2 of the `core` command). While there is an engine whose client core has not passed, a job whose every `--module` is a tool (`contract-tool`, `data-tool`) is merged without looking at the exit code when the passed count of the last `ogw core test tools` item of the run log equals the test count and is greater than 0, because that run leaves out the round-trip tests of that engine and reports the tools as `unknown`
- When the conflicts in the git merge of a core agent job occur only in `settings/core-settings.json`, `settings/core-settings.schema.json`, the CSV files under the core test data `test-data/data/` and generated files (`## core spec and core test`), the generated files are taken from main (the next `ogw core test` makes them again on main) and the CSV files are merged row by row. A conflict in a non-CSV file under `test-data/data/` is a conflict. When either side deleted or renamed a column of the base, it is a conflict. The header is 4 rows for files under `tables/` and `system/` and 1 row for other files (`## CSV format` of the `data` skill), and columns are matched by the names in the last header row. All three files are aligned to a header that has every column of the three headers (the columns of `ours`, followed by the columns that only the other side has), with missing cells empty; each header cell above the name row takes, per column, the value changed on one side only, and when both sides changed it to different values, it is a conflict. When one header has two columns of the same name, or the `id(key)` column of the merged table has two rows with the same value (both sides added different rows for the same key), it is a conflict. Rows added on either side are all included and rows deleted on either side are removed. The data build of the next `ogw core test` checks the merged core test data. The two JSON files are merged key by key, comparing the JSON object of each file with the commit the worktree was made from: a key changed on one side only takes the changed value; a key changed to the same value on both sides takes that value; for a key changed to different values on both sides, when both values are objects their contents are merged by the same rule, when the key is in `required` of the JSON schema and both values are string arrays they are merged into a list that reflects every name added and removed on both sides, and otherwise it is a conflict. Parallel core agents change the same files, because each module adds core settings keys
- For a job for which, above, no passing `ogw core test` is required because of an engine whose client core has not passed (a job whose every `--module` is a client module, a job without `--module`), `ogw agent merge` also does not run the type check (`## command` of the `core` command). The exception for tool jobs does not apply to the type check. Failure lines of the type check are compared by file, code and message, without line and column. The type check runs outside the lock of the main checkout. The check of the branch of a job, run in its worktree, does not depend on main: it runs once per job, beside the check of main, and the branch checks of the jobs of one `ogw agent merge` that get the type check before any merge start together before the first merge. The check of main a job compares with is of main at its turn, after the merges before it. When, at the time the lock is taken, main has changed outside `records/` since the compared commit, the check of main runs again inside the lock, and is compared with the result of the branch. The result for main is kept under `ogw-cache/core-type-check/` in the git common dir of the harness repo, in a file named by that commit and the tree of the harness `tools/`. When the check stopped on an error (e.g. the engine is not on this host), it is not kept; when the harness `tools/` has uncommitted changes, it is neither kept nor used
- The merge order of core agent jobs is set by the module dependencies of `core-spec/` of main overlaid with the `core-spec/` files that the branch `agent/<id>` of each job added or changed since the commit its worktree was made from. A job of a module whose order still cannot be set is not merged, with `not defined`; when `open-game-works-core-impl/` has uncommitted changes, jobs are not merged, with `uncommitted changes`. Other ids continue to be merged
- `ogw agent merge <id>... --when-done [--then <ogw command>]... --background` waits until all the given jobs end and then merges. `--when-done` runs only with `--background`. Before starting the job it checks the `--then` values and the ids; when any id is not an `ogw agent` job or any `--then` value is to be rejected, it does not start the job and fails
  - When any ended job has an `ogw agent status` other than `done`, nothing is merged and the `--then` commands do not run. It outputs a `not done <id>: <status>` line for each such job and ends with exit code 1
  - When all are `done`, it merges them at once the same as `ogw agent merge <id>...` without `--when-done` and outputs the same lines. When any id could not be merged, the `--then` commands do not run and it ends with exit code 1
  - When all are merged, it starts the `--then` commands in the given order, one job per command the same as `--background`, and outputs a `then <job id>: <--then value>` line per command. A command that starts its job with its own `--background` option (`ogw agent`) runs with that option added
  - When a `--then` command cannot start its job, it outputs a `then not started: <--then value>: <error>` line, does not start the later `--then` commands, and ends with exit code 1. The merge lines and `then` lines output before stay as they are
  - A `--then` value is one ogw command line without the leading `ogw`. The tokens split at spaces are the argv of that command. Rejected are: an empty value, a value that contains `--background`, a command that does not exist, a command that does not accept `--background`, a value that does not parse as options of that command, and a value that does not pass the checks done before starting the job when that command runs with `--background`. A command that starts its job with its own `--background` option runs those checks when it starts the job
  - `--then` and `--background` without `--when-done` are a usage error

## loop start

The tool sets the run name `<command>-<unix ms>`, creates the work branch `loop/<run>` from main and checks it out, writes and commits `records/loops/<run>/request.md`, then prints the run name and the main commit the work branch was created from.

- For `update game`, `request.md` is the original request text from stdin; for `create game`, it is the request of `records/setup/request.md` followed by the original request text from stdin
- For `create game`, the tool also writes a draft `brief.md` and commits it together. The draft has every `## brief` heading of [`game-design`](../skills/game-design/SKILL.md) in that order, fills `## reference game` with the `## game` name of `records/setup/reference/reference.md` and that file's path, fills `## request` with the original request text of `request.md`, and leaves the other headings empty. The start commit skips the pre-commit hook, because static check `document format` blocks the empty `## genre conventions` and `## prohibitions` that the content agent fills. If the work branch already has `brief.md`, the tool writes no draft, and the content agent edits that `brief.md` to match `request.md` in iteration 1
- `create game` does not start if any of these is missing: the game repo, game settings that pass `ogw game check`, the `id-registry` branch, `records/setup/request.md`, `records/setup/name.md` with a name for each language of `supportedLanguages`, `records/setup/art-direction.md` whose `## style`, `## palette`, `## mood` are all non-empty, `records/setup/reference/reference.md`.
- `update game` does not start without `records/setup/reference/reference.md` either. Neither command starts when a video file that `## video` of that file names is not in `records/setup/reference/`. The tool prints the missing files and how to put them there.
- If the game has a run that is not closed (a loop run or a build run), the tool prints that run name and does not start. Neither command starts in a game with the regression mark (`## regress`).
- If `git status` of the game repo checkout shows changes, the tool creates nothing and exits with a nonzero code.
- If the agent CLI of play or judge in harness settings `agents`, of an item of `loop.judgePanel`, of `loop.confirmJudge` or of `loop.confirmFallback` is Claude Code and the harness secret `claude-code-oauth-token` is not in the secret store of this host, the tool creates nothing and exits with a nonzero code.
- `--limit <iterations>` sets the iteration limit of the run: the number of the last iteration of the run, an integer of 1 or more. `--until <unix ms>` sets the time limit of the run: a UTC Unix ms later than the current time. For any other value the tool creates nothing and exits with a nonzero code. The run state keeps both, and a limit not given is none. `## loop next` and `## loop verdict` use them, and `ogw loop resume` replaces them
- pin: a harness commit and run settings that the run state keeps. The tool pins the harness repo HEAD as the pinned harness commit of the run (`## loop next`) and the run settings of harness settings
- run settings: the values that harness settings, with the schema defaults filled in, hold at the run paths (AGENTS.md `## settings`). A unit of run settings is a path into them that goes down through objects only, so an array or another value is one unit
- While a loop run is open, a command that works on its game (a command given that game, and the jobs and agents of the run) reads each run path from the run settings of the last pin of the run instead of from harness settings. A run path that those run settings do not hold has no value. `ogw settings` reads and writes harness settings themselves

## loop next

An iteration is a fun iteration or a completeness iteration, and `ogw loop next` prints its kind. A fun iteration tries changes aimed at fun and runs only the checks that block play. A completeness iteration fixes defects and runs every check. The tool decides the kind from the loop iteration records of the run:

- Iteration 1 and a confirmation iteration are completeness iterations
- After a completeness iteration whose `gate` was `fail`, the next iteration is a completeness iteration
- After harness settings `loop.funIterations` fun iterations in a row, the next iteration is a completeness iteration
- After an iteration whose verdict has `success blocked by` (`## loop verdict`), the next iteration is a completeness iteration
- Otherwise the next iteration is a fun iteration

In a loop run, the tool does not raise the number, and exits with a nonzero code, in these cases:

- The current iteration number is at least the iteration limit of the run: the smaller of its `--limit` and game settings `loopIterationLimit`, or `loopIterationLimit` when the run has no `--limit`
- The harness repo HEAD is not the pinned harness commit of the run. The output names both commits. With `--repin`, the tool does not fail for it

In a loop run without `--repin`, the tool compares the harness repo HEAD with the pinned harness commit before it checks the core version of the game against the harness (AGENTS.md `## repo`), so a harness repo HEAD that moved away from the pinned commit fails with the pin output and the run stays open.

repin: a new pin of the harness repo HEAD and of the run settings of harness settings (`## loop start`), made when either differs from the last pin. With `--repin` in a loop run, `ogw loop next` repins for the iteration it starts. It prints `harness: <harness repo HEAD> (repinned from <previous pinned harness commit>)` when the commit changed, and `run settings: <the units whose value changed, joined with ", "> (repinned)` when the run settings changed.

In a fun iteration of a loop run, the output also has the line `variants: <loop.variants of the run settings>`.

Each pin counts for one iteration: the pin of `ogw loop start` for iteration 0, a repin of `ogw loop next` for the iteration it starts, and a repin of `ogw loop resume` as `## loop resume` says. The harness commit of iteration n is the commit of the last pin that counts for iteration n or an earlier one, and iteration n is repinned when a repin that changed the commit counts for it. A build run has no pin: its `ogw loop next` does not check the harness repo HEAD, its commands read harness settings, and `--repin` changes nothing in it.

## loop variants

The tool does the following in this order; the judging of a variant starts when its agent ends, while the other variant agents run, and the choice waits for the judging of every variant.

- It starts `loop.variants` variant agents together. A variant agent is a content agent that works in its own worktree of the work branch HEAD. The k-th (k from 1) gets the content input with a `## variant` heading added, whose lines are `- variant: <k> of <loop.variants>` and `- element: <target element>`. The target element is item ((k + iteration number − 2) mod 3) + 1 of `game feel`, `tension and release`, `no friction`
- variant commit: the HEAD of the branch of a variant agent that ended `done` and changed a path. A variant without a variant commit is not judged and not chosen
- With a baseline game, for each variant commit it runs `loop.judgeVotes` judges of that commit against the baseline game as `## loop evaluate` does for a fun iteration, with no save fixture instances, as soon as the agent of that variant ended, and decides the votes, the element decisions and `vs baseline` of each variant as `## loop evaluate` does, without a confirmation pair. The judges of all variants run within `maxConcurrentInstances`. The shared telemetry runs of the baseline game commit are made once and compared with those of each variant commit. Without a baseline game, no judge runs. `ogw loop variants` takes `--db postgresql` as `ogw loop evaluate` does and then starts the instances of these judges with it
- When the judging fails (e.g. an instance does not start), the tool stops the judges still running and continues with the judges that ended, and waits for the variant agents that still run without judging them. A variant whose judges did not all end gets no votes and no `vs baseline`, and the failure is written to `variants-<iteration>.json`
- It chooses one variant: among the variants whose `vs baseline` is `better`, the one with the most elements decided `this`, then the fewest `baseline` votes, then the lowest k. When none is `better`, the one with the largest count of `this` votes minus `baseline` votes, then the lowest k. A variant with a variant commit and no votes is chosen only when no variant has votes. When the merge of the chosen variant fails, the next variant in that order is chosen
- It merges the chosen variant into the work branch as `ogw agent merge` does, and in the merge commit it copies the report of that variant to `records/loops/<run>/content-<iteration>.md`, so that this report is the content agent report of the iteration, and writes `records/loops/<run>/variants-<iteration>.json`. Then it removes the worktrees and branches `agent/<id>` of the other variant agents
- When no variant is merged, it commits `variants-<iteration>.json`, removes the worktrees and branches of the variant agents, prints the `ogw agent content` call with the content input of the iteration and exits with a nonzero code.
- Step 4 judges the chosen variant again with new judges, because the best of several noisy results is more often a lucky one
- `ogw loop variants` writes the result file `records/loops/<run>/variants-<iteration>.json`. The format is `{"baseline": "<sha>" or null, "judging": "<why the judging failed>" or null, "variants": [<variant>, ...]}`, one `<variant>` per variant in k order: `{"k": <k>, "job": "<job id>", "element": "<target element>", "commit": "<variant commit>" or null, "judges": ["<judge result path>", ...], "votes": [{"element": "<element>", "this": <count>, "baseline": <count>, "decision": "<element decision>"}, ...] or null, "vsBaseline": "<better|worse|indistinguishable>" or null, "merge": "<why the merge failed>" or null, "chosen": <true|false>}`. `votes` and `vsBaseline` are null for a variant that was not judged or whose judges did not all end, and `merge` is null for a variant whose merge was not tried or did not fail

## check

How `ogw check <game> --loop` runs.

- In a completeness iteration, the check runs the regression test, static check, completeness check and row simulation. In a fun iteration, it runs only the regression test, static check and bot playtest (no blocker, full flow); the other checks are not in `check-<iteration>.json`.
- `gate` is `pass` when the regression test, static check, no blocker and full flow are all `pass`.
- The bot playtest of [`client-content`](../skills/client-content/SKILL.md) judges no blocker and full flow
- Row simulation (`## row simulation` of [`client-content`](../skills/client-content/SKILL.md)) runs on a headless instance apart from the bot playtest, which reads `list_commands` first. Its rows, in the order of the `<feature>.simulate_<table>` commands of `list_commands` and then of the rows of each table, are the units of `### spare slots`: each row runs all its random seeds, in order, on one instance
- Before each import of the `client/` of a checkout that a check runs (the import on which its client regression test, its type check and the clients of its instances run), the check puts in that `client/` the packages that `ogw generate` puts there (`## generate`), under the lock of that import, and no other file that `ogw generate` writes, so that the static check reads the committed generated files as they are. `client/addons/` is not committed, so a checkout that no `ogw generate` ran in (e.g. a new worktree) has no GUT and no plugins before that. The type check does this wherever the static check runs (`ogw check`, the pre-commit hook, `ogw build run`). When that fails, the check fails with the error
- `ogw check` imports the `client/` of its checkout once, and the client regression test, the static check and the instances of the check start after that import has ended: the import can write meta files (`.uid`, `.import`) beside the files of `client/` and `resource/`, which the static check lists and reads. The server regression test, no placeholder and the fix test proof, which do not read that `client/`, run beside the import
- Performance and UI quality each have one item in `check-<iteration>.json` per `## platform profile` of [performance](../skills/game-loop/performance.md). The result of that check is `fail` if any item is `fail`, `pass` if every item is `pass`, and `unknown` otherwise
- `ogw check <game> --loop` writes the result file `records/loops/<run>/check-<iteration>.json` and commits only that file. Run by an agent that `ogw agent` started, it fails without checking. The format is `{"commit": "<sha>", "checks": [<check>, ...], "gate": "<pass|fail>", "fixTestProof": [<proof>, ...]}`, `gate` is the `gate` of `## check`, and `fixTestProof` is that of `### fix test proof`. `<check>` is `{"name": "<check name>", "platform": <platform string or null>, "result": "<pass|fail|unknown>", "failures": [<failure>, ...], "warnings": [<failure>, ...]}`, and `<failure>` is `{"where": "<one of file:line, scenario step number, scene>", "message": "<content>", "evidence": ["<path>", ...]}`
- The text output of `--loop` prints at most 20 failures and 5 warnings of each check, then the count of the rest, and the result file holds them all. The text output of the other check modes prints every failure and at most 5 warnings of each check, then the count of the rest: warnings are the `WARN` lines of `ogw data`, and `ogw data <game> --json` holds them all. The text output of `ogw core try` prints every failure and every warning, as it checks another core and tree than `ogw data` does. `ogw data` prints at most 5 `WARN` lines of each data check code, then the count of the rest
- The check names are `regression test`, `static check`, `no blocker`, `full flow`, `performance`, `UI quality`, `no placeholder`, `row simulation`. `row simulation` has one `<failure>` per row whose judgement is not `in`; its `where` is `data/tables/<table>.csv:<line of that row>`, and its `message` starts with the row judgement and the ID name. For a table without a command, the `<failure>` has `where` `data/tables/<table>.csv:1` and a `message` starting with `error`. `platform` is the platform on which that item was judged for `performance` and `UI quality`, and `null` otherwise. The `message` of `static check` starts with the static check name. `warnings` are results that do not count as failures. `static check` has one `warnings` entry per WARN line of the data check, with `where` the `<file>:<line>:<column>` of that line and `message` `data check <code> <message>`. The `warnings` of the other checks are an empty list. `no placeholder` has one `<failure>` per placeholder resource, missing translation and stale translation, and its `message` starts with one of `placeholder <resource key>`, `translation_missing <language>`, `translation_stale <language>`
- The `<check>` of `performance` also has `hostLoad`. Its format and values are given in `### host load` of `## performance`
- When the iteration has a baseline game (`## loop baseline`), `ogw check <game> --loop` also makes the shared telemetry runs (`## loop evaluate`) of this commit and the baseline game commit beside the checks, within the instance slots of the check, so that the step 4 judges do not wait for them. It writes them to `records/loops/<run>/evidence/check-<iteration>/telemetry-runs.json` as `{"commit": "<sha>", "baseline": "<sha>", "scenario": "<SHA-256 of client/dev/bot/scenario.json of the work branch HEAD>", "runs": {"commit": [<run>, ...] or null, "baseline": [<run>, ...] or null}}`. `<run>` is `{"telemetry": <the telemetry of the client of that run>, "guide": "<play-guide.md of its instance>" or null}`, and the runs of a commit are `null` when fewer than three of them reached every step. They are not a check: they are not in `check-<iteration>.json` and do not change `gate`
- If an instance the check started fails while starting, the check's work on that instance fails, or the client process ends, then before stopping the instance the check puts the log files of that instance folder and, on macOS, the engine crash report left by the client process of that instance (the one of `~/Library/Logs/DiagnosticReports/Godot*.ips` whose `pid` is the pid of that client process) in `records/loops/<run>/evidence/check-<iteration>/instance-<id>/`
- The captures, videos and logs that the check made are in `records/loops/<run>/evidence/check-<iteration>/`. Paths are relative to the game repo. `records/loops/<run>/evidence/` is not committed

### spare slots

The units of a part of `ogw check` (the captures of a UI quality item, the rows of row simulation, the test files of the fix test proof) are run in their order by the runner of that part and, beside it, by helpers in spare slots, so that the part ends sooner and no other work of the check waits for it.

- spare slot: an instance slot of the check (harness settings `maxConcurrentInstances`) that is free while no other work of the check waits for one
- From the first unit the runner takes on, whenever a unit is taken or a slot becomes free, each spare slot starts one helper while more units are left than helpers are starting. A helper of a part whose units run on instances first starts an instance of the kind the runner runs on
- A helper takes the next unit, one at a time, until no unit is left or other work of the check waits for a slot; it then gives its slot back after the unit it runs, and a helper that is still starting stops starting. A helper whose start fails starts no more helpers of that part, and the units it did not take are taken by the others
- The result of the part is the one that its runner gives when it runs all the units in order itself

### fix test proof

The fix test proof decides whether a defect that the content agent reports `fixed` has a regression test that fails on the code before the fix. `ogw check <game> --loop` decides it for each `fixed` row of `## defects` of the content agent report `records/loops/<run>/content-<iteration>.md`, in report order, as `<proof>` `{"id": "<defect id>", "result": "<pass|fail|unknown>", "reason": "<why>" or null, "tests": [{"name": "<test name>", "result": "<pass|fail|unknown>", "reason": "<why>" or null}, ...]}`. Without that report or without a `fixed` row, `fixTestProof` is `[]`. A report that is there but cannot be read fails `ogw check <game> --loop` with the error before any check starts. When `defects.json` cannot be read, the proof of each `fixed` row is `unknown` with the reason `records/loops/<run>/defects.json could not be read: <error>`, since no row is then known not to need it; when the proofs of the rows that need it cannot be decided for another reason (e.g. git cannot read the history of the iteration), each of them is `unknown` with the error as its reason. The fix test proof is not a check: it does not change `gate`, and `ogw loop findings` makes no finding of it.

- A `fixed` row needs the fix test proof when, in `defects.json`, the `owner` of its defect is `client content`, `server content` or `contract` and the `source` is not `check`, and its `note` is not `presentation`. The proof of a row that does not need it is `unknown` with the reason `owner <owner>`, `source check` (the check confirms the defect when it runs again) or `presentation`, and runs no test
- fix base: the commit that added `records/loops/<run>/content-input-<iteration>.md` (`ogw loop input` makes it before the content agent of the iteration starts). The commits of the iteration are those from the fix base to the checked commit
- named test: a test name in backticks in the `note` of the row, with its test file relative to the game repo: `<test file>::<function>` for a client test and `<test file>::<describe names and test name joined with " > ">` for a server test (the test name of [`unit-test-core`](../skills/client-core/modules/unit-test-core.md) and of [`testing`](../skills/server-core/modules/testing.md), `client/` in place of `res://`). `tests` holds the named tests whose test file is under `client/tests/` or `server/tests/` and was added or changed by the commits of the iteration
- The tests of `tests` run on the fix base: a worktree of the fix base under `worktrees/<game>/` gets each file under `client/tests/` and `server/tests/` that the commits of the iteration added or changed with its content at the checked commit, and loses each one they deleted; its generated files are written as `ogw generate` writes them and its data binaries as `ogw check` builds them before it checks; then each test file of `tests` has a run of its own, as `ogw check <game> --regression <test file>` runs it. The runs of the server test files start once the generated files and data binaries are written and those of the client test files once the client import has ended; in `ogw check --loop` the test files of each of the two kinds are units of `### spare slots` whose helpers start no instance, and `ogw regress check` runs those of each kind one after another. A test is `fail` when that run reports it `fail`, or when the run started the test runner and does not report it (the file did not load, the run crashed or reached its time limit); `pass` when the run reports it `pass`; `unknown` otherwise (the run reports it `skip`, or it did not start the test runner, e.g. because the worktree, the generated files or the client import failed), with the reason
- `result`: `pass` when a test of `tests` is `fail`; `fail` when `tests` is empty or every test of it is `pass`, with the reason; `unknown` otherwise, with the reasons of its `unknown` tests
- The time it adds is bounded: per iteration at most one worktree, one writing of the generated files and data binaries and one client import, and one test run per test file of `tests`, each within the time limit of `ogw check --regression`. It runs beside the bot playtest and UI quality

## performance

How `ogw check` judges performance.

- The check measures by running the same scenario as the bot playtest once more on an instance that draws the screen. If `QualityCore` is in the module list, it first calls `set_quality_level`(`High`)
- While the scenario runs, the check reads `get_state` and then `get_stats` every 1000ms. One such reading is a tick. The `fps` of `get_stats` of a tick is a sample of the `scene_key` of `get_state` of that tick
- A tick has a scene load when one of its two requests did not answer `ok`, when its `boot_stage` is not `Done` or its `in_transition` is `true`, or when its `scene_key`, `last_scene_load_ms` or `boot_ms` differs from that of the tick before or there is no tick before. Only the samples of the ticks that have no scene load and whose tick before has no scene load are kept, so that no kept sample covers a scene load, a restart or the 1000ms after them
- fps bound of a sample: the smallest of game settings `targetFps`, the refresh rate and the frame limit, minus 1
  - refresh rate: the refresh rate of the main display of the host in Hz, rounded down, when the client draws on the host. It is left out for a client on a device and when it cannot be read
  - frame limit: the `frame_limit_fps` of `QualityCore` for the level that `quality_level` of `get_stats` of that tick names, with `QualityCore.levels` of the game's merged core settings. It is left out when `quality_level` names no level of `QualityCore.levels` (the empty string when `QualityCore` is not in the module list)
- A scene with 2 or more kept samples is judged. It keeps the fps when, at the 5th percentile of its kept samples ordered by fps − fps bound (nearest rank: the ⌈5n/100⌉-th smallest of n samples), the fps is at least the fps bound. A scene with 1 kept sample is `unknown`, and a scene with no kept sample is not judged unless a tick that would be kept had no numeric `fps` in that scene, which makes it `unknown`. When no scene has a kept sample, the fps is `unknown`
- The `frame_intervals_ms` of `get_stats` of a kept tick are kept frame intervals of the scene of that tick. The frame budget of a tick is 1000 ms divided by the smallest of game settings `targetFps`, the refresh rate and the frame limit of that tick. A kept interval longer than 1.5 frame budgets is a hitch: its frame came at least one frame late, while an interval up to 1.5 frame budgets is a frame on time. The hitch time of a hitch is its interval minus one frame budget, and the hitch ratio is the sum of the hitch times of all kept intervals, in ms, divided by the sum of all kept intervals, in s
- The frames keep when the kept intervals add up to at least 10 s, the hitch ratio is below 10 ms/s and no kept interval is longer than 100 ms. At 10 ms/s and more, players see the game hitch; a frame longer than 100 ms delays the response to the input of that frame so that players feel it; and over 10 s one frame within 100 ms alone does not reach 10 ms/s. These are fixed values of the check, not settings. A kept interval longer than 100 ms fails the frames however long the kept intervals add up to. The hitch ratio is judged only when the kept intervals add up to at least 10 s and every kept tick had a `frame_intervals_ms` array of numbers; otherwise, unless a kept interval is longer than 100 ms, the frames are `unknown`
- Judgement: `pass` when every judged scene keeps the fps, the frames keep and every `duration_ms` of telemetry `scene_loads` is at most game settings `loadingTimeLimitMs`. `boot_ms` is not compared. A hitch ratio failure has `where` the scene with the largest sum of hitch times. There is one long frame failure per scene with a kept interval longer than 100 ms, with `where` that scene and the longest such interval in its message
- The performance measurements run while no other instance that the same `ogw check` started runs: they start after every other instance of the check (bot playtest, UI quality, row simulation, the shared telemetry runs of `## check`) has stopped and the fix test proof (`### fix test proof` of `## check`) has ended, they measure the platform profiles one at a time, and the check starts no other instance until they end. `### host load` leaves out only the measured instance, so another instance of the check would lower the fps and the frames of the measured one
- `ogw check` measures holding the performance lease (`### performance lease`), and a measured item whose host was busy is `unknown` (`### host load`). The text output shows an `unknown` item as the line `performance (<platform>): unknown`, then per `<failure>`, which says why it is `unknown`, the line `<where> <message>` and one line per `evidence` path, then its `hostLoad` line. An `unknown` item gives no finding (`## loop findings`)

### performance lease

The performance lease is a lock of this host that keeps `local-model` generation and the instances of the regression suite from running while `ogw check` measures performance.

- `ogw generation run` of a `local-model` method holds the lease shared while its calls run
- An instance of a game with the regression mark (`### regression state` of `## regress`) holds the lease shared from when it takes its slot (`## runner`) until its record goes, unless a performance measurement starts it. It takes its slot only while no measurement holds or waits for the lease; that wait is not in `instanceWaitTimeoutMs` and lasts at most the time limit of a job. So no other instance of an `ogw regress` command runs beside a measurement, while the rest of its checks (their static checks, regression tests and the parts of a check that start no instance) runs on
- The performance measurements of one `ogw check`, those of all its platform profiles together, hold the lease exclusively from before the instance of the first starts until the instance of the last stops: meanwhile no `ogw generation run` call, no instance that holds the lease and no performance measurement of another `ogw check` runs
- A waiting measurement goes first: while it waits, no `ogw generation run` and no instance of a game with the regression mark takes the lease, so it waits only for the holders it found
- A measurement waits for the lease at most harness settings `performanceLeaseWaitTimeoutMs`. When that passes, the check does not measure, and each performance item is `unknown` with one `<failure>` whose `where` is `client/dev/bot/scenario.json:1` and whose `message` is `host busy: local generation` when an `ogw generation run` still holds the lease, `host busy: regress instance` when an instance of a game with the regression mark still holds it, or `host busy: performance measurement` when another `ogw check` holds it. Its `hostLoad` holds the readings of `### host load` taken during the wait
- The holders and waiting measurements of the lease are file locks and reader items (`## agent`): one whose process is gone or that was recorded in another boot holds nothing and is removed

### host load

While `ogw check` measures performance for a platform profile, it reads the host every 1000ms. `cpuMaxPercent` is the maximum of the CPU usage (%) of the host by processes outside the measured instance: the CPU time that the host used in that second minus the CPU time that the supervisor process of the instance and its descendant processes used in it, over the CPU time of the host in it, so that the game's own load, a threaded scene load included, does not count. A process counts in a second only when both readings of that second see it (the same pid and start time), so its CPU time in the second it starts or ends is not the instance's. When the CPU time of the processes of the host cannot be read (a platform other than macOS and Linux, or a failed reading), the CPU time of the instance in that second is 0. `memoryMaxPercent` is the maximum of the memory usage (%), and `instancesMax` the maximum of the number of instances that the runner started during that time. `ogw check` writes them in the `performance` item of that platform profile in `check-<iteration>.json` as `"hostLoad": {"cpuMaxPercent": <number>, "memoryMaxPercent": <number>, "instancesMax": <integer>}`.

A measured item whose judgement is `fail` is `unknown` instead when its `memoryMaxPercent` is at least 95 or its `cpuMaxPercent` is at least 90 (95 and 90 are fixed values of the check, not settings), because the fps and loading time of a busy host do not show those of the game. Its `failures` are then one `<failure>` per value reached, memory first, with `where` `client/dev/bot/scenario.json:1`, `message` `host memory <memoryMaxPercent>%` or `host CPU <cpuMaxPercent>%`, and `evidence` the file `performance-<platform>/samples.json` of the check evidence folder, which holds the kept samples, the kept frame intervals by scene, the telemetry `scene_loads` and the `hostLoad` of that measurement. An item whose judgement is `pass` or `unknown` keeps it.

## UI quality

For UI quality check, `ogw check` runs `capture_screen` and `list_ui` of `QACore` through the automation channel for each combination in the order below.

1. For each language of game settings `supportedLanguages`, calls `set_language` and waits until `boot_stage` becomes `Done`
2. For each item of game settings `uiCheckScreens` whose orientation equals the orientation of game settings `baseResolution`, calls `set_test_screen`(`window`, `fillMode`) and `set_virtual_notch`(`notch`). The orientation is `Landscape` when the width is greater than the height, otherwise `Portrait`
3. For each open command (a content command of `list_commands` whose name is `<feature>.open_<screen>`), calls that command and then reads `get_state` until `ui_flow` is `false` and `finite_tweens` is 0, at most `uiQuality.settleLimitMs` of game settings in real time, so that the opening presentation of the screen has ended. When the limit passes first, it goes on with the screen as it is. When the command fails, the UI quality check of that screen fails. Every later call of that command in this check (keyboard capture, gamepad focus check) waits the same way after it, and when such a call fails, the UI quality check of that screen fails and the rest of that screen's captures, keyboard captures or expansions are skipped
4. For text scale 1000 and for the largest value of `AccessibilityCore.textScales`, calls `set_text_scale`. When `AccessibilityCore` is not in the module list, does not call it and captures once

- keyboard capture: when `keyboard` of the `uiCheckScreens` item is 1 or more, for each capture, for each element of that `list_ui` whose `text_input` is `true` and `modal_covered` is `false`, in turn: puts in a `tap` at the center of the element's `rect`, calls `set_virtual_keyboard`(`keyboard`), runs `capture_screen` and `list_ui`, then calls `set_virtual_keyboard`(`none`) and the open command
- target button: an element of a `list_ui` whose `button` is `true` and `modal_covered` is `false`
- CSS size: a length in window pixels of a capture divided by `pixelRatio` of the `uiCheckScreens` item of that capture, in CSS pixels. When an item of step 2 has no `pixelRatio`, the UI quality check starts no instance and is `unknown`, with one `<failure>` per such item whose `where` is `settings.json:1` and whose `message` is `uiCheckScreens.<index of the item>.pixelRatio: missing`
- large text: an element whose `text` is not an empty string and whose `font_size` in CSS size is at least 24. `list_ui` gives no font weight, so bold text is large text from the same size
- units of the captures (`### spare slots` of `## check`): the captures of each language (step 1 for that language, then steps 2 to 4) in the order of `supportedLanguages`, then the gamepad focus check. The runner is an instance that draws the screen and that reads `list_commands` before the first unit; its helpers run the same open commands. A unit that stops (a command other than an open command fails, the boot after `set_language` does not reach `Done`, or the request of an open command throws) stops the UI quality check there: what it and the units before it judged stays, and the units after it are not in the result
- gamepad focus check: when game settings `gamepadSupported` is `true`, as the unit after the captures of every language, with the first language, the first `uiCheckScreens` item of that orientation and text scale 1000, does the following for each open command. Elements are told apart by `path`
  1. Calls the open command, `set_input_device`(`Gamepad`), `list_ui` in order. The reached buttons are initially the element whose `focused` is `true` and the target buttons whose `pad_action` is `true`
  2. Expands reached buttons b one at a time until no unexpanded reached button is left. Expanding: for each gamepad button `dpad_up`, `dpad_down`, `dpad_left`, `dpad_right`, calls `focus_ui`(`path` of b), `pad_button_down` and `pad_button_up` of that gamepad button, and `list_ui`, and adds the elements whose `button` and `focused` are `true` to the reached buttons. When `focus_ui` of b fails, b is not expanded
  3. When every target button is a reached button, that screen is `pass`; otherwise it is `fail`, and the `path` of each target button that is not a reached button goes in the result
- UI quality check is `pass` when all of the below hold
  - No capture has an element whose `clipped` is `true` or an overlap. An overlap is two elements whose `text` is not an empty string and whose `owner` is the same, whose `rect`s overlap with an area of 1 or more, and neither of whose `path` is an ancestor of the other's `path`
  - In each `list_ui` of a keyboard capture, there is one element whose `text_input` and `focused` are `true`, and its `rect` lies fully between the top edge of the window and the top edge of the keyboard (window height − `keyboard`)
  - When `gamepadSupported` is `true`, gamepad focus check is `pass` on every screen
  - In each capture at text scale 1000 that is not a keyboard capture, with the values of game settings `uiQuality` (the size of large text and the percentile, the percentages and the side length below are fixed values of the check, not settings):
    - text sizes: the distinct `font_size` values, rounded to whole pixels, of the elements whose `text` is not an empty string number at most `maxFontSizes`
    - small text: no element whose `text` is not an empty string has a `font_size` in CSS size under `minFontSize`
    - contrast: for each element whose `text` is not an empty string, whose `dimmed` and `modal_covered` are `false` and whose `rect` is fully in the window, out of the relative luminances (sRGB) of the capture pixels in its `rect`, the background is the median and the text is the luminance whose distance from the median is at the 99.9th percentile of those distances. Their contrast ratio (lighter + 0.05) ÷ (darker + 0.05) is at least `minLargeContrast` for large text and at least `minContrast` for other text. Text under a panel or popup whose modal is off stays measured
    - panel body: an element whose `owner` is a popup, panel or system popup key, whose `text` is an empty string, whose `button` and `text_input` are `false`, whose `rect` is at most 90% of the window area and has a shorter side of at least 64 in CSS size (a thinner element is a bar, not a panel), that has a descendant element, and none of whose ancestors is such an element of the same `owner`
    - empty panel: in the `rect` of each panel body, less than `maxEmptyShare` of its area is outside the `rect`s of its descendant elements whose `rect` is smaller than 90% of the panel body `rect`
    - touch target: in the UI quality check of a platform profile whose platform is `android` or `ios`, the `rect` of each target button is at least `minTouchTarget` wide and at least `minTouchTarget` high in CSS size
  - The flash check of `### flash check` is `pass`
- A UI quality check that has no failure of its own and whose flash check is `unknown` is `unknown`, with the `<failure>`s of the flash check. A UI quality check that has failures of its own and whose flash check is `unknown` is `fail` with its own failures

### flash check

The flash check of the UI quality check of a platform profile judges flashing in every frame of one recording of the bot playtest scenario on an instance of that platform, with the settings of a new device, so `reduce flash` is off.

- recorded screen: the item of step 2 whose game area is the largest in CSS size: the largest fill scale ÷ `pixelRatio`, the first of equal items. The fill scale is, of window width ÷ `baseResolution` width and window height ÷ `baseResolution` height, the larger for `fillMode` `Crop` and the smaller for `Letterbox`
- recording: the client `main` draws in a window of the CSS size of the recorded screen (its `window` ÷ `pixelRatio`, each side rounded, at least 1), gets the `window`, `fillMode` and `notch` of the recorded screen on each connection, and writes each frame as a PNG image with the engine's movie maker at game settings `targetFps` (`## runner`). The movie maker draws every frame and advances the engine by 1 ÷ `targetFps` s per frame, whatever the host speed, so the images do not depend on the host
- frame step: right after the instance started, the check reads `get_state`. When its `frame_step_fps` is not `targetFps` (missing in a core whose clock does not follow the movie maker), a frame of the recording would not be one step of the game after the frame before: the check stops the instance and the flash check is `unknown`, with one `<failure>` whose `where` is `client/dev/bot/scenario.json:1` and whose `message` is `flash: get_state frame_step_fps is <its value or missing>, not targetFps <targetFps>: the client clock does not follow the movie maker frame step`
- Then the check runs `client/dev/bot/scenario.json` on the client `main` as the bot playtest does (`## bot playtest` of [`client-content`](../skills/client-content/SKILL.md)), and reads `get_state` every 250 ms and when the scenario ends. The scene of a frame is the `scene_key` of the first of the readings, that of the frame step included, that answered after its image was written, or of the last reading when none did
- frame: the images in the order the movie maker numbers them. An image that cannot be read is left out only when it is the last one (the client was stopped while writing it)

Each pixel of each frame is judged with the linear values r, g and b of its 8-bit sRGB channels R8, G8 and B8 (for each channel c, with c' = c ÷ 255: c' ÷ 12.92 when c' ≤ 0.04045, otherwise ((c' + 0.055) ÷ 1.055)^2.4).

- relative luminance: 0.2126 r + 0.7152 g + 0.0722 b
- general transition: a pixel has a rising general transition at the first frame whose relative luminance is at least 0.1 above the lowest since its last general transition, while that lowest is under 0.8, and a falling general transition at the first frame whose relative luminance is under 0.8 and at least 0.1 below the highest since its last general transition. After a rising transition only a falling one can come and after a falling one only a rising one; before the first, either. The lowest and the highest since the last transition include the frame of that transition, and before the first they start at the first frame
- redness: r ÷ (r + g + b), and 0 when r + g + b is 0. A pixel is saturated red when its redness is at least 0.8
- chromaticity: (u', v') = (4X ÷ (X + 15Y + 3Z), 9Y ÷ (X + 15Y + 3Z)), with X = 0.4124564 r + 0.3575761 g + 0.1804375 b, Y = 0.2126729 r + 0.7151522 g + 0.0721750 b and Z = 0.0193339 r + 0.1191920 g + 0.9503041 b. Black (r + g + b is 0) has the chromaticity of white (r = g = b = 1), as every gray does
- red transition: the first frame puts the pixel on the red side when it is saturated red and on the other side otherwise, with that frame as its reference. On the red side the reference becomes each frame of that side that is redder than it, and on the other side each frame of that side that is less red than it. At the first frame of the other side whose chromaticity is more than 0.2 from that of the reference, the pixel has a red transition, changes side and takes that frame as its reference
- flashing frame: for each of the two kinds, general and red, when a transition of a pixel comes fewer than `targetFps` frames after the 6th transition of that kind before it (7 transitions, more than 3 flashes of 2 opposing transitions, within one second), the frames from that 6th transition before it to this one are flashing frames of that kind for that pixel
- field: a rectangle of 341 × 256 CSS px anywhere in the frame. One pixel of the frame is w × h CSS px, with w = `window` width ÷ (image width × `pixelRatio`) and h = `window` height ÷ (image height × `pixelRatio`) of the recorded screen, so a field is round(341 ÷ w) × round(256 ÷ h) pixels, each side at least 1 and at most that of the image
- A frame fails for a kind when a field holds more pixels for which it is a flashing frame of that kind than 21824 ÷ (w × h): an area of more than 21824 CSS px², 25% of a field
- The thresholds 0.1, 0.8, 0.2, 7 transitions, 341 × 256 CSS px and 25% are fixed values of the check, not settings
- Each run of consecutive frames that fail for one kind is one `<failure>`. Its `where` is the scene of the first frame of the run, or `client/dev/bot/scenario.json:1` when that `scene_key` is empty, its `message` is `flash <general or red>: more than 3 flashes in one second over <the largest area of the run that a field holds, in CSS px², rounded> CSS px² of a 341x256 CSS px field, frames <first>-<last> in <that scene, or no scene> (<name of the recorded screen>)`, and its `evidence` is the image of the first frame of the run and an image of the same size that is white at the pixels for which that frame is a flashing frame of that kind and black elsewhere
- The flash check is `fail` when it has a `<failure>` of a run. Otherwise it is `unknown` when the scenario stopped, with one `<failure>` whose `where` is `step <n>` and whose `message` is `flash: scenario stopped: <reason>`, or when no image was read, with `where` `client/dev/bot/scenario.json:1` and `message` `flash: the movie maker wrote no image`; it is `pass` otherwise
- The flash check starts no instance and is `unknown` when step 2 has no item, with `where` `settings.json:1` and `message` `flash: no uiCheckScreens item of the orientation of baseResolution`, or when the scenario cannot be read, with `where` `client/dev/bot/scenario.json:1` and `message` `flash: <the reason of the bot playtest>`. It is `unknown` with `where` `client/dev/bot/scenario.json:1` and `message` `flash did not run: <reason>` when the instance does not start, or an image other than the last cannot be read or has another size than the first

## loop evaluate

`ogw loop evaluate` runs step 3 (play) and step 4 (judge) of `## iteration` of [game-loop](../skills/game-loop/SKILL.md). In this document, step 3 and step 4 name these two parts, a step 3 instance is an instance of a play agent, and a step 4 judge is a judge agent of step 4.

The tool starts instances in the group order below. It starts a group only when the number of running instances with that group added does not exceed harness settings `maxConcurrentInstances`; otherwise it starts the group, and no group after it, when instances stop and free up slots. The groups that fit start together, and the instances of a group start together: an instance start waits for no other start, only for a slot. The work after an agent ends (its feedback, its stops, a call again) and the stops of instances a judge gives back run beside the polls of the other agents and beside the starts, and the instances that one stop frees (those of an agent that ended) stop together.

If `records/setup/reference/reference.md` is missing or a video file that its `## video` names is not in `records/setup/reference/`, the tool starts no instance and no agent, prints the missing files and how to put them there, and exits with a nonzero code.

- group order: the instances each step 4 judge starts with, `playInstances` instances of this commit, one instance per moment of `## judge moments` started with that moment's save fixture (`--fixture`), the instances each success confirmation judge starts with, the instances each judge of the confirmation pair starts with
- A judge gets its instances in the order it plays them (`## how to play` of [`judge`](../agents/judge.md)): its save fixture instances moment by moment in `## judge moments` order, `A` before `B`, and then its first-screen instances. The first of them, up to its budget, start together; the others start in that order as it gives instances back. The budget is its share, among the judges of its kind (the step 4 judges, the success confirmation judges, or the judges of the confirmation pair), of `maxConcurrentInstances` minus the number of step 3 instances, so that step 3 and the judges run together, and at least one instance per side. Its input names every instance; the `playGuide` and `names` of `A` and `B` come from `play-guide.md` and `records/setup/name.md` of that commit, as its first-screen instances can start after it. As the judge gives back instances with `ogw instance release`, the tool starts its next instances when a slot is free; a waiting group starts only beside the slots the running judges keep for their next instances, so the judges of one kind run at once
- In a fun iteration, the only moment is the one that the `- moment:` line of `## hypothesis` of the content agent report of the iteration names, when it is a moment of `## judge moments`: the judges get its save fixture instances. No play agent plays in a fun iteration, so it has no play feedback and no `ogw measure`. Every moment of `## judge moments` is judged in completeness iterations
- The `--fixture` of an instance started with a save fixture (steps 3 and 4) is `client/dev/bot/fixtures/<moment name>.json` of the work branch HEAD, whatever the commit of that instance
- The tool calls one play agent per step 3 instance, starting with the instances already started
- defects to confirm: the defects of `defects.json` whose `source` is `play` or `judge` and whose `status` is `awaiting confirmation` after the status changes by `## defects` of the content agent report of this iteration (`## loop record`). Every play agent of the iteration gets all of them in its input `defects`, in defect list order, each as `{"id": "<id>", "where": "<where>", "what": "<what>", "seen": ["<line>", ...]}`: the `id`, `where` and `what` of the defect, and in `seen` the text of each play feedback line that its `evidence` points to (`<feedback path>:<line>`), in `evidence` order. The judge agents get no defect
- Of the `playInstances` instances, the `--platform` of the k-th instance (k from 1) is item ((k − 1) mod the number of items of `buildPlatforms`) + 1 of `buildPlatforms`
- When the content input of iteration 1 of this run asked for the judge moment `memorable_moment`, the tool writes `memorableMoment` into `evaluate-<iteration>.json` of a completeness iteration: `missing` when `## judge moments` has no `memorable_moment` or the work branch HEAD has no `client/dev/bot/fixtures/memorable_moment.json`, and `omitted` when the step 4 judges did not put that moment in. Otherwise it writes no `memorableMoment`
- When a play agent ends, the tool appends the values of `ogw telemetry <instance> --summary` to `## coverage` of that feedback. Each of the `playInstances` instances is then stopped right after the raw data for `ogw measure` is collected from it. When all have ended, the tool calculates `ogw measure` from the collected raw data. A save fixture instance is stopped when its play agent ends
- Step 4 has harness settings `loop.judgeVotes` judge agents when there is a baseline game, and one when there is none. Each judge agent starts with a new context. It is not given the play agent's feedback or the automated check results
  - For each judge, the tool starts the instances of this commit and of the baseline game commit (`## loop baseline`) both with `ogw instance start <game> --commit <sha>`, assigns them to `A` and `B`, and puts them in the input. The first judge gets this commit as `A` or `B` at random, and each next judge gets the side opposite to the judge before it, so that both orders are judged. The two instances must be started the same way so that the judge agent cannot tell `A` from `B`. Which side is which is written only in the loop iteration record. When there is no baseline game, only this instance goes in, as `A`
  - shared telemetry runs of two commits: per commit, three runs of `client/dev/bot/scenario.json` of the HEAD of the game repo checkout (in a run, the work branch HEAD), each on a new headless instance of that commit started with `--commit <sha>`, up to its last step or its first failed step. The runs that did not reach a step are replaced together by as many new runs on new headless instances, up to three new runs per commit; no new run starts once three runs that reached every step can no longer be made. The runs of both commits run at once
  - When there is a baseline game, the tool takes the shared telemetry runs of this commit and the baseline game commit from `telemetry-runs.json` of `## check` when that file names these two commits and the SHA-256 of `client/dev/bot/scenario.json` of the work branch HEAD; otherwise it makes them before the step 4 judges start, ahead of every group in the group order. While it makes them, the runs keep three slots per commit they run and the judges that wait for them keep the slots of their groups, and a group after those judges that does not wait for the runs (step 3) starts beside them when it fits. It compares the telemetry of the two commits the way `ogw telemetry compare` does, with two changes: a metric value of a commit is the mean of its three runs, and a metric difference counts (`d` is not 0) only when the gap between the closest run values of the two commits is larger than the spread (largest minus smallest) of the run values of either commit, because the runs of one commit differ from each other too. For each judge, it writes that comparison with the instances named by that judge's `A` and `B` to `records/loops/<run>/evidence/telemetry-<iteration>-<k>.md` and puts its absolute path in the judge input `telemetry`. All runs got the same inputs, so the comparison does not depend on how a judge played. When a commit has fewer than three runs that reached every step, `telemetry` is `null`
  - The k-th judge (k from 1) runs with item (floor((k − 1) / 2) mod the number of items) + 1 of harness settings `loop.judgePanel` as its agent CLI, model and effort, and with harness settings `agents.judge` when `loop.judgePanel` is empty. Each item thus runs two judges in a row, which get opposite sides, so that each item judges both side assignments. Every item judges only when `loop.judgeVotes` is at least twice the number of items
  - In a fun iteration, the judge input `elements` is `game feel`, `tension and release`, `no friction`, the elements that a short play can judge, and `reference` is `null`. In a completeness iteration, `elements` holds every element of `## fun judgement criteria` of [`judge`](../agents/judge.md) and `reference` is the reference game
  - When there are `## judge moments`, for each moment the tool starts one more pair of instances of the same two commits with `--commit <sha>` and that moment's save fixture (`--fixture`), and puts them in with the same `A`, `B` assignment. An instance that could not be started with its save fixture is not put in. If the number of instances to put in exceeds harness settings `maxConcurrentInstances`, the tool puts in only as many as do not exceed it, in `## judge moments` order, and the moments not put in are recorded in loop iteration record `## judge`
  - When the judge agent ends, all instances of that judge are stopped, together
  - The tool reads a judge result as its judge input sets (`### result format` of `## agent`): `## vs baseline` and `## moments` only when `B` of the input is not `null`, and `## vs reference` only when `reference` of the input is not `null`
  - vote: in each step 4 judge result whose judge did not fail, the winner of each element of `elements`, restated relative to this instance, is a vote for `this` or `baseline`. `indistinguishable` and `n/a` are no vote
  - element decision: `this` when the element has no `baseline` vote, its `this` votes are at least two thirds of `loop.judgeVotes` rounded up and at least 2, and they come from judges of both side assignments; `baseline` the same way the other way round; `uncertain` when the element has both `this` and `baseline` votes; `indistinguishable` otherwise
  - `vs baseline`: `better` when at least one element is decided `this`, no element is decided `baseline`, and no step 4 judge result `## moments` says that the other side is better at a moment of `## judge moments` put in that judge; `worse` when at least one element is decided `baseline` and none is decided `this`; `indistinguishable` otherwise. When there is no baseline game, there is no `vs baseline`. When the confirmation pair is called, the `vs baseline` of the iteration is the one the confirmation pair gives; otherwise it is that of the step 4 judges together
  - `vs reference`: per judge, of the rows of judge result `## vs reference` whose `instance` is the side assigned to this instance, leaving out the rows whose `result` is `n/a`, `pass` when such rows exist and all are `pass`, `fail` when any is `fail`, and `unknown` otherwise. The `vs reference` of the step 4 judges together is `fail` when any judge's is `fail`, `pass` when every judge that did not fail has `pass`, and `unknown` otherwise. A fun iteration has no `vs reference`
- success confirmation judge: when the step 4 judges have ended and the other conditions of a candidate iteration hold (the `vs reference` and `vs baseline` of those judges together, and the four completeness check elements of `check-<iteration>.json` other than no placeholder), `ogw loop evaluate` calls `loopStop.successJudges` more judge agents without waiting for the remaining play. For each judge, it newly starts instances of the same two commits as step 4 (including save fixture instances) with `--commit <sha>` as in step 4, assigns `A` and `B` at random anew, and gives the same input as the first step 4 judge with that assignment. It runs with harness settings `loop.confirmJudge` as its agent CLI, model and effort when it is set, and otherwise with those of the first step 4 judge. The `vs reference` of that judge is decided per judge as in step 4, with that judge's assignment. If any ended judge has a `vs reference` that is not `pass`, the judges not yet called are not called. When a judge ends, the instances that judge used are stopped. Success confirmation judges are not called in a build run
- confirmation pair: in a fun iteration, when harness settings `loop.confirmJudge` is set and the step 4 judges have ended with a `vs baseline` of `better` together, `ogw loop evaluate` calls two more judge agents with `loop.confirmJudge` as their agent CLI, model and effort. For each judge, it newly starts instances of the same two commits as step 4 (including save fixture instances) with `--commit <sha>` as in step 4. The first judge gets this commit as `A` or `B` at random and the second the other side, and each gets the same input as the first step 4 judge with that assignment. When a judge ends, the instances that judge used are stopped. The element decisions of the confirmation pair are made from the votes of its two judges as in step 4, with 2 in place of `loop.judgeVotes`. The confirmation is `confirmed` when the confirmation pair decides `this` for at least one element that the step 4 judges decided `this` and decides `baseline` for no element, and `overturned` otherwise. The `vs baseline` of the iteration is `better` when the confirmation is `confirmed` and `indistinguishable` when it is `overturned`
- `ogw input` and `ogw step` of a play agent fail once harness settings `loop.playBudgetMs` has passed since its first input or step, except the release of a held input, and the play agent then writes its result
- `ogw input` and `ogw step` of a judge agent on an instance fail once harness settings `loop.judgeInstanceBudgetMs` has passed since its first input or step on that instance, except the release of a held input
- A play agent job and a judge agent job are stopped when they reach harness settings `loop.playTimeLimitMs` and `loop.judgeTimeLimitMs`, and a stopped job is a failed agent
- `ogw loop evaluate` calls a failed play agent or judge agent again as a new agent with the same input, on newly started instances. When the call-again count reaches harness settings `backgroundRetryLimit`, it calls no more and sets the result of that agent to `failed`. A `failed` judge gives no vote, and its `vs reference` is `unknown`
- confirmation fallback: when the job of a judge that runs with `loop.confirmJudge` (a judge of the confirmation pair, a success confirmation judge) ends without a judge result whose tables can be read, its agent CLI output (`<id>.cli.log` in `agent-logs/` of the jobs folder) has a limit message of that agent CLI, and harness settings `loop.confirmFallback` is set, `ogw loop evaluate` calls that judge again as a new agent with the same input, on newly started instances, with `loop.confirmFallback` as its agent CLI, model and effort. A judge falls back once. That call is not counted in the call-again count of `backgroundRetryLimit`, and the later calls again of that judge also run with `loop.confirmFallback`. A failure without a limit message is called again with the same agent CLI
- The play agent and the judge agent are not given `brief.md`, `design.md` or the content agent's report
- The input of play and judge holds only the fields of its format. The agent cannot read paths other than `playGuide`, `video` and `telemetry`

limit message: a line of the limit text of a job that starts with one of the texts below and says that the usage limit or the rate limit of that agent CLI was hit. The limit text is read from the agent CLI output, which the agent CLIs print as JSON (`## agent`): for Claude Code, each line of the output, with a result object replaced by the text of its `result`; for Codex, each line of the output, the `message` of each event whose `type` is `error`, and the `message` of the `error` of each event whose `type` is `turn.failed`. A Codex line also counts when it starts with `ERROR: ` and then one of the texts, the form `codex exec` prints on stderr. The `’` of the Codex texts is U+2019.

## loop baseline

`ogw loop baseline <game>` decides the baseline game. The baseline game of a confirmation iteration is the commit of its candidate iteration. Otherwise, `create game` has no first baseline game, and the first baseline game of `update game` is our game started from the main commit the work branch was created from. Going through the loop iteration records of the iterations before the current one in iteration order, the commit of an iteration whose `vs baseline` is `better` becomes the next baseline game, and while there is no baseline game, the commit of an iteration that passed the regression test, static check, no blocker and full flow of `## check` becomes the baseline game

## loop findings

For the hardening record of a build run, `ogw loop findings <game> --hardening` makes a finding for each `## content agent fixes` item of that round and writes them to `records/loops/<run>/findings-hardening-<round>.json`; the `owner` is the `owner` of that item. A finding has the fields of a defect except `id` and `status`, and the tool makes findings from the results below. The tool discards a finding for which one of `where`, `what`, `evidence` cannot be set, and also writes the list of discarded findings in that file.

- Each `<failure>` of a check whose `result` is `fail` in `check-<iteration>.json`. The no placeholder check is left out. The `owner` of `row simulation` is `client content` when the row judgement of that failure is `error`, and `data` otherwise
- Each target whose `result` is `out` in `measure-<iteration>.json`. `source` is `check`, and `owner` is `data` when that target has `data`, and `design` otherwise
- Each observation in play feedback `## observations` whose severity is not `none`. In a confirmation iteration, only the observations whose severity is `blocker`
- Each item in `## defects` of this iteration's judge results (step 4 judges, judges of the confirmation pair and success confirmation judges) whose `instance` is the side assigned to this instance
- When `evaluate-<iteration>.json` has `memorableMoment`, one finding: `source` `judge`, `severity` `minor`, `owner` `design`, `where` `judge moment: memorable_moment`, `what` `memorable_moment <value of memorableMoment>`, `why` "the judge does not see the memorable moment of `brief.md`", and `evidence` the path of `evaluate-<iteration>.json`
- Each row in `## vs reference` of this iteration's judge results (step 4 judges, judges of the confirmation pair and success confirmation judges) whose `instance` is the side assigned to this instance and whose `result` is `fail`. `source` is `judge`, `severity` is `major`, `where` is `vs reference: <element>`, `what` is the `reason` of that row, `why` is "worse than the reference game, so `vs reference` is `fail`", and `evidence` is the `evidence` of that row and that judge result path

`ogw loop findings` also fills `id`, `severity`, `owner` and `why` of a UI quality failure whose message names its problem kind and the prefab or scene it is in: `id` is `<kind>-<prefab or scene>` in kebab-case, or the `id` of a defect of `defects.json` whose message names the same kind and prefab or scene; `severity` is `major` and `owner` is `client content`. So the same kind in the same prefab or scene, in every resolution, language and text scale, is one defect under one `id` in every iteration. While a row of `resources.csv` of type `nine_slice`, `background` or `font` is `placeholder` or `requested`, it fills only `id`, as the placeholder may be what fails.

## loop record

A play of `evaluate-<iteration>.json` with an empty `result` (its save fixture did not start) has no observations for `ogw loop findings` and `ogw loop record`.

`ogw loop record` merges findings with the same `id` into one defect. `severity` is the highest one, `evidence` is all of them, and the other fields are those of the first finding in the file. The defect list is in `severity` order, in finding file order within the same `severity`, followed by the defects not in this iteration's findings in their previous order.

`ogw loop record` changes status as below, and writes the defect list and the `## loop verdict` counts of each defect to `records/loops/<run>/defects.json`. When the same iteration or the same round is recorded again, it discards the changes of the earlier record and does them again.

- A defect with a new `id` is `open`
- First, status changes by `## defects` of this iteration's content agent report (not with `--hardening`): `not reproduced` becomes `awaiting confirmation`; `fixed` becomes `awaiting confirmation` when the row does not need the fix test proof or its proof in `fixTestProof` of `check-<iteration>.json` is `pass` (`### fix test proof` of `## check`), and otherwise changes nothing; `refused` becomes `refused` (with the reason kept). `not done` changes nothing
- Then each `awaiting confirmation` defect is decided by the confirmation of this record. The confirmation is, when `source` is `check`, `## check` of this iteration (for a defect from a target of `ogw measure`, the `ogw measure` of `## loop evaluate`); when `hardening`, the hardening record of the round recorded with `--hardening`; when `play` or `judge`, the findings of this record and the answers about the defect in `## defects` of the play feedback of the plays of `evaluate-<iteration>.json` whose `status` is `done` (an answer is the `result` of the row of its `id`). If the confirmation gave a result, the defect is `open` when a finding with the same `id` appears in this record from any `source` (the same `id` means the same cause) or a play agent answered `reproduced`, and `fixed` otherwise
- If the confirmation gave no result, the defect stays `awaiting confirmation`. The confirmation gave a result: for `check`, when one of the checks that the defect's `evidence` points to has an item whose `result` is `pass` or `fail` in `check-<iteration>.json`, or one of the metrics that `evidence` points to has `result` `in` or `out` in `measure-<iteration>.json`; for `hardening`, when that hardening record exists; for `play` and `judge`, when a finding with the same `id` appears in this record or a play agent answered `reproduced` or `absent`. An answer `not reached` gives no result, and no judge answers: the judges are not shown defects. In a record with `--hardening`, only the defects whose `source` is `hardening` are decided
- A `reproduced` answer adds `<feedback path>:<line of its row>` and its `capture` to the `evidence` of the defect
- When a finding of a `fixed` defect appears again, the defect is `reopened`. The content agent fixes a `reopened` defect the same way as an `open` one
- A `refused` defect stays `refused` even when its finding appears again
- `refused` marks a defect that the content agent decided not to fix in order to keep the brief

## loop verdict

`ogw loop verdict` judges from the loop iteration records and `defects.json` of the current run.

| reason | condition |
|---|---|
| `success` | The current iteration is a candidate iteration or a passed confirmation iteration, `defects.json` has no blocking defect, and there is no unhandled worker job |
| `repeated defect` | The same defect went from `awaiting confirmation` to `open` by confirmation (`## loop record`: a finding of its `id`, or a `reproduced` answer of a play agent) `loopStop.repeatedDefect` times. The count starts with the first counted change, returns to 0 when that defect becomes `fixed`, and starts again with the first change after that. Defects whose `owner` is `resource` are not counted |
| `oscillation` | The same defect changed from `fixed` to `reopened` `loopStop.oscillation` times |
| `plateau` | Counting only the iterations that are not confirmation iterations and have a `vs baseline`, `loopStop.plateau` consecutive iterations ending with the last one have a `vs baseline` that is not `better` |
| `limit reached` | The current iteration number is at least the iteration limit of the run (`## loop next`), or the current time has reached the time limit of the run |

- When the conditions of several reasons hold together, the loop stops with the reason highest in the table
- candidate iteration: a completeness iteration that is not a confirmation iteration, whose step 4 judges together have `vs reference` `pass` and a `vs baseline` that is not `worse`, whose four completeness check elements other than no placeholder (no blocker, performance, full flow, UI quality) are all `pass`, and whose `loopStop.successJudges` success confirmation judges all have `vs reference` `pass`. The no placeholder element is not looked at, because resource work and translation work do not make the loop wait
- confirmation iteration: the iteration after the verdict of a candidate iteration did not stop the loop and gave `confirm`. The content agent does not edit, and steps 2 to 8 of `## iteration` of [game-loop](../skills/game-loop/SKILL.md) run on the state with the finished resource work and translation work merged. It passes when it meets the conditions of a candidate iteration and the sum of `blocker` in loop iteration record `## play` is 0. The no placeholder element does not block passing here either, and what remains is reported as a failure in `## loop end-record`
- unhandled worker job: a resource or translation `ogw agent` job of this run that the `- instance:` commit of the current iteration record has not seen. These are running jobs, jobs that ended but are not merged, and jobs merged after that commit. A job that was reassigned or is no longer reassigned, and a job that `ogw loop sync` finally could not merge for a reason other than a conflict or an `ogw data` failure, are not unhandled worker jobs. When there is an unhandled worker job, that iteration was judged without the resources and translations that job made
- blocking defect: a defect of `defects.json` whose `severity` is `blocker` or `major` and whose `status` is `open`, `reopened` or `awaiting confirmation`. A `refused` defect is not one. When the current iteration is a candidate iteration or a passed confirmation iteration and `defects.json` has blocking defects, the output has the line `success blocked by: <their ids joined with ", ">` after the evidence lines, whatever the reason, and the run state keeps those ids with the verdict
- For a candidate iteration or a passed confirmation iteration that has no blocking defect, is not `success` and has no other reason, `ogw loop verdict` gives `confirm`. The next iteration is the confirmation iteration of that candidate iteration. A confirmation iteration that did not pass, and a candidate iteration or a passed confirmation iteration that has a blocking defect, give `continue` when there is no other reason, and the next iteration is a normal iteration
- The evidence of `limit reached` has one line per limit reached: `iteration <n> reached --limit <limit>` or `iteration <n> reached game settings loopIterationLimit <limit>`, whichever gives the iteration limit of the run, and `now <unix ms> reached --until <unix ms>`. The time limit is judged only by `ogw loop verdict`, so the iteration in progress when that time comes ends with its loop iteration record before the loop stops

## loop prepare-merge

- no arguments: runs only in a loop run. Picks the commit to merge from the loop iteration records of the current run by the rules below. When the HEAD of main is not the main commit that the work branch of the run state was made from, it makes nothing, outputs the two commits and ends with a nonzero code. Otherwise, when the picked commit was picked by the last rule below, it does the same as `--commit <that commit>`. When it is the commit of a `success`, confirmation iteration or candidate iteration, it creates and checks out branch `merge/<run>` from that commit, replaces only `records/` with that of the work branch HEAD, and commits. The resource work and translation work merged after that commit is left out because it was not checked. When no commit is picked, it does the same as `--records-only`, and code, data and resources do not go into main. It outputs the picked commit (`none` when there is none)
  - On `success`, the commit to merge is the commit of that iteration. Otherwise it is the commit of the most recent passed confirmation iteration, or when there is none, the commit of the most recent candidate iteration. When there are neither, it is the most recent commit among the iterations whose loop iteration record has regression test, static check, no blocker and full flow `pass` in `## checks` and a step 4 judge whose `status` is `done` and whose `vs baseline` is not `worse`
- `--records-only`: creates and checks out branch `merge/<run>` from the main commit the work branch was made from, replaces `records/` with that of the work branch HEAD, and commits
- `--commit <sha>`: creates and checks out branch `merge/<run>` from that commit, replaces `records/` with that of the work branch HEAD, adds, out of the changes to `resource/`, `data/translations/` and the `<language>` cells of `data/glossary.csv` made by resource work and translation work merged after that commit, those for resource keys, translation keys and glossary rows that exist in that commit, runs `ogw resource sync` and `ogw data`, and commits. The work merged after that commit is only those of the merges recorded in the run state each time `ogw loop sync` merged with `ogw agent merge` (role, work branch commit before the merge, work branch commit after the merge) whose commit before the merge is that commit or a descendant of that commit
- In all three modes, when a branch `merge/<run>` not merged into main already exists, it is deleted and made again. When a branch `merge/<run>` merged into main exists, nothing is made and the command ends with a nonzero code
- All three modes record the result in the run state, replacing the previous record. The result is the commit to merge (the picked commit with no arguments, that commit with `--commit`, `none` with `--records-only`), whether the work merged after that commit was added (as with `--commit`), the HEAD of main, whether `merge/<run>` was made, and the reason of the failure when it was not made. The failure `did not finish` is recorded before the work starts and replaced when it ends, so a process that dies midway also stays recorded as a failure

## loop resume

The tool does the following in this order.

1. If it is a loop run and `merge/<run>` has been merged into main, prints `resume at: end 5` and ends
2. Changes nothing and exits with a nonzero code when `--limit` or `--until` is given in a build run or holds a value that `## loop start` refuses; when, in a loop run, the harness repo HEAD is not the pinned harness commit (`## loop next`) and `--repin` is not given; or when, in a loop run, the repin of step 3 changes the pinned harness commit, counts for the current iteration, and game settings `coreVersion` at the HEAD of the branch of the run is not the core version of the harness repo HEAD (AGENTS.md `## repo`), since no `ogw loop next` checks the core version for that iteration. For the harness repo HEAD, the output names both commits; for the core version, it is the output of `ogw loop next`
3. With `--repin`, repins (`## loop next`) and prints the lines of a repin of `ogw loop next`, each followed by `, counts for iteration <n>`. The repin counts for the current iteration when that iteration has started and its loop iteration record does not exist, and for the next iteration otherwise. With `--limit` or `--until`, replaces that limit of the run
4. Waits for the `running` jobs, except the `ogw agent` jobs whose role is resource or translation. If a job does not end within harness settings `jobWaitTimeoutMs`, counted per job, prints `job <id> is still running; run ogw loop resume again` and exits with code 1. The lead agent then runs `ogw loop resume` again
5. Checks out the branch of that run (`loop/<run>` for a loop run, `build/<env>-<version>` for a build run). If there are uncommitted changes, puts them away with `git stash push --include-untracked`
6. Stops all running instances
7. Removes the worktrees and branches `agent/<id>` of the variant agents of the run that were not merged
8. Runs `ogw loop sync <game>`
9. Prints where to continue. For a build run, it is the step that `## procedure` of [`build`](../skills/build/SKILL.md) sets. For a loop run, it is the first of the following that matches. `n` is the current iteration number
   - If `n` is 0, step 2 of `## start` of [game-loop](../skills/game-loop/SKILL.md)
   - If `records/loops/<run>/iteration-<n>.md` exists, step 8 of iteration `n`
   - If `records/loops/<run>/content-<n>.md` exists, step 2 of iteration `n`
   - Otherwise, step 1 of iteration `n`

An interrupted `ogw loop variants` leaves no `content-<n>.md`, because the tool commits it in the merge commit of the chosen variant, so iteration `n` continues at step 1 and `ogw loop variants` runs again.

## loop dispatch

- `ogw loop dispatch` runs `ogw resource request <game> --pending` before it calls resource sub-agents
- It starts the resource sub-agents together, then writes the translation inputs of every language in one commit and starts the translation sub-agents together
- `ogw loop dispatch` holds back a resource request file from resource sub-agents while a key of it has methods (those that `ogw generation methods` gives, other than the temporary method) none of which has the install that `ogw generation install` gives it on this host, and an install job of those methods runs. Once per run for each such method, it starts `ogw generation install <method>` as a background job or takes a running install job whose job record names the install folder of that method that this checkout uses (`## generation install`); it starts none for a method with `provider` while harness settings `tools.ffmpeg` is not installed. It prints `held <request file>: <methods> not installed on this host` and `<job id> <install command>`. A later `ogw loop dispatch` gives the file to a resource sub-agent once those methods are installed, or once their install job ended without installing them; then it prints `install failed <method>: ...`, and the lead agent tells the human that line in its report

## loop sync

- Resource sub-agents and translation sub-agents work in separate worktrees that `ogw agent` created from the work branch. `ogw loop sync` merges them into the work branch with `ogw agent merge <id>`
- `ogw loop sync` reassigns, with the same input, work that hit a conflict while merging or whose `ogw data` failed, and reassigns failed work with `ogw agent retry`. Resource work and translation work is no longer reassigned once its reassignment count reaches harness settings `backgroundRetryLimit`
- In a pass, the failed work is reassigned before the merges, which run one after another in the checkout, so that a reassigned job does not wait for them. With `--wait`, between passes it reads only the jobs that run, and starts the next pass once one of them ended

## video

What `ogw video <game> [--commit <sha>] [--language <language tag>]` does.

The tool starts an instance of that commit (when omitted, the game repo checkout) and records client `main` with the engine's movie maker at the size of game settings `baseResolution`. With `--language`, it switches to that language with `set_language` of `QACore`. Then it runs only the first `auto` step of `client/dev/bot/scenario.json` until its `until`, records 5000ms more, stops the instance, writes an H.264 mp4 to `builds/videos/` of the game repo, and prints its path. The movie maker advances game time by a fixed amount per frame, so the recording duration and the video length can differ. When they differ by more than 2%, the tool fits the video length to the recording duration.

## judge calibrate

`ogw judge calibrate` and `ogw judge label` do not start in a game with the regression mark (`## regress`), while the game has an open run, while an `ogw judge calibrate` job of the game runs, or while `git status` of the game repo checkout shows changes. Before their work, they check out main in that checkout.

- judged pair: the `- instance:` and `- baseline:` commits of a loop iteration record on main whose `- baseline:` is not `none` and whose `## judge` is not `none`. The most recent judged pair is that of the record added by the most recent commit in the history of main
- calibration judge: a step 4 judge of a fun iteration (`## loop evaluate`) on a pair of a `this` commit and a `baseline` commit. Both instances start with `--commit <sha>` as in `## loop evaluate`, the sides alternate from judge to judge, `elements` holds the elements of a fun iteration, `fixtures` is empty and `reference` is `null`. When main HEAD has `client/dev/bot/scenario.json`, `telemetry` is the comparison of the shared telemetry runs (`## loop evaluate`) of the two commits of the pair, which the tool makes itself
- judging: the judges of a pair whose votes make one element decision per element. A retest pair has two judgings: its first `loop.judgeVotes` judges and the judges after them. Every other pair has one judging of all its judges. The k-th judge of a judging runs with `loop.judgePanel` as in `## loop evaluate`, with k counted from 1 in that judging
- The element decisions of a judging are made as in `## loop evaluate`, with the number of judges of the judging in place of `loop.judgeVotes`. A pair counts in its rates only when every judge of the pair is `done`. A pair one of whose commits is not in the game repo is not judged
- The judges of all pairs run as `ogw loop evaluate` runs its judges: one instance group per judge within `maxConcurrentInstances`, and a failed judge is called again up to `backgroundRetryLimit`

| pair | this | baseline | judges | rate |
|---|---|---|---|---|
| null pair `null-<n>`, harness settings `calibration.nullPairs` of them | main HEAD | main HEAD | `loop.judgeVotes`, the first on a random side | false win rate: the share of the element decisions of the counted null pairs that are `this` or `baseline` |
| order pair `order-<n>`, one per judged pair of the `calibration.orderPairs` most recent judged pairs with different commits, `order-1` the most recent | the `- instance:` commit of the judged pair | its `- baseline:` commit | 2 × `calibration.orderRuns`; `this` is `A` for the odd-numbered judges and `B` for the even-numbered | order consistency: the share of the order items whose side vote is the same for the two side assignments and is not `mixed`. An order item is an element of a counted order pair. The side vote of a side assignment is the vote that every judge of that assignment gave the element (`this`, `baseline` or no vote), or `mixed` when they differ |
| retest pair `retest-<n>`, one per judged pair of the `calibration.retestPairs` most recent judged pairs with different commits, `retest-1` the most recent | the `- instance:` commit of the judged pair | its `- baseline:` commit | 2 × `loop.judgeVotes` in two judgings, the first on a random side | retest agreement: the share of the retest items whose element decisions in the two judgings are the same. A retest item is an element of a counted retest pair |
| degraded pair `degraded-<degradation>-<n>`, `calibration.degradedPairs` per degradation | main HEAD | main HEAD, whose instances start with the degradation | `loop.judgeVotes`, the first on a random side | sensitivity: the share of the counted degraded pairs whose element decision of the target element of their degradation is `this` |
| labeled pair `label-<n>`, one per entry of `records/calibration/labels.json`, `<n>` the order of the entry | `A` of the entry | `B` of the entry | `loop.judgeVotes`, the first on a random side | human agreement of an element: the share of the counted labeled pairs whose decision of that element equals the answer of the entry. `this` equals `A`, `baseline` equals `B`, `indistinguishable` equals `same`, and `uncertain` equals no answer |

`<n>` starts from 1. When main has fewer judged pairs with different commits than `calibration.orderPairs` or `calibration.retestPairs`, there are as many order pairs or retest pairs as it has. A degradation makes the target element of the baseline instances of a degraded pair worse and leaves the game code as it is.

| degradation | target element | baseline instances |
|---|---|---|
| `latency` | `game feel` | start with `--input-latency <calibration.degradeLatencyMs>` (`## runner`), the instances of the bot runs of the shared telemetry included. The shared telemetry adds that latency to each `input_latency_ms` of that side, because the client measures from when it gets the input |
| `network` | `no friction` | start with `--network-delay <calibration.degradeNetworkDelayMs>` (`## runner`), the instances of the bot runs of the shared telemetry included |
| `feedback` | `game feel` | start with `--feedback-off` (`## runner`), the instances of the bot runs of the shared telemetry included |
| `reward` | `tension and release` | start with `--reward-presentation-off` (`## runner`), the instances of the bot runs of the shared telemetry included |

- value: a share that a rate line writes. The false win rate has one value. Order consistency and retest agreement each have the value `all` over all their items and one value per element of `elements` over the items of that element. Sensitivity has the value `all` over all counted degraded pairs and one value `<degradation> (<target element>)` per degradation over its counted degraded pairs. Human agreement has one value per element of `elements`
- A value is written `<value rounded to two decimals> (<count> of <total>)` when its total is at least harness settings `calibration.minDecisions`, and otherwise `none (<total> of <calibration.minDecisions>)`. A value counts only in the first form
- kappa: the chance-corrected agreement (p_o − p_e) ÷ (1 − p_e) over the items of a value of order consistency or retest agreement. Each item has one rating per rater, and the categories are the values a rating takes
  - order item: the raters are the judges of the pair, and a rating is the vote of the judge for the element (`this`, `baseline` or no vote). With 2 judges it is Cohen's kappa of the judge with `this` on `A` and the judge with `this` on `B`, and with more judges it is Fleiss' kappa
  - retest item: the raters are the two judgings, and a rating is the element decision of the judging (`this`, `baseline`, `indistinguishable`, `uncertain`). It is Cohen's kappa
  - Cohen's kappa: p_o is the share of the items whose two ratings are the same, and p_e is the sum over the categories of the product of the shares of the items that each of the two raters gave that category
  - Fleiss' kappa, with m ratings per item: p_o is the mean over the items of Σ n_c × (n_c − 1) ÷ (m × (m − 1)), where n_c is the number of ratings of the item in category c, and p_e is the sum over the categories of the square of the share of all ratings that are in that category
- A kappa is written `kappa <value rounded to two decimals>`, `kappa undefined` when p_e is 1 (every rating is in one category), and `kappa none` when its value does not count. A kappa counts when its value counts and it is not `undefined`

A recommendation line is written for each row below whose condition holds, followed by ` (<the conditions that hold>)`, the conditions joined with `, `. A condition that holds is written `<rate> <value name> <value>`, `<rate> <value name> kappa <kappa>` for a kappa, and `false win rate <value>` for the false win rate. The value name of human agreement is its element.

| condition | recommendation line |
|---|---|
| the false win rate counts and is above 0 | `raise loop.judgeVotes to <loop.judgeVotes + 2>` |
| a value of order consistency or retest agreement that counts is below 0.8, a kappa that counts is below 0.6, a value of sensitivity that counts is below 0.8, or a value of human agreement that counts is below 0.6 | `set loop.judgePanel to judges that mix models and efforts of the agent CLIs that are logged in` |

The tool writes the judge results to `records/calibration/<unix ms>/judge-<pair>-<k>.md` and the report to `records/calibration/<unix ms>.md`, and commits them on main. `<pair>` is the name of the pair, and `<k>` is the order of the judge in its pair from 1. The judge inputs, the telemetry comparisons and the captures go to `builds/calibration/<unix ms>/`. The report has the headings below in this order.

| heading | contents |
|---|---|
| `## rates` | The lines `- false win rate: <value>`, `- order consistency: <value name> <value> <kappa>, ...`, `- retest agreement: <value name> <value> <kappa>, ...`, `- sensitivity: <value name> <value>, ...` (one item per value, `all` first), `- human agreement: <element> <value>, ...` (one item per element of `elements`, `none` without a counted labeled pair), `- labels: <number of entries of labels.json>` |
| `## recommendations` | One line `- <recommendation line>` per recommendation, or `none` when there is none |
| `## pairs` | A table with columns `pair`, `this`, `baseline`, `status`, and one column per element of `elements`. `status` is `counted`, `not counted` or `not judged (<commit> missing)`. An element cell is `<element decision> (<this votes>/<baseline votes>)` of each judging of a counted pair, the two of a retest pair joined with `; `, and empty otherwise |
| `## judges` | A table with columns `pair`, `k`, `this side`, `status`, `agent`, `result`. One row per judge: the side of `this`, `done` or `failed`, `<agent CLI> <model> <effort>` and the judge result path |

## judge label

`ogw judge label <game>` fails when stdin or stdout is not a terminal. It takes the most recent judged pair whose commits are in the game repo and that no entry of `labels.json` has (in either order), and maps its two commits to `A` and `B` at random. It starts an instance of `A` as an instance of a step 4 judge, prints that this is `A` and that the human presses Enter after playing it, waits for Enter and stops the instance; then it does the same for `B`. Then, for each element of `## fun judgement criteria` of [`judge`](../agents/judge.md), it prints the element and its `looks at` text and asks for `a`, `b` or `s` (same) until it gets one of them, and asks for a one-line note that may be empty. It appends `{"A": "<commit>", "B": "<commit>", "answers": {"<element>": "A", "B" or "same", ...}, "note": "<note>", "at": <unix ms>}` to the JSON array of `records/calibration/labels.json` and commits it on main. It labels one pair per run. When there is no such pair, it prints that and writes nothing.

## regress

The regression suite (AGENTS.md `## terms`, [`harness-regress`](../skills/harness-regress/SKILL.md)). Each `ogw regress` command other than `ogw regress init`, `ogw regress status` and the side commands (`### side`) takes the lock `ogw-regress.lock` in the git dir of the regress repo for its whole work, so that one runs at a time, and fails at once when another holds it.

In each `ogw regress` command, a step waits only for the steps whose results it uses, and the others run together: its side commands (`### side`), its fixer agents (`ogw agent` with `ogw agent wait`) and their merges (`ogw agent merge`), its seed agents (`### seed agent`), its core upgrades (`ogw core upgrade`) and the patch applications of admission, at most harness settings `regress.parallel` at a time. The merges into one game repo run one at a time, as each writes the checkout it merges into. A performance measurement keeps the other instances of the command off the host through the performance lease, which each instance of a game with the regression mark holds (`### performance lease` of `## performance`).

### regress repo

The regress repo is the git repo at harness settings `paths.regress` on branch `main`. Only `ogw regress` writes it, and it commits each change.

| path | contents |
|---|---|
| `states.json` | `[{"state": "<state>", "game": "<source game>", "commit": "<source commit>", "settings": {"<game settings path>": <JSON value>, ...}}, ...]`, one per regression state. `settings`, which an item may lack, holds the game settings values that the state needs and its source commit lacks, which the content agent may not write (e.g. `uiCheckScreens.0.pixelRatio`) |
| `seeds/<id>/seed.json` | the seed manifest (`### seed`), which a human writes and `ogw regress expect` changes |
| `seeds/<id>/patch-<v>.diff` | the patch that makes the seeded commit from the base of core version `<v>` |
| `seeds/<id>/reference-<v>.diff` | for a seed with an oracle, the reference fix: the patch that fixes the seeded commit of `<v>` |
| `seeds/<id>/oracle/` | for a seed with an oracle, `oracle.json` and the files it names (`### oracle`) |
| `seeds/<id>/admitted-<v>.json` | the admission at `<v>` (`### admission`) |
| `seeds/<id>/rebase-<v>.md` | the result file of the last seed agent of the seed at `<v>` (`### seed agent`), for the human |
| `accepted.json` | the accepted harness: `{"commit": "<harness commit>", "agents": {"<role>": {"cli", "model", "effort"}, ...}, "run": "<unix ms>", "at": <unix ms>}`; absent before the first `ogw regress accept` |
| `records/refresh-<v>.md` | the record of `ogw regress refresh` at `<v>` |
| `records/runs/<unix ms>.md` | the report of a run (`### regress report`) |
| `records/runs/<unix ms>/` | `run.json`, which holds every result of the run that the report shows, the check files of the run, and `<seed-run>.diff` per seed-run: the diff from its seeded commit to its final commit |

- `ogw regress init` fails when `paths.regress` exists. Otherwise it makes the regress repo with `seeds/` copied from `regress/seeds/` of the harness repo, makes each regression state of `regress/states.json` of the harness repo (`### regression state`) with its `settings`, and commits. The seeds of `regress/` are the first seeds; later seeds are added and replaced in the regress repo with `ogw regress seed`
- `ogw regress status` changes nothing. It prints the regress repo, the core version of the harness, per state its `base-<v>` tag at that version or `none`, per seed `admitted`, `stale (<reason>)` or `not admitted` at that version, the accepted harness or `none`, and per side of the last run its `## totals` line, or `none`
- `ogw regress accept <run>` writes the after side of run `<run>` (its commit and agent settings) as `accepted.json`. It fails for a run made with `--catch-only` and for a run that has an `unknown` side

### regression state

- `ogw regress state <state> --game <game> --commit <sha>` makes the regression state `games/ogw-regress-<state>/`: a game repo whose `main` is one root commit holding the tree of commit `<sha>` of game `<game>` without `records/loops/`, and whose `id-registry` is one root commit holding the tree of `id-registry` of that game. It installs the pre-commit hook of `ogw game init`, which in a game with the regression mark runs the harness tool of `OGW_HARNESS_ROOT` when that is set, so that the commits of a side run the hook of that side. It writes the regression mark and adds the state to `states.json`. It fails when that folder exists. The source game is only read
- `ogw regress settings <state> <path> <JSON value> [<path> <JSON value>]...` writes each pair into `settings` of the state in `states.json`, over a value of the same path, and commits. It fails for a state that `states.json` does not have and for a value that is not JSON. `ogw settings set` checks the values when `ogw regress refresh` writes them
- regression mark: the file `ogw-regress.json` in the git dir of a game repo that `ogw regress` made, `{"kind": "<state or fix>", "state": "<state>"}`. It is in the git dir and not in the tree, so the fixer does not read it with the game. `ogw loop start`, `ogw build start` and `ogw judge calibrate` fail in a game with it, `ogw instance measure` leaves such a game out, and `ogw agent --seed-run` (`## agent`) starts only in such a game
- base: the commit of a regression state tagged `base-<v>` by `ogw regress refresh`: its core version is `<v>`, and the 3 base checks of `### regress refresh` ran on it
- clean for a seed: a check is clean for a seed when no failure of it matches the seed (`### seed`) and every item of the target checks of the seed is `pass` or `fail`, or `unknown` with only failures of the flash check (`### flash check` of `## UI quality`). A failure of the base that is not the seed's (e.g. another UI quality failure) does not make it unclean, because keys are compared with the base. The flash check is `unknown` until the core of a state has a frame step, and it makes a UI quality check without a failure of its own `unknown`; without the flash exception no UI quality seed could be admitted or confirmed fixed
- fix repo: the game repo `games/ogw-regress-fix-<k>/` that `ogw regress run` makes for seed-run `<k>` (`### seed-run`) from the seeded commit of its seed, the same way as a regression state from a source commit, with the regression mark of kind `fix`. The fixer of that seed-run works in it. It holds neither the base nor the patch, so the history the fixer reads does not show the seed

### seed

`seed.json` has the fields below.

| field | contents |
|---|---|
| `state` | the regression state the seed is put into |
| `class` | the defect class it stands for, e.g. `K1` |
| `element` | the completeness element or check it tests |
| `expect` | `caught` when a target check is to catch it, `missed` when no check is known to catch it |
| `match` | for `caught`: `[{"check": "<check name>", "where": "<regex>", "message": "<regex>"}, ...]`. The target checks of the seed are their `check` names; a seed without `match` has none |
| `performance` | `true` when the checks of its seeded commit and its seed-runs include `performance` |
| `fixer` | `content`, `translation`, or `none` for a seed that only the catch measures |
| `row` | `id`, `severity`, `owner`, `why` and `source` of its defect, and for a seed that no check catches also `where`, `what` and `evidence` |
| `frozen` | the path globs of the game repo that its fixer must not change, besides `records/setup/**` and `brief.md` |
| `frozenColumns` | `[{"file": "<data table>", "columns": ["<glob>", ...]}, ...]`: the columns of a table, by the names of its last header row, whose cells its fixer must not change in any row (e.g. the `sim_*` targets of row simulation) |
| `oracle` | `true` when its oracle (`oracle/`) decides whether it is fixed |
| `regenerate` | `true` when `ogw data <state>` runs after its patch is applied |
| `reference` | where it comes from (e.g. the historic fix commit it reverses), for the human |

- finding key: of a `<failure>` of a check whose `result` is `fail`, `<check name>|<platform or ->|<where>|<message>` with `:<line>` and `:<line>:<column>` removed from the end of `where` and each run of digits in `message` replaced with `#`; for a UI quality failure to which `ogw loop findings` gives an `id` (`## loop findings`), `<check name>|<platform>|<id>`. Keys compare two check files of the same side tool
- A failure matches the seed when its check is the `check` of a `match` item and its `where` and `message` match the regexes of that item
- catch: of a seed by a side, from the check of the base and the check of the seeded commit made by its side tool. For `expect` `caught`: `caught` when a failure of the seeded check matches and none of the base check matches; else `missed` when every item of the target checks of the seeded check is `pass`, `fail`, or `unknown` with only failures of the flash check; else `unknown` with the message of the first failure of the first `unknown` item. For `expect` `missed`: `caught` when the seeded check has a key that the base check has not, `missed` otherwise; a check that starts to catch such a seed is an improvement
- collateral: the keys of the seeded check that the base check has not, without those of failures that match the seed
- pipeline: of a `caught` seed with `match`, the finding that `ogw loop findings` makes of the first matching failure: `pass` when each of `id`, `severity` and `owner` that it fills is the value of `row`, `fail` otherwise, and `none` when it fills none of them or the check is `no placeholder`, of which it makes no finding

### oracle

`oracle/oracle.json` is `{"probe": "<TypeScript file in oracle/>", "languages": ["<language tag>", ...], "fixture": "<save fixture file in oracle/>"}`, `fixture` optional. The default export of the probe is `async (probe) => ({ "result": "pass" | "fail", "reason": "<why>" })`, where `probe.language` is the language of the call and `probe.command(<name>, ...<arguments>)` sends an automation command to the client `main` as `ogw command` sends it and gives `{"ok", "result"}`.

`ogw regress probe` (`### side`) starts an instance of the commit, with that save fixture when there is one, and a client that draws the screen, and for each language sends `set_language` through the runner, which restarts the client until `boot_stage` is `Done`, and calls the probe. The probe reaches the screen it measures with commands, since the restart leaves the screen of the fixture. Its result is `fail` when a call gives `fail`, `pass` when every call gives `pass`, and `unknown` with the reason when the instance does not start or the probe throws.

### admission

`ogw regress refresh` and `ogw regress seed` admit a seed at the core version of the harness `<v>` on the base `base-<v>` of its state:

1. Base: each of the 3 base checks of the base, made with the check inputs of the harness repo HEAD (`### regress refresh`), is clean for the seed. Otherwise the seed is stale with the reason `base fails target: ` and, of the first base check that is not clean for it, its first failure that matches the seed as `<check> <where> <message>`, or the target check without a result as `<check>: <why>`
2. Apply: in a worktree of the base on branch `seed/<id>-<v>`, `git apply -3` the `patch-<u>.diff` with the highest `<u>` not above `<v>`; with `regenerate`, run `ogw data <state>`; commit. This commit is the seeded commit. With `oracle`, apply `reference-<u>.diff` on the seeded commit the same way on branch `reference/<id>-<v>`: the reference commit
3. Catch: 3 checks (`ogw regress check` of `### side`) of the seeded commit, of the target checks for `expect` `caught` and of every check for `expect` `missed`, each with performance when the seed has `performance`, written with the probe results of 4 to the admission folder `<dataDir>/regress/admit-<v>/<id>/` (`### regress run`). With each of the 3 base checks of the refresh, each catch is the `expect` of the seed
4. Oracle: with `oracle`, the probe of the seeded commit is `fail` and that of the reference commit is `pass`
5. Admitted: `patch-<v>.diff` (with `oracle`, also `reference-<v>.diff`) is written as the binary diff from the base to the seeded commit (from the seeded to the reference commit), and `admitted-<v>.json` is `{"result": "admitted", "base": "<sha>", "seeded": "<sha>", "reference": "<sha>" or null, "catch": ["<catch>", ...], "oracle": {"seeded": "<result>", "reference": "<result>"} or null, "reason": null, "added": [[{"check", "platform", "where", "message"}, ...], ...] or null, "at": <unix ms>}`. `added` is, for a seed with `expect` `missed` that step 3 checked, per check of step 3, the failures of its `fail` items whose finding key none of the 3 base checks has (none for a check that did not run), and `null` otherwise: what `ogw regress expect` makes `match` of. A seed that fails a step is `stale`: `admitted-<v>.json` has `"result": "stale"` and the `reason` `patch does not apply`, `base fails target`, `not <expect>` or `oracle`, followed by `: <detail>`. The detail of `not <expect>` is the catches of the 3 checks joined with `, `, each `unknown` one followed by ` (<why>)`: the error of a check that did not run, or the reason of the catch

A stale seed is `unknown` in every run at `<v>` until a human gives a new patch with `ogw regress seed` or the seed agent of a refresh rebases it (`### seed agent`).

### regress refresh

`ogw regress refresh --background` brings each regression state to the core version of the harness `<v>` and admits each of its seeds there. The states are refreshed together (`## regress`); for each state without the tag `base-<v>`:

1. When the core version of `main` is below `<v>`: the values of `settings` of the state are written to the game settings of `main` with `ogw settings set`, as the lead agent writes them, and committed as a commit without the hook (`## pre-commit hook`). When that write fails, or when `ogw settings list game <state> --missing` then gives a path whose `x-owner` is not `content`, a value that the content agent may not write, the state is not refreshed and nothing else of this step runs; the record names the reason or the paths. Otherwise `ogw core upgrade <state> --version <v>`, then one content agent on `main` with the seed-run records `records/loops/refresh-<v>-<unix ms>/`, whose content input (`### seed-run` 1) has in `## request` the iteration 1 items of `## agent` for a raised core version and in `## defects` `none`. When the agent does not end `done`, the state is not refreshed
2. Translations, also for a state that step 1 did not upgrade: when `main` has missing or stale translations (`translation_missing` and `translation_stale` failures of `no placeholder`), one translation sub-agent per language that has them, with the seed-run records of step 1 (made here when step 1 ran no content agent): the tool writes `translation-input-<language>-<unix ms>.md` holding the language in the seed-run records for each of them and commits them, then runs per language `ogw agent translation --game <state> --input <that file> --seed-run <records>:1 --background`, `ogw agent wait` and `ogw agent merge <id>`, as `### seed-run` 2 runs a translation fixer. When an agent does not end `done` or its merge fails, the state is not refreshed
3. Base checks: 3 checks of every check of `main`, with performance; the keys of the base failures are written to the record. The check files stay in `records/refresh-<v>/<state>-base-<k>.json` of the regress repo, each with `"harness": "<harness commit>"` and `"checkInputs": "<key>"` beside the fields of `ogw regress check` (`### side`): the harness repo HEAD, whose tool made it, and the check inputs of that commit. The check inputs of a harness commit are the SHA-256 of the lines of `git ls-tree` at that commit of the harness paths that the checks of its tool read: `tools/` without `tools/ogw.md` and `tools/test/`, `schemas/`, `settings.json`, and the harness documents that check code reads: `skills/game-design/SKILL.md`, `skills/client-core/SKILL.md`, `skills/client-core/modules/qa-core.md` and `skills/build/engines/`. When one of them does not run, the state is not tagged
4. Tag `base-<v>` on `main`. A base check that is not clean for a seed makes only that seed stale (`### admission` 1)

For a state with the tag `base-<v>`, `ogw regress refresh` and `ogw regress seed` take the 3 kept base checks when each of them is of that base and its `checkInputs` are those of the harness repo HEAD, whose tool admits the seeds. Otherwise the 3 base checks of step 3 run again on that base, which keeps the tag, and their files replace the kept ones: a base check that other check code, settings or schemas made is no evidence for this one. When one of them does not run, the seeds of the state are stale as those of a state without the tag.

A state without the tag after steps 1 to 4 leaves its seeds stale with the reason `base fails target: <state> <why>`. Each seed of a tagged state is admitted (`### admission`) once the refresh of its state has ended. A seed whose admission ends stale for a reason that goes to the seed agent is rebased then (`### seed agent`). The tool writes `records/refresh-<v>.md` with `## states` (a table with columns `state`, `from`, `settings`, `upgrade`, `content job`, `translation`, `base checks`, `base failures`, `tag`; `settings` is `set` when step 1 changed game settings, `failed: <reason>`, `missing: <path>, ...`, or `none`; `translation` is `done (<job>, ...)` when each translation sub-agent of step 2 ended `done` and was merged, `<language>: <why>` for the one that did not or whose merge failed, or `none` when step 2 started none), `## seeds` (a table with columns `seed`, `result`, `reason`, `catch`, `oracle`, `rebase`, with the admission after the seed agent; `rebase` is the outcome of `### seed agent` followed by ` (<job>)` and, when it has one, `: <reason>`, or `none` when no seed agent ran) and `## cost` (`## cost` of `## loop record` over the content agents, translation sub-agents and seed agents of the refresh, the row `seed` after the others), and commits.

`ogw regress seed <folder> --background` copies the folder into `seeds/<name of the folder>/` of the regress repo, removes `admitted-<v>.json` there, and admits the seed at `<v>`. It fails when the state of the seed has no `base-<v>`.

`ogw regress expect <seed> caught --background` makes a seed with `expect` `missed` whose admission at `<v>` is stale with the catch `caught` in each of its 3 checks into a seed with `expect` `caught`: a check now catches a seed that no check was known to catch. The lead agent of `regress harness` runs it on the human's yes, without reading the seed. From `added` of that admission, the target checks are the checks that have a failure in each of its 3 lists, and `match` has one item per failure of those checks in the lists, each item once: `check` its check name, `where` the regex of its `where` with any `:<line>` or `:<line>:<column>` at the end, and `message` the regex of its message with any run of digits in place of each run of digits, as finding keys compare them. It writes `seed.json` with that `expect` and `match` and every other field as it was, removes `admitted-<v>.json`, admits the seed at `<v>` as `ogw regress seed` does, commits, and prints the target checks and the admission. It fails for another seed, when the admission has no `added`, when no check has a failure in each list, and when the state of the seed has no `base-<v>`.

### seed agent

The seed agent ([`seed`](../agents/seed.md)) rebases a seed onto the base of its state: it writes a new patch, for a seed with `oracle` a new reference fix and, when the probe no longer reaches its screen, a new probe, that plant the defect the manifest describes, and nothing else. `ogw regress refresh`, and no other command, starts one for each seed whose admission at `<v>` is stale with a reason that starts with `patch does not apply` or `oracle`, as soon as that admission ends: not for `not <expect>`, a change of the catch of the checks of the harness, which goes to the human, and not for `base fails target`, a problem of the base. Each seed agent is one piece of work of the refresh (`## regress`), so the seed agents of different seeds run together, with the other work at most harness settings `regress.parallel` at a time. A seed agent holds no performance lease (`### performance lease` of `## performance`): it starts no instance and runs no `ogw`, and its agent CLI and git commands are lighter work than the static checks and regression tests that run beside a measurement.

1. Folder: the tool makes the folder of the agent (`## temp folder`) and in it `seed/`, a copy of `seeds/<id>/` without the files that the tool writes there (`admitted-*.json`, `rebase-*.md`); `base/`, a new git repo whose branch `base` is the tag `base-<v>` of the state fetched with its history and no other ref, so that no branch of another seed is in it, with no remote and a git identity of its own; and `input.md` with `## seed` (`<id>`), `## core version` (`<v>`), `## stale reason` (the reason of the admission), `## old patch` and `## old reference` (the name of the `patch-<u>.diff` and, for a seed with `oracle`, of the `reference-<u>.diff` that admission 2 applies, or `none`), and `## core release` (the folder of `<v>` in `open-game-works-core-releases/`, or `none` when it is not there)
2. Agent: `ogw agent` runs the seed agent in that folder with that input (`## agent`), and the refresh waits for it. A seed whose folder could not be made, whose job could not start, or whose job did not end `done` is `failed`, with the error or the `failed:` line of the job
3. Take: a result file whose `## result` is `not rebased` is `not rebased`. For `rebased`, the tool compares `seed/` with `seeds/<id>/`, leaving out of both the files that the tool writes there. They may differ only in `patch-<v>.diff`, and for a seed with `oracle` in `reference-<v>.diff` and the probe file that `oracle/oracle.json` names; `patch-<v>.diff`, and with `oracle` `reference-<v>.diff`, must be in `seed/`; and each entry of `seed/` must be a file or a folder. Otherwise the result is `refused`, with the paths: a changed `seed.json` among them
4. Admit: the tool writes the result file as `seeds/<id>/rebase-<v>.md`. For `rebased`, it puts those files into `seeds/<id>/` and admits the seed at `<v>` (`### admission`). When it is admitted, the outcome is `rebased`. Otherwise the files are put back as they were and `admitted-<v>.json` keeps the admission before the rebase: `not admitted`, with the reason of the admission of the rebase
5. End: the tool removes the folder, the folder of Claude Code for it under `/tmp/claude-<uid>/` (`## agent`), and, once it has read them, the `<id>.cli.log`, `<id>.stdout` and `<id>.stderr` of the job in `agent-logs/`: they hold the seed. The job record keeps the `usage` that `## cost` sums

### side

- side: a harness commit with agent settings. The before side is `--before <commit>`, by default the `commit` of `accepted.json` with its `agents`; the after side is `--after <commit>`, by default the harness repo HEAD, which must have no uncommitted changes. `--before-agent` and `--after-agent` `<role>=<cli>/<model>/<effort>` replace harness settings `agents.<role>` of that side; without them, the after side runs with harness settings `agents`
- side worktree: `worktrees/_harness/<id>/`, a worktree of the harness repo at the commit of the side, one per side, removed when the run ends. Its `tools/node_modules` is a link to `tools/node_modules` of the harness repo when its `tools/package.json` and `tools/package-lock.json` are those of the harness repo, and `npm ci` installs it otherwise. Its `settings.local.json` is that of the harness repo with the agent settings of the side as `agents`
- side tool: `tools/src/cli.ts` of the side worktree, run with `OGW_HARNESS_ROOT` set to the side worktree and `OGW_WORKSPACE_ROOT` to the workspace root, so that it reads its own settings, schemas, prompts and check code and works on the games, worktrees and jobs folder of this workspace. Each step of a side runs with its side tool: its checks, its fixers (`ogw agent`, `ogw agent wait`, `ogw agent merge`) and the pre-commit hooks of their commits. Only the confirmations of seed-runs run with the side tool of the after side, so that a stricter check of the after side does not look like worse fixing of the before side; `own fixed` gives the before side's own check beside it
- A side is `unknown`, with the reason, when its worktree or its `npm ci` fails, when its side tool does not run `ogw regress side` (a harness commit from before the regression suite), or when its settings do not load. The two sides must have the same harness core version (AGENTS.md `## repo`); otherwise `ogw regress run` fails before any check and names the `core-v<version>` tags of both
- side commands: the commands that `ogw regress run` and `ogw regress refresh` run with a side tool (`ogw regress refresh` with the harness repo itself). They print JSON and change no repo but the game worktrees they make and remove
  - `ogw regress side`: `{"commit": "<harness commit>", "coreVersion": "<version>", "promptBytes": {"content": <bytes>, "translation": <bytes>}, "agents": <harness settings agents of the side>, "instanceLease": true}`; `instanceLease` says that the instances of games with the regression mark that its tool starts hold the performance lease (`### performance lease`). `ogw regress accept` keeps the `agents` of the after side, so that the accepted harness runs with the same agent settings when the local settings change. The prompt bytes of a role are the UTF-8 bytes of its prompt (`## agent`) with empty `input` and `output`, plus those of each harness file that a link of that prompt points to, each file once
  - `ogw regress check <game> --commit <sha> --out <file> [--check <check name>...] [--performance] [--proof <records>:<n>]`: in a worktree of that commit under `worktrees/<game>/`, the checks of `ogw check --loop` of a completeness iteration, only those of `--check` when it is given, and `performance` only with `--performance`; with `--proof`, also the fix test proof (`### fix test proof` of `## check`) of iteration `<n>` of the seed-run records `records/loops/<records>/`. It writes `{"commit": "<sha>", "checks": [<check>, ...], "fixTestProof": [<proof>, ...]}` to `<file>` and the evidence to the folder of `<file>` without `.json`, and removes the worktree
  - `ogw regress probe <game> --commit <sha> --oracle <folder> --out <file>`: the oracle of `<folder>` (`### oracle`) on that commit, written to `<file>` as `{"result": "<pass, fail or unknown>", "reason": "<why>" or null}`

### regress run

`ogw regress run [--before <commit>] [--after <commit>] [--before-agent <role>=<cli>/<model>/<effort>]... [--after-agent <role>=<cli>/<model>/<effort>]... [--repeats <n>] [--seeds <id>...] [--catch-only] --background` compares the two sides. `--repeats` is the seed-runs per seed and side, harness settings `regress.repeats` by default, and `--seeds` limits the seeds. A seed that is not admitted at the core version of the sides is `unknown` with the reason of its admission, or `not admitted`. Without `accepted.json` and `--before`, it fails.

1. Sides: makes both sides. With an `unknown` side, the report has only `## sides` and `## unknown`, and the run ends with exit code 1
2. Catch, per side: the check of the base of each state of the seeds, with performance, and the check of each seeded commit, with performance when the seed has `performance`, each written under `<dataDir>/regress/<unix ms>/catch/<side>/` (`<dataDir>` is `.ogw/` of the workspace root), which the fixers can read and which holds no seed. A catch that is not the `expect` of the seed, and an `unknown` catch, is checked once more with its seeded check, and the second counts. The two sides run together, and a catch waits for the check of the base of its state
3. With `--catch-only`, the report follows. Otherwise the seed-runs are `--repeats` per side of each seed whose `fixer` is not `none` and whose catch by the after side is not `unknown`, in the order repeat by repeat, seed by seed, the two sides of a repeat next to each other, the before side first in an odd repeat and the after side first in an even one; `<k>` of a seed-run is its place in that order. Before any fixer starts, the tool makes the folders `ogw-regress-fix-<k>/` of each seed-run under harness settings `paths.games` and `paths.worktrees`, so that the sandbox of each fixer, which takes its list of games when it starts, blocks the fix repos of the other seed-runs (`## agent`)
4. Fix: each seed-run makes its fix repo in its folder when it starts and removes both folders when it ends. The seed-runs start in their order, at most harness settings `regress.parallel` at a time, so that the two sides of a repeat run at the same time and a drift of host load or of rate limits between repeats favours neither side
5. End: removes the folders of the fix repos and the side worktrees, writes `records/runs/<unix ms>/` and the report `records/runs/<unix ms>.md`, commits them, and prints the report path and the lines of `## difference`

When the `ogw regress side` of a side has no `instanceLease`, the instances of its tool keep no other instance off a measurement: then a check of step 2 with performance runs while no other check of step 2 runs (it starts once the checks running have ended, and a check that comes while it waits starts after it), and the seed-runs of the seeds with `performance` start after every other seed-run has ended, one at a time.

### seed-run

seed-run: the work of one side on one seed once, in its fix repo on `main`, with the seed-run records `records/loops/regress-<unix ms>-<k>/` of the fix repo (`<unix ms>` of the run, `<k>` the order of the seed-run in the run). Its iteration n, from 1 to at most harness settings `loopStop.repeatedDefect`:

1. Input: the tool writes in the seed-run records the defect list `defects.json` (`## loop record`) and the content input `content-input-<n>.md` in the format of `ogw loop input` for a completeness iteration, and commits them. `## request` is `none`, `## previous record` is the path of `iteration-<n − 1>.md` or `none`, and `## defects` holds the seed's defect when it is `open`, `reopened` or `awaiting confirmation`. Its `id`, `severity`, `owner`, `why` and `source` are those of `row`, and its `where`, `what` and `evidence` are those of the first matching failure in the last check of the after side that found it (the catch in iteration 1), or those of `row` when no check found it; the evidence paths are outside the regress repo. In iteration 1 its status is `open`. A translation fixer gets instead `translation-input-<language>-<unix ms>.md` holding the language, one per language of the `translation_missing` and `translation_stale` failures of the after side's seeded check
2. Fixer: `ogw agent content --game <fix repo> --input <content input> --seed-run regress-<unix ms>-<k>:<n> --background` and `ogw agent wait` with the side tool; for a translation fixer, `ogw agent translation` the same way and then `ogw agent merge <id>` with the side tool. A fixer that does not end `done`, or a merge that fails, makes the seed-run `unknown` with the reason
3. Confirmation, with the side tool of the after side on the HEAD of `main`, written under `<dataDir>/regress/<unix ms>/fix/<seed-run>/`: `ogw regress check` of the target checks (the regression test for a seed without target checks) with `--proof regress-<unix ms>-<k>:<n>` and, with `oracle`, `ogw regress probe`. When a target check item or the probe is `unknown` (beside the flash exception of clean), they run once more and the second counts
4. Status: the tool changes the status of the seed's defect as `## loop record` does, with the content agent report and the fix test proof of this iteration, and with this confirmation in place of the findings and play answers: the defect is found when a failure of the confirmation matches it, or for a seed with `oracle` when the probe is `fail`; and the confirmation gives a result when the confirmation check is clean for the seed or has a matching failure, and with `oracle` when the probe is `pass` or `fail`. A translation fixer writes no content agent report: its defect becomes `awaiting confirmation` when the merge is done
5. Record: the tool writes `iteration-<n>.md` with `## commit` (the lines `- instance: <HEAD>`, `- side: <before or after> <side commit>`, `- kind: completeness`), `## checks`, `## defects`, `## fix test proof` and `## cost` in the formats of `## loop record`, and commits it
6. The seed-run ends when the defect is `fixed` or `refused`, or after the last iteration. When its last confirmation gave no result, the seed-run is `unknown`

final commit: the HEAD of `main` when the seed-run ends. On it the tool runs every check with the side tool of the after side (performance when the seed has `performance`), and for the before side the target checks and the oracle with its own side tool; it computes the guards; it writes `git diff` from the seeded commit to the final commit to `<seed-run>.diff`.

| measure | value of a seed-run | better |
|---|---|---|
| `fixed` | 1 when the defect became `fixed`, else 0 | higher |
| `iterations` | the iteration in which it became `fixed`, else `loopStop.repeatedDefect` + 1 | lower |
| `new defects` | the keys of the final check that neither the base check nor the seeded check of the after side has, without the `no placeholder` failures | lower |
| `guards` | the paths the fixer changed that match `frozen`, `records/setup/**` or `brief.md`; the cells of `frozenColumns` that changed; the test files under `client/tests/` and `server/tests/` of the seeded commit that have fewer tests (`func test_` of GDScript, `it(` and `test(` of TypeScript) on the final commit; for a translation fixer, the rows of `data/translations/<language>.csv` whose `text` changed and that were neither missing nor stale on the seeded commit | lower |
| `unconfirmed claims` | the iterations whose content agent report says `fixed` for the defect and whose confirmation found it | lower |
| `test first` | the fix test proof of the last iteration whose report says `fixed`: 1 for `pass`, 0 for `fail`, no value for `unknown` or without such an iteration | higher |
| `input tokens`, `cached tokens`, `output tokens`, `cost USD`, `turns` | the sum of that value of `usage` (`### usage` of `## agent`) over the fixer jobs; no value when a job has none | lower |
| `agent minutes` | the sum over the fixer jobs of the time from their start to their end | lower |
| `check minutes` | the sum of the time of the confirmations and the final check | lower |
| `placeholders` | the `no placeholder` failures of the final check that the seeded check has not: the resource and translation work made | none |
| `own fixed` | for the before side, 1 when its own target checks and oracle on the final commit do not find the defect and give a result, 0 when they find it, no value otherwise | none |

### regress comparison

- A seed-run counts for a measure when it is not `unknown` and has a value of the measure. A seed counts for a measure when each side has at least 2 seed-runs that count
- transformed value: ln(1 + value) for `input tokens`, `cached tokens`, `output tokens`, `cost USD`, `turns`, `agent minutes` and `check minutes`, whose differences are ratios; the value for the other measures
- difference D: the mean over the seeds that count of the mean of the after side minus the mean of the before side of the transformed values
- permutation test: for each of harness settings `regress.permutations` permutations, the side labels of the seed-runs that count are shuffled within each seed that counts, with the count of each side kept, and D is computed again. p is (1 + the number of permutations whose |D| is at least the |D| of the run) ÷ (1 + `regress.permutations`). The shuffles take the PRNG mulberry32 with the `<unix ms>` of the run as its random seed, so the same results give the same p
- verdict of a measure: `better` when p is below harness settings `regress.level` and D goes the way the measure is better, `worse` when p is below `regress.level` and D goes the other way, `no difference` otherwise, and `unknown` when no seed counts. A measure whose better is `none` gets no verdict
- A comparison of a side with itself (the same commit and agent settings) measures the spread: each of its `better` and `worse` is a false difference, which happens for about `regress.level` of the measures

### regress report

`records/runs/<unix ms>.md` has the headings below in this order. A heading without content is `none`.

| heading | contents |
|---|---|
| `## sides` | A table with columns `side`, `commit`, `core version`, `content agent`, `translation agent`, `content prompt bytes`, `translation prompt bytes`: per side that is not `unknown`, `<cli> <model> <effort>` of the two roles; then the line `- <side>: unknown (<reason>)` per `unknown` side |
| `## catch` | A table with columns `seed`, `state`, `expect`, `before`, `after`, `collateral before`, `collateral after`: per admitted seed, the catch of each side followed by ` (pipeline <pipeline>)` for a `caught` seed with `match`, and the collateral keys of each side joined with `, ` |
| `## fix` | A table with columns `seed`, `side`, `repeat`, `result`, and one column per measure: per seed-run, `fixed`, `not fixed` or `unknown (<reason>)`, and the values, `none` for no value |
| `## totals` | One line per side: `- <side>: <seed-runs> seed-runs, <fixed> fixed, <unknown> unknown, input tokens <sum>, cost USD <sum with two decimals>, agent minutes <sum>, check minutes <sum>` |
| `## difference` | One line per measure with a better, in the order of the measure table: `- <measure>: before <mean>, after <mean>, D <D>, p <p>, <verdict> (<number of seeds that count> seeds)`, with ` ratio <e^D>` after D for the ln measures; then per seed whose catch differs between the sides `- catch <seed>: before <catch>, after <catch>`, or `- catch: same` |
| `## unknown` | The `unknown` sides, the seeds not admitted with their reasons, the `unknown` catches and the `unknown` seed-runs, each with its reason |

The means of `## difference` are those of the values, not of the transformed values, over the seed-runs that count.

## runner

The behavior of `ogw instance start`.

- main client: the client of an instance that is not a bot client. Its name on the control channel is `main`
- For each instance, a supervisor process handles the server process, the clients and the bot loops and opens a loopback HTTP control channel. The control channel accepts two tokens. The full control token accepts every request. The play token accepts only the requests below and refuses the rest: built-in commands with the input mark sent to the main client, `capture_screen`, `capture_video`, `extract_logs`, `get_telemetry`, `get_state`, `get_anchor` (for `click_anchor` of `ogw input`), `set_step_mode`, `step`; `get_state`, `set_step_mode`, `leave_match`, `step` sent to bot clients; pausing the bot loops, resuming them, and marking that time is advancing. For requests that come with the play token, the supervisor writes no files. The frames of `capture_video` are written by the calling process
- The instance record (full control token, admin secret, dev access value) and the instance folder (DB, logs, secret files) are kept in `ogw-instances/` (the instance record folder) under the git common dir of the harness repo, and the play access file that holds the play token and the control channel port is kept in `ogw-instance-play-access/`. `ogw input`, `ogw capture`, `ogw log`, `ogw telemetry`, `ogw step-mode` and `ogw step` use the play token; other commands use the full control token
- `--platform`: passes the launch value `OGW_PLATFORM` and the renderer of that platform to the client
- `--input-latency <ms>`: only `ogw judge calibrate` uses it, for the degraded pairs of the degradation `latency`. The supervisor delays each built-in command with the input mark sent to the main client (`ogw input`, a timed input script, a bot run of the scenario). When `step_mode` of the `get_state` of the main client is not `true`, it answers `ok` at once and sends the command `<ms>` after it got it, in the order it got the commands, so the delays of commands sent one after another do not add up. When it is `true`, it answers `ok` at once and holds the command until the `step` commands sent to the main client after it have advanced game time by `<ms>`: the `step` during which that happens is sent as a `step` up to that point, the held command and a `step` for the rest, and its answer is that of the last part sent, or of the first part that failed. When `set_step_mode` turns step mode of the main client off, the held commands are sent in order, each once the rest of its `<ms>` has passed. The play access file holds `<ms>`, and the play commands add it to the time limit of their requests
- `--network-delay <ms>`: only `ogw judge calibrate` uses it, for the degraded pairs of the degradation `network`. Each time the automation channel of the main client connects (its first boot and each restart), the supervisor sends it `set_network_delay <ms>` of `QACore`, so that the client takes each server response as received `<ms>` after it arrived. When the answer to the first one is not `ok`, the instance start fails; the answer to a later one that is not `ok` goes to `runner.log` of the instance folder
- `--feedback-off` and `--reward-presentation-off`: only `ogw judge calibrate` uses them, for the degraded pairs of the degradations `feedback` and `reward`. Each time the automation channel of the main client connects (its first boot and each restart), the supervisor sends it `set_feedback_off on` or `set_reward_presentation_off on` of `QACore` (`### feedback switch` of [`qa-core`](../skills/client-core/modules/qa-core.md)), both when both are given, before any other command of that connection. Their answers are taken as those of `set_network_delay` of `--network-delay`
- flash recording and test screen: only the flash check of `## UI quality` uses them (`ogw video` records as `## video` says). The client `main` starts with `--resolution <width>x<height> --write-movie <folder>/frame.png --fixed-fps <targetFps>`, the window size being the CSS size of the recorded screen, so that the movie maker writes `frame<8-digit frame number from 0>.png` per frame (the engine keeps the window within the display). Each time the automation channel of the client `main` connects (its first boot and each restart), the supervisor sends it `set_test_screen`(`window`, `fillMode`) and `set_virtual_notch`(`notch`) of the recorded screen after the commands of `--feedback-off`, `--reward-presentation-off` and `--network-delay`. Their answers are taken as those of `set_network_delay` of `--network-delay`
- `--fixture`: when the `boot_stage` of the client becomes `Done`, calls the steps of the file in order, and returns when it becomes `Done` again after `restart`
- server process: starts `node core/start.ts <server start arguments>` with the `node` that runs `ogw`, with `server/` of the instance checkout as cwd. The server start arguments are, per `## server start` of [`server-core`](../skills/server-core/SKILL.md), `--env LOCAL`, `--port <free loopback port>`, `--db <SQLite file or postgresql>`, `--secret-file <server secret file>`. The server secret file holds `accessTokenKey`, `updateSigningKey`, `iapAccountToken`, `devAccess`, `adminSecret.ogw` and, with `--db postgresql`, the connection string `db` of the PostgreSQL container. The values are made new for each instance. The server has started when it answers `GET /update/deploy_list.json` over HTTP
- The dev access value of the instance is passed to every client of that instance (opponent bot clients and the social bot client included) as the launch value `OGW_DEV_ACCESS`
- The runner does not put secret values (the values of the server secret file (the PostgreSQL connection string included), the launch values `OGW_DEV_ACCESS` and `OGW_AUTOMATION_TOKEN`) in the environment variables of a process either (`## secret in command line`). It writes them to a new file in the instance folder that only the owner reads and writes (0600) and gives the process only that path: the server secret file for the server process, the server secret file for the populate process, and for clients a launch value file per client that holds all its launch values (the engine-specific implementation rules of [`client-core`](../skills/client-core/SKILL.md))
- An instance of a realtime game starts the server process with `--matchmaker`
- When `server/dev/populate.ts` exists, `## populate` of [`server-content`](../skills/server-content/SKILL.md) is called after the server process starts and before the clients start: a `node` process with `server/` of the instance checkout as cwd calls `populate(await connect_server(<server URL>, <absolute path of server/build/data/>, <dev access value>))`. `connect_server` is imported from `server/core/testing/dev/index.ts` and `populate` from `server/dev/populate.ts`. When the process ends with a nonzero code, the instance start fails
- An instance that `ogw loop evaluate` starts without `--fixture` to pass to the play agent and the judge agent does not pass the launch value `OGW_DEV_ACCOUNT` to the main client. That client goes through the `AuthCore` `boot_login` (terms, new account login, auto login) with `ogw-secure-storage` of the host OS. Other instances pass the dev account `main` as the launch value `OGW_DEV_ACCOUNT` to the main client (a client the runner does not start included). That client logs in with the `AuthCore` `dev_login`, so it does not open the terms popup
- `instance start` ends when all clients the runner started are ready. A client with a dev account is ready when its `boot_stage` becomes `Done`; a client without a dev account is ready when its automation channel connects
- An instance of a realtime game (bot playtest instances included) starts `min_players` − 1 opponent bot clients per row of `data/tables/match_mode.csv`. Each opponent bot client gets a different dev account `opponent_<n>` (`n` from 1) as the launch value `OGW_DEV_ACCOUNT`
- When the `boot_stage` of an opponent bot client becomes `Done`, the content command whose name ends with `.opponent_step` is looked up in `list_commands`. When there is not exactly one, the instance start fails. When it is found, until the instance is shut down, that command is called with the ID name of the row that opponent bot client is assigned to and the returned input command is put into that opponent bot client, repeatedly
- When `match_mode` has a mode that can open a room of `matchmaker`, the content command whose name ends with `.opponent_join_room` is also looked up when `.opponent_step` is looked up. When there is not exactly one, the instance start fails. After that, each time `room_code` in `get_state` of the main client changes from the empty string to another value, `.opponent_join_room` is called once with that `room_code`, between `.opponent_step` calls, for k of the opponent bot clients assigned to the row whose ID name is `room_mode` of that `get_state`, in ascending order of `n`. k is the number of opponent bot clients assigned to that row when the `allow_room` of that row is `true`, and when it is `false`, the smaller of that number and the `max_party_size` − 1 of that row. An opponent bot client for which `.opponent_join_room` was not called enters the queue alone through `.opponent_step`
- When the modules the game uses (`## module` of the `core` skill) include any of `friend`, `guild`, `chat`, one social bot client is started and gets the dev account `social` as the launch value `OGW_DEV_ACCOUNT`
- When the `boot_stage` of the social bot client is `Done` and `user_id` in `get_state` of the main client is not 0, the content command whose name ends with `.social_step` is looked up in `list_commands`. When there is not exactly one, the instance start fails. When it is found, until the instance is shut down, that command is called repeatedly with the decimal string of that `user_id`
- While the step mode of the instance is on, `.opponent_step` and `.social_step` are called only while `ogw step` advances time, and not while `ogw step-mode` has paused it
- Before it starts a client for the first time in each checkout, the runner runs `godot --headless --path client --import` once. It is the first time when the checkout has no `client/.godot/`. When the import fails, the runner deletes `client/.godot/` and the instance start fails
- import cache: the import of a `--commit` checkout is kept in `ogw-import-cache/` of the git common dir of the game repo under its key, the SHA-256 of the engine executable path and of every file Godot reads in the checkout: each file under `client/` and `resource/` but `client/.godot/`, by path and content, and a symbolic link by its target text (with the content of its target when that is outside those folders). An entry holds `client/.godot/` and the files outside it that the import added, changed or removed (the `.uid` files it made, the `.import` files it wrote). A `--commit` checkout whose key has an entry gets a copy of the entry (an APFS clone where the volume allows) in place of the import: it then has the files of the checkout the entry was made from, and Godot imports none of them again. A checkout whose files differ from those of the entry has another key. The starts of one key take the lock of that key, so that one imports while the others wait for its entry. The cache keeps the `maxConcurrentInstances` entries used last. When a copy fails, the runner removes the entry and the copied `client/.godot/`, and the instance start fails
- The bot clients of an instance and the bot playtest are started with `--headless`. The clients of the performance check, the per-resolution capture and the play agent draw the screen
- The runner starts a client with the `rendering_method` of the instance platform (`ogw instance start --platform`) in the renderer table of `## engine settings` of [`client-content` Godot rules](../skills/client-content/engines/godot.md). The value is passed on the Godot command line as `--rendering-method`

## engine project

What the harness tool writes in the engine project of a game. The renderer table is in `## engine settings` of [`client-content` Godot rules](../skills/client-content/engines/godot.md), because content runs on it.

- The harness tool, the data tool and the contract tool set the actual path with the engine-specific implementation rules of game settings `engine`.
- The harness tool writes `client/.gitignore`, which ignores `addons/`, `android/`, `ios/plugins/` and `.godot/`. `.gitignore` of the game repo root ignores `build/`
- In `project.godot`, `rendering/rendering_device/fallback_to_opengl3` is `true`
- In `project.godot`, the harness tool writes the source text of reserved string `[app_name]` to `application/config/name`, its translation per supported language to `application/config/name_localized` (the source text for a missing translation; the key is the language `code` with `-` replaced by `_`), the file of resource `app_icon/main` to `application/config/icon`, and the file of resource `splash/main` to `application/boot_splash/image`
- The harness tool writes `display/window/handheld/orientation` of `project.godot` as `4` (sensor landscape) when the width of game settings `baseResolution` is greater than its height, otherwise as `5` (sensor portrait), and writes the width and height of `baseResolution` to `display/window/size/viewport_width` and `display/window/size/viewport_height`
- The harness tool writes `rendering/textures/vram_compression/import_s3tc_bptc` and `rendering/textures/vram_compression/import_etc2_astc` as `true`, and `editor/export/convert_text_resources_to_binary` as `false`. This is so that one set of bundle files holds the texture formats of all platforms, and `.tscn` and `.tres` of a bundle override the files with the same path in the app

## instance wait

| command | work |
|---|---|
| `ogw instance wait <instance>` | Waits until an instance of the input of the judge agent that runs it runs, and prints `ready <instance>`. The evaluation starts some instances of a judge only as the judge gives others back. It ends with exit code 75 when the instance still starts after 60 seconds, and with exit code 1 and the reason when the instance does not run: the evaluation could not start it, or the judge gave it back. It refuses an instance that is not in that input, and a caller that is not a judge agent |
| `ogw instance release <instance>` | Gives back an instance of the input of the judge agent that runs it. The evaluation stops it at its next check of that agent, so that the next agent waiting for instance slots starts sooner. It refuses an instance that is not in that input, and a caller that is not a judge agent |

## instance measure

- The targets are the benchmark game of the highest release, among the releases of harness settings `coreReleaseRepository`, that has `benchmark-<engine>.zip`, and the games in `games/` that have `client/dev/bot/scenario.json` and no regression mark (`## regress`). When there is no target, nothing is measured
- Per target, measure while varying the number of instances N. To measure N, start N instances that render the screen together, run that scenario in each instance, then stop them all. The value of the target is the largest N at which every instance keeps the `fps` condition of the `## performance` judgement (the `targetFps` of the benchmark game is the `targetFps` default of the game settings schema) and no process ended abnormally. Fps is taken to fall as N grows. `maxConcurrentInstances` does not limit this measurement. When an instance fails to start while instances are being added, that N counts as not kept, and the reason is written in the result. When, while measuring 1 instance, that instance fails to start or the standard test task run together with it fails, the measurement fails and writes no result
- The first N measured is harness settings `maxConcurrentInstances` of this host, or, when there is none, half the CPU count of this host (at least 1). The upper limit is harness settings `instanceMeasureLimit` of this host. Measure the next N until the largest N that kept the condition and the smallest N that did not differ by 1: when there is no N that failed yet, the value + 1 when the N that kept it is `maxConcurrentInstances`, otherwise double the N that kept it (up to the upper limit); when there is no N that kept it yet, half the N that failed; otherwise the middle of the two N (rounded down)
- It measures while running together one standard test task: the one with the largest peak memory among the `local-model` method stages that are `ok` in the result of `ogw generation measure`

## env benchmark

`ogw env benchmark` measures the benchmark index of this host and writes it to its result file.

- benchmark index: the Lighthouse `BenchmarkIndex` of a browser page, the mean of two scores measured one after the other in that page. The first score builds a string of 10000 characters one character at a time, again and again for at least 500 ms. The second copies an array of 100000 integers into a second array and back, one copy after another, until at least 10 copies and at least 500 ms are done, reading the clock every 10th copy. Each score is the number of strings or copies divided by 10 and by the seconds taken, rounded
- It opens `about:blank` in the headless browser of harness settings `tools.chromium` without CPU throttle and measures the benchmark index in that page five times in a row. The benchmark index of this host is the median of the five. When `tools.chromium` is not on this host, it measures nothing and fails, naming that program
- The result file holds the five values, the median and the time of the measurement

## generation install

- install folder: the folder `.ogw/generation/<method>/<install key>/` of the workspace root, taken by its real path (symbolic links resolved), that holds the install of a method and the work files of its calls (`## generation call`). `<install key>` is the first 16 hex digits of the SHA-256 of the JSON `{"pins":<pins>,"ffmpeg":<ffmpeg>}`, where `<pins>` is the `pins` of the method in harness settings with the `sha256` of each hf pin left out and `<ffmpeg>` is, for a method with `provider`, the real path of the `tools.ffmpeg` program that its `cli` puts on PATH, and `null` for other methods. A method is installed when its install folder holds `installed.json`, which the install writes last, and the `sha256` of each hf pin that has one equals the SHA-256 of the files of that pin that the install got. When it holds an `installed.json` whose SHA-256 of an hf pin differs from the `sha256` of that pin, the install of that method fails, naming both values, and changes nothing in that folder. A checkout of the harness installs into and calls from only the install folders of the install keys its harness settings give, so an install from a checkout with other pins or another `tools.ffmpeg` program never changes or removes an install folder that another checkout of the harness on this host uses. The paths that `installed.json` holds are inside the install folder by its real path
- The job of `ogw generation install` records in its job record, before it installs a method, the install folder of that method
- When the revision or SHA-256 of a fetched file differs from the pinned information, that method is left as failed.
- A method whose git pin has no `revision` is not fetched and is left as failed. The git pin repository of a `local-model` method is not installed, so its `pyproject.toml` `dependencies` must be in the pip pin (`pin:<method>` of `## env propose`). An hf pin with `secret` is fetched with the Hugging Face access token of that harness secret, and a method whose secret is not in the host secret store is not fetched and is left as failed. For an hf pin with `sha256`, that `sha256` is matched against the SHA-256 of the LFS file that Hugging Face publishes before the LFS files are fetched, and each fetched LFS file is matched against the published SHA-256. An hf pin without `sha256` is fetched without checking the fetched files. When a method installation fails, among the LFS files that hf pins fetched, only the files whose SHA-256 equals the SHA-256 that Hugging Face published are kept, and the method is treated as not fetched.
- When an install fetches an hf pin, each LFS file of that pin whose SHA-256 equals the SHA-256 that Hugging Face published is taken without being fetched: first from the LFS files that a failed install of the same install folder kept, which are moved, and then from another install of the method on this host, which keeps its file: the file is hard-linked, or copied when no hard link can be made. Another install of the method is a folder `.ogw/generation/<method>/` or `.ogw/generation/<method>/<name>/` other than the install folder, whose `installed.json` names that method and has an hf pin with the same `source` and `revision`; its files of the pin with index `<i>` in its `pins` are in `hf/<i>/` of that folder. Other files and pins are fetched anew.
- `ogw generation install <method>` does not get `tools`, and changes only the item of that method in the result file

## generation measure

- `ogw generation measure <method>...` changes only the items of those methods in the result file
- The stages (resolution, length) and the test inputs are fixed in the tool per method. Stages run from the lowest
- Per stage, the result (`ok`, `failed`, `timeout`) and the duration taken are written. When a stage exceeds the `safetyTimeoutMs` of that method, it is cut off and is `timeout`
- When `failed` or `timeout` comes out, the higher stages are not run
- The tool gives the peak memory and the output folder (`output`) per stage, and for a `failed` or `timeout` stage also the last 20 lines of stderr of the stopped call (`error`). These three are not put in harness settings. It prints the result file once (`result`)
- Among `procedural` methods, the methods other than `blender` and `rig-2d` have no standard test task. One `ok` stage without resolution and length is written
- For `rig-2d`, one `ok` stage is written when `flux2-klein` has an `ok` stage (the result measured in this measurement; when this measurement did not measure it, the result in the result file; when it could not be measured, harness settings `measured`) and `ogw resource rig-split`, `rig-check`, `rig-mesh` pass the fixtures fixed in the tool, and otherwise one `failed` stage is written
- When the sandbox blocked an access, it is written in the result
- An `external-service` method not in `--allow` is not called. The result keeps the item that the result file has for that method when it has a stage, and otherwise writes that it was not called. The result of an `external-service` method that was called holds the duration taken and the cost; memory is not measured
- An `external-service` method without `provider` has no standard test call, so it is not called, and that fact is written in the result
- For a method with `provider`, the cost in the result is 0 for every billing
- `catalog` methods have no standard test task. When the files that `ogw generation install` fetched are the same as the pinned information, one `ok` stage without resolution and length is written

## env propose

The tool gives, per revision, an id, the harness settings path, the current value, the new value and the reason, and gives only the revisions below and the notices of `## procedure` 7 of [`host-env`](../skills/host-env/SKILL.md).

- revision `measured:<method>`: per method, replaces `measured.<method>` with the result of `ogw generation measure`
- revision `maxConcurrentInstances`: the smallest of the target values measured by `ogw instance measure`. Not given when that value is less than 2
- revision `playInstances`: when the smallest of the target values measured by `ogw instance measure` is 2 or more and less than harness settings `playInstances`, changes `playInstances` to that value
- revision `webSmokeCpuThrottleRate`: the benchmark index of this host that `ogw env benchmark` measured divided by harness settings `webSmokeDeviceBenchmarkIndex`, rounded, and 1 when that is less than 1. Not given when it is the value of `webSmokeCpuThrottleRate`
- revision `tools.postgresql`: when `ogw generation install` could not get the image, changes it to the highest `<major>.<minor>` tag of Docker Official Image `postgres` whose major is the same as that of `tag`, and its digest
- revision `pin:<method>`: for a method that has a target git pin, and for a `local-model` method that has a pip pin. The target git pins are the git pins without `revision` and every git pin of `local-model` methods. For a git pin without `revision`, the HEAD commit of the default branch of its repository is written as `revision`. The `[project] dependencies` of `pyproject` (`pyproject.toml` when that pin has none) at that commit of a target git pin, and the pip pin entries of the projects that those dependencies do not name (by PEP 503 normalized name), are resolved with `uv pip compile` per macos-arm64 (macOS 14.0 or later), linux-x64 and windows-x64 with the CPython version of the method's isolated environment, and every package down to dependencies of dependencies is pinned as `<name>==<version>`. Each resolution starts from the current pip pin: its entries that hold on that platform are the existing output file of `uv pip compile`, so a pinned version stays while the dependencies allow it, and a newer published version alone changes no pin. The results of the three platforms are merged into one pip pin: an entry that is the same on all three platforms stays without a marker, and an entry that differs gets the `sys_platform` marker of the platforms that receive it. This pip pin replaces the first pip pin, and the other pip pins are dropped. When there is no pip pin, it is added at the end. A PEP 440 local version label (`torch==2.7.1+cu128`) is not on PyPI, so it is resolved with the label removed. A project not on PyPI is not put in, and is written in the reason. Among the direct references (`<name> @ <URL>`) of the dependencies, a `git+` URL whose repository is `https://` or `ssh://` is pinned to the commit that the ref of that URL (HEAD when there is none) points to and is put in as `<name> @ git+<repository>@<commit>`; any other URL is not put in, and is written in the reason. For a platform that does not resolve, the packages of that method are not fetched, and that platform and the uv error are written in the reason. When none of the three platforms resolves, it gives no revision, gives the uv error and fails. When `pins` does not change, it is not given
- revision `sha256:<method>`: for each hf pin without `sha256` among the hf pins of the methods that `ogw generation install` fetched, writes the `sha256` calculated from the fetched files. Even after this revision is applied, `ogw generation install` does not fetch that method again
- revision `tools.gdtoolkit`: when there is no `tools.gdtoolkit` or `ogw generation install` could not get it, adds the pinned information of the `any` wheel of the highest version of PyPI `gdtoolkit` whose major version is the same as the Godot major version of `open-game-works-core-impl/client/godot/engine.json`, and of every wheel that wheel depends on (dependencies of dependencies included). Dependency wheels are chosen per macos-arm64, linux-x64 and windows-x64, and `python` is the highest CPython `3.<minor>` for which all three platforms have the dependency wheels
- revision `tools.ffmpeg`: when there is no `tools.ffmpeg` or `ogw generation install` could not get it, adds pinned information with the URLs of the assets `ffmpeg-darwin-arm64` (macos-arm64), `ffmpeg-linux-x64` (linux-x64), `ffmpeg-win32-x64` (windows-x64) in tag `b6.1.1` of GitHub release `eugeneware/ffmpeg-static`, and the SHA-256 digests that GitHub gives for those assets. These builds contain the `libvorbis` encoder

  - DEV, STG: with `--version`, the version is that value, and when that value is not higher than the game's highest tag version, stops and tells the human. The version is that tag's version. When there is no such commit, when the `prod-<version>` tag already exists, or when it is not a bundle patch and the version is not higher than the version of the last PROD build, stops and reports to the human. When main has no `records/loops/build-stg-<version>/end.md` or its `## compatibility base` differs from the tag of the current last PROD build (`none` when there is no PROD tag), stops and reports to the human that a new STG build is needed. Unless it is a bundle patch without data, the tool also checks with this host's GitHub CLI login that game settings `serverImage.repository` has the server image with image tag `stg-<version>`. When it does not, stops and reports to the human
  - When a PROD tag exists and the contract version of the commit the branch was created from is greater than the contract version of the last PROD build, the tool also checks that the secret of operator `ogw` in PROD `adminOperators` is in this host's secret store and that admin operation `sample_user_ids` (`count` 1) on PROD `serverUrl` succeeds with that operator. Otherwise, stops and tells the human

## build run

The order of the work of `ogw build run` after its data check and binary build.

- The build-time checks before the platform build that run no game read no result of each other and start together: the settings checks and the human checks, the static check, `native plugin`, the STG server image build of `DEV code`, the repository scan of `secret`, `placeholder`, `backward compatibility`, the preparation of the check workspaces (`### client checks`), and checks `device performance` and `web smoke` up to their check exports (`### device performance` 1 to 3, `### web smoke` 1 and 2), whose Gradle and web exports load the host as the other checks do. The contract tool of `backward compatibility` runs in its own worktree of the build branch HEAD, because it and the `ogw generate` before it write generation targets, which the other checks and the check instances read in the build checkout
- The checks that run the game measure performance or judge times on the modelled device (harness settings `webSmokeBootTimeoutMs`), so their runs on the device and in the browser start when all of those have ended: `device performance` from `### device performance` 4 and `web smoke` from `### web smoke` 3 together, check `repeat test` when `web smoke` has ended, and check `soak test` when `repeat test` and `device performance` have ended. The run starts no other work while they run
- When no check blocks the build, the platform build runs together with the server image build into the build cache (`## server image`), the app versions of `update/update.json` (`## deploy` of [`build`](../skills/build/SKILL.md)), the data versions of the last PROD build and the match wait duration, and the PROD values of `## converters` and `## core schema` of `## build report`. The push of the server image, `update/` and these values in the result wait until the artifact checks (the artifact scan of `secret`, the made packages of `DEV code`, `bundle`) have passed. When those checks fail, the build into the build cache stops and no other app version starts its check
- A DEV web build does not run checks `repeat test` and `soak test` before the platform build: they only warn in a DEV build, so its hand-off does not wait for them. When no check blocks the build, the run ends by starting the late checks job `ogw build late <game> --commit <build branch HEAD>` and writes `lateChecks` (their names, the job and that commit) into `build-run.json`; its text output has `check <name>: pending` per check and `late checks job <id>`. The job runs `repeat test`, then `soak test`, in a worktree of that commit, whose HEAD the check workspaces are made of and in which the check instances run (`ogw instance start` with that folder as its root), so that `ogw build finish` changing the game repo checkout changes no file they run. It writes `{"commit": "<sha>", "checks": [<check>, ...]}` to `builds/<env>-<version>/late-checks.json`, `<check>` as in `build-run.json`. A DEV build that a check blocks starts no late checks job
- The app versions of `update/update.json` are checked together, each with its own worktree and data build, at most as many at a time as this host has CPUs
- The match wait duration reads the data and game settings `core` of the last PROD build from git, and the core settings of the release of its core version
- The artifact scan of `secret` reads the files ahead while it scans the files before them, at most 256 MiB of files read and not yet scanned at a time, and a larger file alone

## server image

How `ogw build run` makes the server image of a DEV or STG build.

- The build context is a copy of `server/` in a temporary folder (without `node_modules/`)
- For STG, `generated/core_settings.json` and `generated/server_modules.json` of that copy are rewritten with the STG prepared modules (`## module` of the `core` skill)
- For DEV and STG, the items whose path contains an environment name other than this build's are removed from `generated/core_settings.json` of that copy
- The Dockerfile is `core/Dockerfile` of that copy
- Every `docker buildx build` of the image of a build has the same arguments but its output, so that a later one takes every step from the build cache of an earlier one: the STG build of check `DEV code` into a tar of the image file system (`--output type=tar`), the build into the build cache beside the platform build (`--output type=cacheonly`), and the push (`--push`), which waits for the checks of the artifacts (`## build run`)
- The registry login uses this host's GitHub CLI login

## save schema check

`ogw build run` runs the migration test of [`migration`](../skills/server-core/modules/migration.md). A changed kind is a UserState, server state or game state kind of the game contract whose definition and the definitions of the game contract messages and enums reachable from it (excluding comments) differ from the last PROD build.

1. Calls the admin API of PROD `serverUrl` as operator `ogw` to get samples. For each user chosen by `sample_user_ids` (`count` is the merged core settings `migration.testSampleCount` of the build checkout), gets a snapshot with `export_user_snapshot`. For each changed game state kind that is also in `contract/game_state.proto` of the last PROD build, gets game state snapshots with `sample_game_state` (kind, `migration.testSampleCount`). The format follows [`user-snapshot-clone`](../skills/server-core/modules/user-snapshot-clone.md)
2. The runner starts a one-off PostgreSQL container with the harness settings `tools.postgresql` image. The tool starts a test server of the new server code in the build checkout with `start_test_server` of [`testing`](../skills/server-core/modules/testing.md), and for each snapshot and game state snapshot calls `call_dev` (that test server, `migration`, `migrate_snapshot`, that snapshot)
3. When `migrate_snapshot` returns a record whose `result` is `FAILED` or returns `bad_request`, the check fails. The failure contents are the snapshot source (user ID or game state kind) and the record's `table`, `key`, `from_version`, `error`
4. A changed kind that is also in the last PROD build and for which no received record has a contract version lower than the current contract version is reported as `unknown`. When the `backward compatibility` check has no failure and there is an `unknown` kind, the result of that check is `unknown`

- Snapshots and game state snapshots are received one at a time into memory, passed to `migrate_snapshot` and discarded. They are not written to files
- When the PROD admin API cannot be called (no secret, connection failure, authentication failure), the check fails, and the failure contents start with `save schema: PROD admin API`

How `ogw build run` does step 2:

- One `node` process with `server/` of the build checkout as cwd calls `start_test_server` of `server/core/testing/dev/index.ts` without input and starts a test server. The environment variables are those of a server regression test with `--db postgresql` in `### test run` of [`testing`](../skills/server-core/modules/testing.md)
- The tool writes one snapshot or game state snapshot as one line of JSON to the stdin of that process. The process writes the result of `call_dev`(test server, `migration`, `migrate_snapshot`, that JSON value) as JSON on one stdout line that starts with `ogw-result `. `bigint` is a decimal string. After it receives that line, the tool writes the next snapshot
- When stdin ends, the process calls `stop_test_server` and exits

## bundle patch

What a bundle patch build holds and writes.

- The bundle holds only what matches the code of the target app version
- It leaves out scenes and prefabs that use code changed after that app version
- The resource keys it holds are the keys whose `sha256` in `resource/resources.csv` differs from the tag, or that were not in the tag, at any commit from the `<env>-<app version>` tag commit of the target app version to the build commit, minus what it leaves out
- It does not delete resource keys that were in the bundle of the target app version
- It does not hold data whose protocol hash differs from that of the target app version, or data that names a resource key that the target app version with its bundle lacks
- When these rules are broken or the bundle has code, the `bundle` check blocks it
- When it carries data, it holds all client table binaries of `client/build/data/` and the translation binary of each language
- The result files go in `builds/<env>-<version>/patch/`: bundle files, data files and `patch.json`. `patch.json` is the target app version item of deploy list `patches` (`data_version`, `data_files`, `translation_files`, `bundle_files`), and its format follows [`game-update`](../skills/server-core/modules/game-update.md). When it does not carry data, `data_files` and `translation_files` are empty lists and `data_version` is the client data version of the target app version tag commit
- A bundle patch build also runs checks `device performance`, `web smoke`, `repeat test` and `soak test`

## godot build

How the harness tool builds with the Godot engine. The signing key table and what a human prepares are `## signing` of [godot](../skills/build/engines/godot.md), and the native plugin rules are `## native plugin` of that document.

### export

`ogw build run` does the steps below in this order for each platform in the build workspace.

1. Puts the `plugins` of `engine.json` for that platform into `addons/` and `ios/plugins/`. For android, puts the Android build template into `android/build/` and writes the `res://` paths of all `addons/<folder>/plugin.cfg` (the editor plugin of a Godot Android plugin v2) of the added plugins, in byte order, into `[editor_plugins]` `enabled` (`PackedStringArray`) of `project.godot`. The export plugin of an editor plugin that is not enabled does not add the `.aar` and its dependencies. A `.gdextension` plugin has no setting that enables it, because Godot reads it in the project scan
2. For STG and PROD, changes the `LogCore.log_debug(...)` lines by the `LogCore` row of `engines/godot.md` `## engine behavior` of the `client-core` skill
3. Writes `generated/build_info.json` and `application/config/version` of `project.godot`. `generated/build_info.json` is a JSON object keyed by the `BuildInfo` field names of `BootstrapCore`: `app_id` is game settings `appId`, `app_version` is the version, `environment` is the environment name, `platform` is the platform, `server_url` is that environment's `serverUrl` (an empty string when there is none), `game_update_url` is `server_url` followed by `/update/deploy_list.json`, `update_trust_keys` is a `{key_id, public_key}` for each item of that environment's `updatePublicKeys` (`key_id` is the key ID of `game-update`), `adapters` is that environment's `adapters`, `ad_units` is the ad unit IDs of that platform keyed by the ID value of the placement (read from `id_registry.json` of the `id-registry` branch) as a decimal string, and `instance_id` is an empty string. DEV adds the value of DEV secret `devAccess` as `dev_access`. When a placement of `adUnits` is not in `id_registry.json`, it fails
4. Writes `export_presets.cfg`
5. Puts in the signing values. For ios and macos without free signing, does the keychain preparation of `### signing`, and for ios also the provisioning profile preparation
6. `godot --headless --path client --import`
7. Runs `godot --headless --path client --export-<debug|release> "<preset>" <output file>` with `--export-debug` for DEV and `--export-release` for STG and PROD. For ios when game settings `consent.trackingRequest` is `true`, it then puts the localized `NSUserTrackingUsageDescription` into the `.ipa` before the keychain of `### signing` is deleted: it unpacks the `.ipa` with `ditto -x -k`, and for each language of game settings `supportedLanguages` writes `NSUserTrackingUsageDescription` of `Payload/<app>.app/<language with `-` replaced by `_`>.lproj/InfoPlist.strings` (made with `plutil -create xml1` when it does not exist) as the text of that language with `plutil -replace`. The text is the translation of reserved string `[auth_tracking_usage]`, and the source text for a missing translation. Then it re-signs the app bundle with `codesign --force` using the entitlements read with `codesign -d --entitlements <file> --xml`, the signing identity of that environment (DEV `Apple Development`, STG and PROD `Apple Distribution`) and the keychain of `### signing`, and packs `Payload` into the `.ipa` again with `ditto -c -k --sequesterRsrc --keepParent`. For macos without free signing, it then does the macOS signing after the export of `### signing` before the keychain of `### signing` is deleted
8. When the exit code is not 0, the output of the export has a line with `No "<architecture>" library found for GDExtension`, or a named output file (the files starting with `<game>`, `index.html` for web) is missing, it fails
9. When the file list inside the made package has a target of `exclude_filter`, or the app bundle root inside the ios `.ipa` has no `PrivacyInfo.xcprivacy`, it fails
10. For windows without free signing, signs the output files by `### signing`. When signing fails, it fails

#### export preset

- There is one preset per platform and environment, named `<platform>-<lowercase environment>`. e.g. `android-prod`. `export_presets.cfg` is written only in the build workspace and is not committed
- `export_filter` is `all_resources`, and `include_filter` is `build/data/*,generated/*.json`
- `exclude_filter`

  | environment | value |
  |---|---|
  | DEV | `tests/*,addons/gut/*,generated/launch_values.json` |
  | STG, PROD | `tests/*,addons/gut/*,dev/*,core/*/dev/*,generated/core_settings_types.json,generated/launch_values.json` |

- The app ID is game settings `appId`. It is `package/unique_name` for android, and `application/bundle_identifier` for ios and macos
- When `ads` of that environment's `adapters` in game settings is `ads-admob`, writes the ads SDK app ID. For android it is `admob.appIdAndroid` in meta-data `com.google.android.gms.ads.APPLICATION_ID` of `android/build/AndroidManifest.xml`, and for ios it is `admob.appIdIos` in Info.plist key `GADApplicationIdentifier`
- iOS entitlements are written with `entitlements/push_notifications` and `entitlements/additional` of the ios preset. `entitlements/push_notifications` is `Production` when that environment's `adapters.push-apns` is `push-apns`, `Development` when it is `push-apns-sandbox`, and `Disabled` otherwise. `entitlements/additional` is `com.apple.developer.applesignin` (an array with the one value `Default`) when `adapters.login-apple` is `login-apple`, and an empty string otherwise. For macos without free signing, an entitlements plist is written in the build workspace, and `codesign/entitlements/custom_file` of the macos preset points to it. It holds `com.apple.application-identifier` (`<appleTeamId>.<appId>` of game settings), `com.apple.developer.team-identifier` (game settings `appleTeamId`) and, when `adapters.login-apple` is `login-apple`, `com.apple.developer.applesignin` (an array with the one value `Default`)
- The privacy manifest items of the ios preset are written from the values of the build's `PrivacyInfo.xcprivacy`. `privacy/tracking_enabled` is `NSPrivacyTracking`, and `privacy/tracking_domains` is an empty list. For each item of `NSPrivacyCollectedDataTypes`, writes `privacy/collected_data/<key>/collected` as `true`, and `privacy/collected_data/<key>/linked_to_user`, `used_for_tracking` and `collection_purposes` as the linked, tracking and purpose of that item. `collection_purposes` is an integer that adds one bit per purpose: `Analytics` 1, `AppFunctionality` 2, `DeveloperAdvertising` 4, `ThirdPartyAdvertising` 8, `ProductPersonalization` 16, `Other` 32 (the names are the values without `NSPrivacyCollectedDataTypePurpose`). `<key>` is the snake_case of the name left after removing the leading `NSPrivacyCollectedDataType` from the `NSPrivacyCollectedDataType` value. e.g. `NSPrivacyCollectedDataTypeUserID` → `user_id`. The required reason API items (items whose name starts with `privacy/` and ends with `_access_reasons`) use the export preset defaults
- When that environment's `login-google` is `login-google`, writes `loginGoogle.iosClientId` in Info.plist key `GIDClientID` of ios, and its reversed client ID (the parts split by `.` in reverse order) in `CFBundleURLSchemes` of `CFBundleURLTypes`
- The keys added to the ios Info.plist are written as XML of `<key>` and value in `application/additional_plist_content` of the ios preset: `GADApplicationIdentifier` (ads), `GIDClientID` and `CFBundleURLTypes` (Google Sign-In), and `NSUserTrackingUsageDescription` (the source text of reserved string `[auth_tracking_usage]`) when game settings `consent.trackingRequest` is `true`
- The ios preset writes `plugins/<name>` as `true` for each `.gdip` under `ios/plugins/` of the plugins added in 1. `<name>` is `[config]` `name` of that `.gdip`. A `.gdip` plugin that is not enabled is not included in the export

### repeat test

`ogw build run` does check `repeat test` of an STG web build, and its late checks job of a DEV web build, in the order below, after check `web smoke` has ended (`## build run`). Each run plays the bot playtest scenario as a new user, and 36 runs without a failed run show at 95% confidence that fewer than 8% of runs fail (0.92^36 < 0.05). 36 is a fixed value of the check, not a setting.

1. Starts 36 runs, at most harness settings `maxConcurrentInstances` at a time. A run makes its own copy of the web check workspace, starts its own check instance, makes its own check export in that copy, and does `### web smoke` 3 to 5 with them. The DB of the check instance and the browser profile of the page are new, so the run starts as a new user with a new save. The server makes the random seed of each request with secure random and writes it to the `request` log, so each run has other random seeds and its server log holds them
2. A run is `fail` when its no blocker or full flow is `fail`, `unknown` when neither is `fail` and one is `unknown` or when the run could not run to the end (e.g. its instance, export or browser did not start), and `pass` otherwise
3. The kind of a failed run is the first of the following that its first failure matches: `crash` (the page, the browser or the server process ended), `softlock` (`state.softlock` is not `null`, or a step or the boot did not end within its time limit), `error log` (an error level line in the browser console or the server log), `failed goal` (full flow is `fail` and no blocker is not: the goal is not `true` after the last step, or a `save` step failed), `other` (any other no blocker failure)
4. The check is `fail` when a run failed, `unknown` when no run failed and a run is `unknown`, and `pass` otherwise. Its first line is `<failed runs> of 36 runs failed: crash <n>, softlock <n>, error log <n>, failed goal <n>, other <n>`, followed by one line per run that is not `pass`: `run <n>: ` and the first line that check `web smoke` would give for that run, or `did not run: <reason>` for a run that an instance, export or browser error stopped. The browser console and the server log of each run that is not `pass` go in `builds/<env>-<version>/repeat-test/run-<n>/`

### soak test

`ogw build run` does check `soak test` of an STG web build, and its late checks job of a DEV web build, in the order below, after checks `repeat test` and `device performance` have ended (`## build run`), so that the runs of other checks do not change its frame intervals. One session plays the bot playtest scenario and then 45 minutes of cycles of bot play and idle, and the tool watches it for blockers, memory growth and frame degradation. The counts, times and limits of this section are fixed values of the check, not settings.

1. Does `### web smoke` 1 to 4. When its no blocker or full flow is not `pass`, the result is that of `web smoke`, and 2 and 3 are not done
2. Reads a tick (`get_state`, then `get_stats`, as `## performance` does) every 1000 ms, 2700 ticks (45 minutes), counted from 0. Each 150 ticks are a cycle: at tick 0 of a cycle the tool sends `clear_telemetry`, during ticks 0 to 119 of the cycle the bot plays, and during ticks 120 to 149 no input goes in. The bot is the command of the last `auto` step of the scenario, called with its arguments, and the input command it returns is put in as an `auto` step does, with the same gap between inputs. When the scenario has no `auto` step, no input goes in
   - After each tick, the tool checks the blockers of the bot playtest (`## bot playtest` of [`client-content`](../skills/client-content/SKILL.md)): the page, the browser or the server process ended, an error level line in the browser console or the server log, `state.boot_stage` `Halted`, `state.invariant_failures` not empty, `state.softlock` not `null`, and a command (a tick request, `clear_telemetry`, the bot command or its input command) that returned `ok` `false`. A blocker ends the session, and the check is `fail` with the line `tick <n>: <blocker>`. A request that fails without a blocker, or a bot command that returns neither `null` nor an input command, ends the session, and the check is `unknown`
3. Judges the ticks. Each 300 ticks (two cycles) are a window: window 0 is the warm-up, in which the caches and pools of what the cycles use fill, and windows 1 to 8 are the measured windows. Each measured window has two values
   - memory floor: the smallest `static_memory_bytes` of `get_stats` of the ticks of the window. A tick whose value is not a positive number has no memory reading
   - hitch ratio: the hitch ratio of `## performance` of the kept frame intervals of the ticks of the window, with the refresh rate left out, as the headless browser draws to no display. A tick is kept as `## performance` keeps it
   - trend of the 8 values of one kind in window order, v_1 to v_8: S is the number of pairs i < j with v_j > v_i minus the number of pairs with v_j < v_i, p is the share of the 40320 orders of 8 distinct values whose S is at least that S, and the slope is the median of (v_j − v_i) / (j − i) over the 28 pairs i < j (the mean of the two middle values). The trend rises when p < 0.05; for 8 distinct values, when S is at least 16
   - memory leak: the memory floor trend rises, and the memory floor of window 8 plus 288 slopes (24 hours of windows) is at least 2048 MiB, the WebAssembly memory maximum of a Godot web export with threads. Such a leak fills that memory within one day of play
   - frame degradation: the hitch ratio trend rises, and 7 slopes (its rise from window 1 to window 8) are at least 10 ms/s, the hitch ratio at which players see the game hitch
4. The check is `fail` with a blocker, a memory leak (the line `memory floor rises <slope> MiB per window (p <p>) and reaches 2048 MiB <hours> hours after window 8`) or frame degradation (the line `hitch ratio rises <7 slopes> ms/s from window 1 to window 8 (p <p>)`). Otherwise it is `unknown` when the session ended before its last tick, when a measured window has no memory reading, or when the kept frame intervals of a measured window add up to less than 10 s or a kept tick of it has no `frame_intervals_ms` array of numbers; its lines say which. Otherwise it is `pass`. The window values, the two p values and the two slopes go in `builds/<env>-<version>/soak-test/samples.json`, and the browser console and the server log beside it
5. Does `### web smoke` 5

## generation methods

How `ogw generation methods` chooses.

## rig tools

How the commands of `## rig tools` of [production](../skills/resource/production.md) calculate.

The three commands are deterministic. An opaque pixel is a pixel whose alpha is 128 or more. Boxes are in integer pixel coordinates and do not include their end, and centers are rounded down.

### rig-split

1. Check the input
2. The canvas is a transparent image of `--size`. Scale the source illustration and each layer to fit in the canvas keeping the aspect ratio, and place each at the center of the canvas. Write the scaled source illustration to `<out>/rig-canvas.png`
3. Per layer on the canvas, take the box of the pixels whose alpha is greater than 0, widen it by 3 px on each side, and write that area to `<out>/<part name>.png`. Its pixels outside the canvas are transparent. The top left of the widened box is `offset`, and it can be negative. When a layer has no pixel whose alpha is greater than 0, it fails
4. Per bone, decide the initial joint position, starting from the root. B is the union box of the boxes (before widening) of the parts attached to that bone, and P is the union box of the boxes of the parts attached to the parent bone
   - for the root, or when there is no P: the center of B
   - when B and P overlap: the center of the overlap box
   - when they do not overlap: the point in B closest to the center of P
   - a bone with no attached part takes the value of its parent, and such a root takes the center of the canvas
5. Measure the recompose of `### rig-check`
6. Write the rig split JSON and output it

### rig-check

- It scales `source` onto a transparent image of `canvas` as `rig-split` does, and draws the parts onto another transparent image of `canvas` in `parts` order at `offset` (rest pose). Part pixels outside the canvas are dropped
- `alphaIou`: the size of the intersection ÷ the size of the union of the opaque pixel sets of the composite and the scaled source illustration
- `colorDiff`: for each pixel that is opaque in both, the mean of the absolute differences of the R, G, B channels, averaged over all those pixels. From 0 to 255; `null` when no pixel is opaque in both

### rig-mesh

1. The shape is the opaque pixels of the part image widened by 2 px, cut to the part image, so every point is inside the part image. On its contour, pick contour points at an interval fixed in the tool, and from a grid with the same interval that starts at the top left of the box of the pixels whose alpha is greater than 0, pick the inner points of the shape that are not closer than that interval to any contour point
2. Delaunay-triangulate the points, and discard the triangles whose center is outside the shape
3. The segments of a bone run from the `pivot` of that bone to the `pivot` of each child bone, and a bone without children is the single point `pivot`. The distance d between a point and a bone is the shortest distance to those segments. Per point, calculate 1 ÷ (d + 1)² for each of the `bones` of the part, keep only the 3 largest, and divide them so that their sum is 1
4. Write the mesh JSON

The frame rate of an animation is the number of frames × 1000 ÷ the length in `spec` (fps), and its repetition is `loop` or `once` of `spec`
- any other type: not changed

3. Write the result of step 2 to `resource/<key>.<extension>`. Also write the files of the attached rows: for `sprite_animation`, the sheet PNG to `resource/sprite_sheet/<name>.png`; for `rig_animation_2d`, the part files of `--split` to `resource/image/<name>/<part name>.png`. Delete the attached rows and files of the parts that are not in this skeleton spec

For any other method, `source` is an empty cell, and `license` and `attribution` are the `license` and `attribution` of that method in harness settings `resourceGeneration` (an empty value when missing)

## secret set

`ogw secret set <game> <DEV|STG|PROD|signing> <secret name>` and `ogw secret set --harness <secret name>` put the value from stdin, without one trailing newline, into the secret store of this host. An empty value is not put. For the harness secret `claude-code-oauth-token`, the steps below run in order before it is put; when any of them does not pass, nothing is put, the reason is output, and the command ends with a nonzero code.

1. Checks whether the value can be an HTTP `Authorization: Bearer` header value: every character must be printable ASCII that is not a space (0x21 to 0x7E). The prefix and format of the token are not documented, so they are not checked. When it does not pass, it outputs the position and kind (whitespace, control, non-ASCII) of the first character that failed, and a way to put the value as one line (e.g. on macOS `pbpaste | tr -d '[:space:]' | tools/bin/ogw secret set --harness claude-code-oauth-token`). The value is not output
2. When neither play nor judge in harness settings `agents`, nor an item of `loop.judgePanel`, nor `loop.confirmJudge`, nor `loop.confirmFallback` has Claude Code as its agent CLI, no agent uses that token, so it is not put
3. Runs the token check run. When it fails, outputs the error of the agent CLI

The token check run uses the first agent, looking in the order play and judge of harness settings `agents`, then the items of `loop.judgePanel`, then `loop.confirmJudge` and `loop.confirmFallback` (these as the judge role), whose agent CLI is Claude Code, and runs with the same folder, agent sandbox, command, environment and prompt as the run in which `ogw env check` checks the agent CLI of that role with that agent CLI, model and effort, with only two changes: the environment variable `CLAUDE_CODE_OAUTH_TOKEN` is the value to check, and the command leaves out its `--output-format json` (`## agent`) and has `--output-format stream-json --verbose` added at the end. The time limit is 5 minutes, the same as the prompt run of `ogw env check`.

- It passes when the exit code is 0, it ended within the time limit, and it is not an authentication failure
- It is an authentication failure when a stdout line is a JSON object (`SDKAssistantMessage` of the Agent SDK) whose `type` is `assistant` and whose `error` is `authentication_failed`
- The error is the `result` of a JSON object whose `type` is `result`, when it is a string with a character that is not whitespace; otherwise stderr; when stderr also has no character that is not whitespace, stdout. When the time limit is exceeded, the error is that fact

|---|---|

Then it outputs the two secret names with a message to put matching values with `ogw secret set` and then run `ogw secret generate` again, and ends with a nonzero code

## secret store

The host secret store where `ogw` keeps secret values.

- macOS: the keychain file `~/Library/Keychains/ogw/ogw.keychain-db`. It is separate from the login keychain that the agent CLI in the agent sandbox uses, so that the sandbox blocks that folder. `ogw` handles that keychain with `/usr/bin/security` and creates it on first use with a password of 32 secure random bytes. The password is kept in the login keychain item with service `ogw/keychain` and account `ogw`
- Linux: the Linux secret store folder `$XDG_DATA_HOME/ogw/secrets/` (`~/.local/share/ogw/secrets/` when `XDG_DATA_HOME` is not set or is not an absolute path). It keeps one 0600 file per secret in a 0700 folder that only the owner reads and writes, writing to a temporary file and then renaming it. The D-Bus Secret Service is not used
- Windows: the Windows Credential Manager
- On macOS the login keychain and on Linux the D-Bus Secret Service are the old store. Values are moved from the old store to the secret store once per host. Before `ogw agent` starts a play agent or judge agent and before `ogw secret set` and `ogw secret generate` write to the secret store, when `moved.json` in the folder of the secret store (on macOS `~/Library/Keychains/ogw/`, on Linux the Linux secret store folder) has no `"done": true`, `ogw` moves, inside a lock, every secret name in harness settings and in the game settings of every game under `paths.games`, then records the moved names and `"done": true` in `moved.json`. Until then, when `ogw` reads a value that is not in the secret store and it is in the old store, it moves it to the secret store. Once `moved.json` has `"done": true`, `ogw` does not read the old store. Moved values are deleted from the old store. On Linux, when the D-Bus Secret Service cannot be reached, the old store is treated as empty

## secret show

`ogw secret show <game> <DEV|STG|PROD|signing> <secret name>` and `ogw secret show --harness <secret name>` are commands with which a human sees, in a terminal, a secret value in the secret store of this host. The argument and name checks are the same as `ogw secret set`.

- The value is output to stdout only when stdin and stdout are both TTYs. Otherwise it does not read the secret store, outputs a message that this is a command a human uses in a terminal, and ends with a nonzero code. Agents run without a TTY
- When the secret store does not have that secret, it ends with a nonzero code
- The value is not written to logs, agent run logs, job records or files. The command does not accept `--background` and is not a broker command

`ogw` does not put secret values (values of the secret store, passwords and tokens that `ogw` made) in the command line of a child process; it passes them through stdin or a file. - The Godot type check (the type check of `ogw code check` and `ogw check`) keeps each check that ended without errors in `ogw-cache/godot-type-check/` under the git common dir of the harness repo, as a file named by the hash of its input, and does not run a check of the same input again. A run without `--file` that leaves no record for this reason ends its output with the line `no test record: uncommitted changes in the checkout` or `no test record: HEAD moved during the run`
- `ogw core test` keeps passed module results in `ogw-cache/core-test-results/` under the git common dir of the harness repo, as files named by the hash of a key. The key also holds harness settings `tools` and the `fixtures/`, `proto/` and `settings/` that the run reads; for server and engine targets also `tools/contract-tool/` and `tools/data-tool/`, which make the core test data; for the tools target `tools/` and all of `client/` that the engine round-trip tests compile. ## host

- The first 32 hex digits of the SHA-256 of `ogw-host:<id>`, where `<id>` is the machine identifier of the OS in lowercase with `-` removed, are the host id. This keeps the machine identifier out of git. The machine identifier is `IOPlatformUUID` of `ioreg -rd1 -c IOPlatformExpertDevice` on macOS, `/etc/machine-id` on Linux, and `MachineGuid` of the registry `HKLM\SOFTWARE\Microsoft\Cryptography` on Windows
- host item: an item of the key `hosts` of `settings.json` or `settings.local.json`, keyed by host id, that holds values of that host. Harness settings are read with the host items of this host, the one of `settings.local.json` merged over the one of `settings.json`, without their `name`, merged under the top-level values of `settings.local.json`, and without `hosts` in either file; the next write of harness settings writes both files in that form. The host id is read only when a file holds a host item, and when it cannot be read then, reading harness settings fails
- `ogw` and the processes that `ogw` starts use IPv4 addresses first among DNS results (`--dns-result-order=ipv4first` in the environment variable `NODE_OPTIONS`)

## core upgrade

The behavior of `ogw core upgrade <game> (--check | --version <version>)`.

- For a game without a PROD tag, the version to change to is the highest release version of harness settings `coreReleaseRepository` that is not higher than the core version of the harness (AGENTS.md `## repo`), when it is higher than game settings `coreVersion`
- With `--version <version>`, it fails and changes nothing when `<version>` is not the version to change to at that time. It also fails and changes nothing when `settings.json`, `contract/`, `data/` or a generated folder has uncommitted changes. Otherwise it changes `coreVersion` to that version, runs `ogw core fetch` and `ogw env install-engines`, runs `ogw generate`, the data tool and the contract tool in the order of `generated diff`, commits `settings.json` with what those three wrote, and outputs the new version. A data check error or a contract violation does not stop it, and their lines are printed: the content agent fixes them after the upgrade. A data tool run with errors writes no generation target, and what it put in `data/` goes back to HEAD, so the commit holds no row with an error: the next `ogw data` puts it in again. When a step fails, `coreVersion` goes back, `ogw generate` runs again with it, what the tools wrote goes back to HEAD, and nothing stays staged
- The commit of `--version` holds only files the tool wrote and is a commit without the hook (`## pre-commit hook`), whose static check refuses content that the game has not caught up with yet (e.g. a game settings value that the new core version makes required, at `settings.json:1`). Like a data check error and a contract violation, the failures it prints are fixed by the content agent after the upgrade
- With `--check`, it changes nothing and commits nothing. It prints the current `coreVersion`, the version it would change to (or that there is none), the skipped versions, the first lines of the commit messages of the core release repository between the tags `v<current>` and `v<that version>` (GitHub compare) other than those of the commits that `ogw` itself makes for agent records, review lists and releases (first lines starting with `ogw agent `, `ogw: review lists ` or `core release `), and the released core proposals of the game whose version is above the current and at most that version
- The only failures of `ogw env install-engines` that make `ogw core upgrade` fail are failures of the engines and programs that `engine.json` of the core version release of that game lists, and the failure to read that `engine.json`. Failures that come from `engine.json` of other games and of `open-game-works-core-impl` are ignored
- For a game with a PROD tag, starting from the highest version not higher than the core version of the harness, it compares the game contract and the base proto of that version with the last PROD build by the backward compatibility of [`contract`](../skills/contract/SKILL.md), with the contract tool of that version. The version to change to is the highest version that keeps compatibility, and it also outputs the skipped versions. A backward compatibility violation is a violation line that appears only in a run given `--previous`; a version that has only other violations is not skipped

## core release

The release conditions that `ogw core release <version>` checks before the release (`## version and release` of [core command](../skills/core/command.md)), the asset it merges, and how it pushes.

- There is a record that `ogw core test` passed every module of the targets with an implementation on the `open-game-works-core-impl/` main HEAD commit. The targets with an implementation are `server` when `open-game-works-core-impl/server/core/` exists, the native run and the browser run (`--web`) for each engine that has `open-game-works-core-impl/client/<engine>/engine.json`, and `tools` when there is a tool that has `open-game-works-core-impl/tools/<tool>/package.json`. The modules of `tools` are those tools. The latest result of a module is that of its last record on that commit, except that an `unknown` does not replace an earlier `pass` or `fail` of the same module and target on that commit; a module with no record on that commit is `unknown` with the reason `not recorded`. A module whose latest result is `unknown` blocks the release with the line `core test <target>: <module> is unknown at <commit>: <reason>; rerun with the screen unlocked: <command>` for the reason `screen locked`, and `core test <target>: <module> is unknown at <commit>: <reason>; rerun: <command>` for another reason. `<command>` is `ogw core test <target without --web> <module>`, followed by ` --web` for a browser run
- `core-spec/` equals the result of running `ogw core spec` with the current harness specs
- For each target with a review state of `## review and code check` of [core command](../skills/core/command.md), the last round is judged and its result is `done`, and the target's folders (`server/core/<module>/`, `client/<engine>/core/<module folder>/`, `tools/<tool>/`) and `core-spec/<module>.json` did not change after the commit that started that round. The release output line of a changed target gives `ogw review run core <target> --reopen`
- When there is a release lower than that version, each module and tool that `ogw core review-targets --since v<highest of those releases>` outputs has a review state. The release output line of a target without one gives `ogw review run core <target> --since v<highest of those releases>`
- The must-fix lists of `## review lists` of [core command](../skills/core/command.md) have no items. Debt lists do not block the release. The release output has a `review debt <target>: <item count>` line for each debt list with items, which the lead agent handles as [core command](../skills/core/command.md) says
- `ogw code check core` is `pass`. The release runs it
- The values of `open-game-works-core-impl/settings/core-settings.json` satisfy the settings constraints whose `left` and `right` modules are both modules of targets with an implementation (`server`, engine). A key is `<module>.<name>`
- For each item of `plugins` of `engine.json` whose name starts with `ogw-`, the plugin build results for all target platforms are at the path that the engine-specific implementation rules set
- For each `open-game-works-core-impl/benchmark/<engine>/`, the binary build of the data tool of `open-game-works-core-impl/` passes on a copy of it, with the modules that benchmark game uses and its `id_registry.json`, as `ogw instance measure` builds the released benchmark game
- When there is a release lower than that version, the base proto of the highest of those releases and this base proto are compared with the backward compatibility rules of [`contract`](../skills/contract/SKILL.md), and when there is a change that breaks compatibility, the major is higher than that release's. The comparison runs the contract tool of `open-game-works-core-impl/` with `--base-proto-only`. `--base-proto` is `open-game-works-core-impl/proto/`, `--core-settings` is `open-game-works-core-impl/settings/core-settings.json` (`{}` when it does not exist), and the `--previous` folder holds `proto/` of that release's `contract-tool.tgz` and that release's `core-settings.json`. When that release has no `core-settings.json`, `core-settings.json` of the `--previous` folder is `{}`
- `ogw core release` merges the settings constraints of all modules into the release asset `core-settings-constraints.json`. This file is a JSON array whose items are `{"left": "<core settings key>", "factor": <integer>, "right": "<core settings key>"}`
- The core release repository is `https://github.com/<coreReleaseRepository>.git`. Before it checks the release conditions, it reads main of the core release repository. When that main exists and is not an ancestor of main of `open-game-works-core-impl/` (this checkout does not have that commit, or main does not contain it), it changes nothing and fails with the line `main of <repository> is at <commit>, which main of open-game-works-core-impl/ (<commit>) does not contain: <repository> has commits that are not on main here`
- It pushes the release commit to main and the tag `v<version>` with one `git push --atomic` without force, so that either both refs change in the core release repository or neither does. When main of the core release repository moved after the check, the push is rejected, and the release fails as with any failed push
- When the push fails, or `gh release create` fails and no GitHub release was made, it undoes the release so that the same version can be released again: after a push that went through, one atomic push deletes the tag and, when the release made a commit, sets main back to the `open-game-works-core-impl/` main HEAD before that commit, with `--force-with-lease` on the release commit, so that it changes main only while main is the release commit; then it deletes the local tag and the release commit. When the release exists or `gh` cannot tell (e.g. `gh release create` timed out after it made the release), it keeps the tag, main and the commit, so that main keeps the asset URLs the release was made with

## core spec and core test

What `ogw core spec` and `ogw core test` do beyond `## core spec file` of [core command](../skills/core/command.md).

- When `ogw core spec` and `ogw core test` run in the `open-game-works-core-impl/` main checkout on branch main, the tool, when it ends, commits to main all generated files that differ from HEAD and does not commit other changes. The generated files are `core-spec/`, `server/core/testing/dev/setting_types.ts`, the committed generation targets of the core test data build, per engine the `project.godot`, module list file, core settings file and core settings type file of the core project and the engine meta files (`.uid`, `.import`) of those files, and the files under `test-data/data/` that the data tool run aligning the core test data changed. Files under `test-data/data/` that already had uncommitted changes when the run started are not committed. `ogw core test` of an engine target imports the core project before the commit to make those meta files. `ogw core test` runs the tests on that commit
- When a spec violates `### tool-read form` of [core command](../skills/core/command.md), `ogw core spec` writes no file, outputs the spec file:line and the reason for each violation, and fails. The violations are: a code span of a dependency line is a module name that does not exist. A table that a used table line or the `→` of a reserved name points to has no table definition in any module. The header or a cell of a table definition, enum table, invariant table, format argument table, settings table, settings constraint table or collected data table differs from its form. The `text` of a format argument table is not in a reserved name or table definition. The same settings constraint is in two specs
- When `open-game-works-core-impl/server/core/testing/` exists, `ogw core spec` also writes `open-game-works-core-impl/server/core/testing/dev/setting_types.ts`, the settings type table that `testing` checks settings overrides against: one entry `'<key>': '<type>'` of `export const SETTING_TYPES` per distinct `key` of the settings tables of all modules, in byte order of `key`. When two settings rows have the same `key` with different `type`, it writes no file, outputs both spec file:lines and fails
- core checkout: the checkout that `ogw core spec`, `ogw core test`, `ogw core dependents`, `ogw core review-targets`, `ogw core licenses`, `ogw core pin-engine`, `ogw code check core`, `ogw meta sync core` and the `core` scope of `ogw settings` work in. It is the git worktree of `open-game-works-core-impl/` that holds the current folder: the main checkout, a worktree under `worktrees/_core/`, or any other worktree of that repo. When the current folder is in none, it is the main checkout, except when the current folder is in a core tree (a folder that holds `core-spec/` and `settings/core-settings.json`) that is not such a worktree: then the command fails, naming that folder and `git -C <open-game-works-core-impl/> worktree add <folder>`, which makes a worktree it works in
- `ogw core test` reads each `<module>` argument as the module names it holds split at whitespace, so `"AdCore AuthCore"` is the two modules `AdCore` and `AuthCore`
- The `--file` value of `ogw core test` is a path relative to the checkout, to the module folder or to the `tests/` folder of the module, or an absolute path. It names the one file that exists among those paths in the `tests/` folder of the module and has the suffix of the target: `.test.ts` for `server`, `.gd` for an engine. When none or more than one does, the command fails and prints the paths it tried
- `ogw core test` checks before it starts its job: the target, that `--file` is not given with `--web` or `tools`, that `--file` has one module, and the `--file` value. A refusal starts no job. The refusal of `--file` with `--web` prints the command without `--web`
- When the target is `server` or an engine, `ogw core test` checks `core-spec/` after `ogw core spec`, and when any of the following is violated, it fails without running tests
  - The file name equals `name`. In a run without a module given, the modules with an implementation equal the modules with a file. The implementation of a server module is a module folder that has the entry file set by `## folder` of [`server-core`](../skills/server-core/SKILL.md)
  - The other core modules that module code references are in `dependencies` or `optionalDependencies`. DEV code can also reference the modules of `devDependencies`
  - Following `dependencies` does not come back to the same module
  - For each name in `adapters` of any module, some module has a `collectedData` row whose `source` is that name
  - `source` of `collectedData` is `module` or a name in `adapters` of some module
  - Of `left` and `right` of `settingsConstraints` of the modules with an implementation, the keys of modules with an implementation are in `core-settings.json`. The module of a key is the name before the first `.` of the key
  - In `settings` of the modules with an implementation, the `key` of each row whose `source` is `core` is in `core-settings.json`, and the set of `key` of the rows whose `owner` is `human` equals the set of keys of modules with an implementation among the keys that have `"x-owner": "human"` in `core-settings.schema.json`
- The module runs of all `ogw core test` runs on this host together hold at most the CPU count of this host, because each run sizes its parallel module runs to the whole host, and runs that overlap (several core agents, `ogw review run` jobs) would otherwise push module tests past their test time limit. A module run holds 2 in the native run of an engine (an engine process keeps about two CPUs busy), 3 in `server` (a module test is two vitest runs with workers of their own), and 1 in a browser run and in `tools`; a share above the CPU count is the CPU count. A module run holds its share from before its first process starts until its last process ends, and waits for it without a time limit, so the wait counts toward neither its run time limit nor its test time limits. A share whose holder process is gone is freed

## review run

How `ogw review next` and `ogw review run` carry out `## review and code check` of [core command](../skills/core/command.md).

- When the result of the previous round is `fix` or `escalate`, or the round before a round started with `--continue` is `limit`, and that round's `open` findings include a finding whose `spec change` is `no` and whose aspect is `correctness`, `spec` or `security`, the tool gives the code check `--fix-base <commit that started the previous round>` to add `fix test proof`. When the `fix test proof` of the previous round is `fail` and the round that proof proves had such a finding, it gives that round's `--fix-base` again. When the proof of the same `--fix-base` is `fail` in two rounds, it does not give it again: when the code before the fix of that finding already behaved correctly (the aspect is behavior but there was no test), no test fails on that base. The second `fail` stays in the code check result of that round. The fix of a `test evidence` finding adds a test to code that already behaves correctly, so the test cannot fail on the code before the fix. Whether that test catches the defect is checked by the review agent changing the code (mutation)
- When only tests of other modules are `fail`, the tool runs those modules again in a worktree of main right before the fix was merged (the first parent of the merge commit; when that commit is not found, the commit that started the round). This is because the fixes of several modules are merged into main in parallel, and a failure made by another merge after the round started is not to be counted as a failure of this fix. When it is `fail` there too, it is a failure that existed before the fix. When it passes there, and main changed files outside `records/` after that merge commit, it runs again in a worktree of that merge commit too, and when it passes there, it is a failure made by a later merge. These two failures do not stop the run and are output as `pre-existing test fail:` lines in the job output. Other failures are failures made by the fix, so it stops with `test fail`.
- `fix test proof`: runs the tests on the target code of the `--fix-base` commit, with the target's test files changed from that commit to the round start commit laid over it. `ogw review next` gives the code check the round start commit as `--commit` and the review target as `--target` together. The target's test files are the files under `server/core/<module>/tests/`, `client/<engine>/core/<module folder>/tests/`, `tools/<tool>/tests/`. The tests run with `ogw core test` on the target only (an engine without `--web`). When one or more are `fail`, the result is `pass`. It means that a fixed test checks the fixed behavior only when it fails on the code before the fix. When all are `pass`, the result is `fail`. When there is no changed test file, the core test stops before the tests or before starting the test framework (vitest, GUT) (e.g. dependency installation failure, no vitest), or the core test result of the target is `unknown`, the result is `unknown` and the reason is output. For a `fail` after the test framework starts, a crash or a timeout is also `fail`
- When the target's code outside its test files (outside `tests/` in `server/core/<module>/`, `client/<engine>/core/<module folder>/`, `tools/<tool>/`; `tools/src/` for harness `tools/`) did not change from the `--fix-base` commit to the round start commit, `fix test proof` is `unknown`. This is because with a fix that edited only tests (e.g. a `test evidence` finding), the code before the fix equals the code after it, so no test can fail on it
- The type check and lint of `ogw code check core` do not read files under `benchmark/`. The benchmark game is a game repo, and its server code compiles only together with the server core of a core release. The other checks (dependency, secret) also read `benchmark/`
- `ogw code check` uses the `node_modules/` of that checkout for each package folder of the code it checks. When the checkout has none (a tool package in a core agent worktree), it uses the `node_modules/` of the main checkout when the `package-lock.json` of that package equals the one in the `open-game-works-core-impl/` main checkout. The check does not put links in the checkout: when a package has to use it that way, the check puts the checkout's files in the check's work folder, links there and checks. A link in the checkout that goes to the `node_modules/` of the main checkout (left by an earlier check) does not count as the checkout's own. While it checks, `ogw code check core` is a reader of the build lock of each tool folder of the main checkout, so a tool build does not change `node_modules/` in the meantime
- Each time `ogw review run` finishes a step, when harness `tools/` differs from when the job started (the `tools` tree of harness repo HEAD), it continues `ogw review run core <target>` in a new process of the changed code and outputs its result. The new process takes over the count of consecutive `invalid` results that the job counted and the `pre-existing test fail:` lines that the job collected. A long-running job does not keep running on the harness code from when it started
- `ogw review next` and `ogw review run` refuse options that `## review and code check` of [core command](../skills/core/command.md) does not accept together before they start a round or a job, and the refusal names those options. Their usage line shows one of `--full`, `--debt`, or `--since <commit>` with one of `--restart`, `--respec`, `--continue`, `--reopen`
- The tool records `--since`, `--continue`, `--respec`, `--reopen`, `--full`, `--debt` in the review state. `--since` is also used for the round 1 that starts again after round 1 is deleted as `invalid`, and `--continue`, `--respec`, `--reopen`, `--full`, `--debt` are used until the round started with them is judged with a result other than `invalid`. A rerun of `ogw review next` or `ogw review run` does not need that option again
- The review agent jobs, core agent jobs and core test jobs that all `ogw review run` jobs on this host run together are at most harness settings `reviewRunConcurrency`. When there is no free slot, a job waits until a slot frees up

## code check

lint of `ogw code check tool` (and `node scripts/lint.ts` in `tools/`): the TypeScript lint, and for the files under `tools/src/` the rule `ogw/no-swallowed-error`. It fails a `catch` clause, a `.catch(...)` handler and the rejection handler of `.then(...)` that does not use its error and can end other than by a throw. A handler given by name or by a factory call is checked at its definition in its file. A name that its file does not define passes only when it is `whenNotFound` (it turns a not-found error into a value and throws every other error), `ignoreCleanupError` (a cleanup whose failure cannot change a result) or the `reject` of a promise executor.

type check (`ogw code check` and the static check `type check`): after `godot --headless --path <project> --import`, one Godot process loads the script of each `.gd` file (the same load and validity check as `--check-only`) and ends without errors. A script that depends on a script that failed earlier does not report the error of that dependency again. When that process does not end without errors, each file is checked again with `godot --headless --path <project> --check-only --script <file>` to find which file causes it. Not ending without errors means an error line that belongs to no script's load (before the first script, between two scripts, after the last script), a non-zero exit code, or exceeding the time limit.

## pre-commit hook

The pre-commit hook that `ogw game init` installs runs `ogw meta sync <game> --staged` (`## meta sync`), then the static check of the checkout, and refuses the commit when the static check has a failure that the commit makes, printing each such failure as `<where>: <message>`. A failure that the commit makes is:

- a failure at a line of `settings.json` (`settings.json:<line>`) when the commit changes the value that starts on that line of the checkout's `settings.json`: the outermost value that starts there, the whole file on line 1. The commit changes it when the value at its path in the commit differs from the value at that path in HEAD, or when only one of them has a value there. Game settings are independent values, so a commit that does not change the value a failure points at did not make it: an option entry that a second supported language requires, at `supportedLanguages`, is made by the commit that adds that language, not by a commit that fills `uiCheckScreens`
- another failure whose `where` is a staged file or a line of one
- an absence failure whose `where` `<folder>:1` is a folder that holds a staged file

A commit without the hook commits files whose content the game may not have caught up with yet (`ogw core upgrade` `--version`, `ogw settings commit`, step 1 of `### regress refresh`): the tool stages the files of the commit, runs `ogw meta sync <game> --staged` (`## meta sync`) as the hook does, and commits the files of the commit with the meta files that this sync stages or removes from the index for them, skipping the hook. With no change of those files from HEAD, it commits nothing and runs no sync. When the sync or the commit fails, what it staged leaves the index. After the commit, `ogw core upgrade` and `ogw settings commit` run the static check of the checkout and print, as `<where>: <message>` lines like the hook's, the failures for which the hook would refuse the commit. These failures do not fail the command. When that static check cannot run, the command prints the reason, and the commit stays

## meta sync

At each commit, `ogw meta sync <game|core> --staged` of the pre-commit hook syncs the meta files: it runs `godot --headless --path <project> --import` only when the staged files include an import trigger file, deletes `.uid`, `.import` whose source file does not exist, for a meta file whose source has a staged change stages that change when the source is in the index and removes the meta file from the index when the source is not in the index, and reverts the changes of meta files whose source has no staged change. A commit without the hook runs the same sync (`## pre-commit hook`).

An import trigger file is a file with a staged change (addition, modification, rename, deletion) that is visible to the Godot project: a file that is under `client/` or `resource/` for a game, or under `open-game-works-core-impl/client/godot/` for core, that is not under `.godot/`, `addons/`, `android/`, `ios/plugins/`, `plugins/`, whose extension is not `.uid`, `.import`, and, for core, that is not `open-game-works-core-impl/client/godot/engine.json`. Godot does not read `engine.json`, and a commit that changes the Godot version must pass the hook even when that version is not on this host.

When `resource/resources.csv` exists, `ogw generate` writes `resource/resources.csv.import` as a file with only one line `importer="skip"` in the `[remap]` section. It is the file that Skip of the Godot import dock saves, and Godot does not import its source or put it in an export. Only the harness tool reads the resource list file. `ogw meta sync` does not sync this file.

## deploy

How `ogw deploy <game> <DEV|STG> <version>` deploys the `<env>-<version>` build to that environment. The deploy rules are `## deploy` of [`build`](../skills/build/SKILL.md).

- It connects to the `host` of game settings `environments.<ENV>.deploy` as `user` with the SSH private key of `secrets.deploySsh`, and starts the server and PostgreSQL with Docker Compose in `<dir>` on the host. SSH connects with strict host key checking that trusts only `deploy.hostKey`; when the host key differs, it does not connect and fails
- Admin operations are sent to the `serverUrl` of that environment as the operator `ogw` of `adminOperators`
- First it reads the current deploy list with `get_deploy_list` and saves it to `builds/<env lowercase>-deploy-list.json` of the game repo. When `<dir>/compose.yaml` does not exist, or the result is `not_found`, or, in a deploy that deletes the DB volume in 1 (a build without a PROD tag that has a server image), the read sent to the server fails without a failure response with a `{"error": "<reason>"}` body (e.g. connection failure, a response that is not JSON), the deploy list of that file with `patches` replaced by an empty list is used as the deploy list read beforehand. This keeps the `app` that a human set from being lost even when a deploy stopped after deleting the DB volume in 1. When that file also does not exist, there is no deploy list read beforehand. When the read fails for another reason (e.g. a failure before sending to the server: no `serverUrl`, or no secret of the operator `ogw`), the steps below are not done; it stops and reports it
- Then it does the steps below in order; when any of them fails, it stops and reports the failed step
  1. When there is no PROD tag, stops the server and PostgreSQL and deletes the DB volume with `docker compose down --volumes`. Skipped when `<dir>/compose.yaml` does not exist
  2. When there is a PROD tag and `<dir>/compose.yaml` exists, uploads the update files with `put_update_file`
  3. Writes the secret files per the secret file rule of `build` `## deploy`, writes `<dir>/compose.yaml` again with the server image of this build, and runs `docker compose pull` and `docker compose up --detach`. When any secret file was newly written, `--force-recreate` is added to `docker compose up`. It waits until the server has started (`build` `## deploy`)
  4. When they were not uploaded in 2, uploads the update files with `put_update_file`
  5. When there is a PROD tag, calls `start_migration_batch` and waits with `get_migration_batch` until the batch ends
  6. Calls `publish_deploy_list` with the deploy list read beforehand, per the deploy list rule of `build` `## deploy`. When the DB volume was deleted in 1, `patches` of the deploy list read beforehand is treated as an empty list, because those files are not in the deleted DB
  7. When this build has a web artifact, uploads the version folder of `build` `## web hosting` and switches the entry page to this version
  8. When there is a PROD tag, runs `ogw clone sweep <game> <env>`
- writing secret files: when any secret to write is not in the secret store of this host, it does nothing on the host, outputs all those secret names and fails. Then it creates `secrets/` with mode 0700 and, for each file on the host, compares the SHA-256 that `sha256sum` outputs with the SHA-256 of the file content to write. Only for a secret that differs or whose file does not exist, the value is passed through stdin, not the SSH command line, written to a temporary file in the same folder, and renamed. Finally the mode of every secret file is set per the rule
- A build without a server image (a bundle patch that holds no data) skips 1, 3 and 5. When there are no update files, 2 and 4 are skipped
- Uploading the web artifact uses the same S3-compatible API and signature as the `game-update` `cdn-r2` `put`, and the secret access key is the value of `secrets.cdn` of that environment
- headers of uploaded files: for files of the version folder, `Cache-Control` is the same as the `GET /update/files/<sha256>` response of [`game-update`](../skills/server-core/modules/game-update.md); for the entry page it is `Cache-Control: no-cache`. `Content-Type` is set by the file extension: `text/html; charset=utf-8` for `.html`, `text/javascript` for `.js`, `application/wasm` for `.wasm`, `image/png` for `.png`, `application/octet-stream` for others
- The top-level `name` of `compose.yaml` is `<game>-<env>`. The services are the two below; no coturn server is included
  - `db`: the image `postgres:<tag>@<digest>` of harness settings `tools.postgresql`. Its data is in the named volume `db-data`, mounted at `/var/lib/postgresql` when the major of `tools.postgresql` `tag` is 18 or more, otherwise at `/var/lib/postgresql/data`. The password of user `postgres` is received as a Docker secret from the `<dir>/secrets/<secret name>` file of `secrets.dbPassword` of that environment and passed as `POSTGRES_PASSWORD_FILE` (`/run/secrets/<secret name>`). The healthcheck is `pg_isready -U postgres` with interval 2 seconds, timeout 5 seconds, retries 30. No port is opened on the host
  - `server`: the server image with image tag `<env>-<version>` of `serverImage.repository`. Its arguments are `--env <ENV>`, plus `--matchmaker` for a realtime game. Container port 8080 is opened at `127.0.0.1:<deploy.port>` of the host. The secrets of `secrets` of that environment except `deploySsh` and `dbPassword`, and every `secret` of `adminOperators`, are received as Docker secrets from `<dir>/secrets/<secret name>` files. It starts after `db` accepts connections, through the `db` condition `service_healthy` of `depends_on`, and its restart policy is `unless-stopped`. A Docker secret file is `/run/secrets/<secret name>` inside the container
- The `logging` of the two services follows the container log rule of `build` `## deploy`
- A build that is not a bundle patch without data puts, in `ogw build run` (step 5 of `## procedure` of [`build`](../skills/build/SKILL.md)), all client table binaries of `client/build/data/`, the translation binary of each language and `update.json` in `builds/<env>-<version>/update/`. `update.json` has `data_version` (the Client build target data version of this build), `data_files`, `translation_files` and `apps`. The format of the first three is that of the same-named fields of a deploy list `patches` item. `language` of `translation_files` is `<code>` of the translation binary file name `translation_<code>.bin`. `apps` is the version of this build when it is not a bundle patch, plus each app version with an `<env>-<app version>` tag for which the Client build target data version of that tag commit has the same protocol hash and which passed the `bundle` check when this build's data was put in together with the `<env>-<app version>-bundle-<n>` bundle of the largest n of that app version (no bundle when there is none)

## measure

How `ogw loop evaluate` calculates `ogw measure`. The same calculation can also be called with the commands below.

- `ogw measure <game> --collect <instance id> --out <file>`: writes the raw data of that instance (`get_telemetry` result, `get_state` result, instance id, instance commit) to the file. When the instance is not of that game, was started with a save fixture, `get_telemetry` or `get_state` fails, or the telemetry is not a JSON object or has no `started_at`, it does not write and fails
- `ogw measure <game> --collected <file>...`: calculates from files that `--collect` wrote. The telemetry of the files is checked by the same conditions
- `ogw measure <game> <instance id>...`: collects the raw data of each instance and calculates right away
- The calculation runs only when the game has an open run, no instance appears twice, and all instances have the same commit. One instance is one sample. The result file is `records/loops/<run>/measure-<iteration>.json` of that run, and the targets are read from `design.md` of the game repo. The free scenes of the metrics are read from `play-guide.md` of the instance commit; when that commit has none, no scene is a free scene
- `ogw measure` writes the result file `records/loops/<run>/measure-<iteration>.json`. The format is `{"commit": "<sha>", "targets": [<target>, ...]}`, and `commit` is the commit of the measured instance. `<target>` is `{"metric": "<metric name>", "min": <number>, "max": <number>, "value": <number or null>, "result": "<in|out|unknown>", "data": "<table>.<column>" or null}` for each row of the `## feel targets` and `## tuning targets` tables of `design.md`. `value` is `null` when there is no value, and `data` is `null` when the `data` cell of that row is empty
- When the number of values is even, the median is the smaller of the two middle values
- The scene at a time is the `scene_key` of the last `scene_loads` whose `at` is at or before that time.
- The free scene time of a span is the device time of the span during which the scene is a free scene.

## generation call

The standard test task of `ogw generation measure` and the programs that `ogw generation run` calls per method. A `local-model` method not in the table has no standard test task and no `generation run`, so it fails.

- `local-model` calls and `blender` calls run in a sandbox: it blocks the network and limits writes to the install folder of the method (`## generation install`) and the output folder. The sandbox runs only on macOS (`sandbox-exec`) and Linux (`bwrap`); on other OSes those calls fail
- The Python of a `local-model` call is the Python of the isolated environment of the method. `ogw generation install` creates an isolated environment for a `local-model` method that has a pip pin or a git pin and installs the pip pins. Git pin repositories are not installed; they are used through `PYTHONPATH`
- environment of a `local-model` call: `HOME` is `home/` of the install folder of the method, `HF_HOME` is `home/.cache/huggingface/`, `HF_HUB_OFFLINE` and `TRANSFORMERS_OFFLINE` are `1`, `PYTHONPATH` is the checkout of the first git pin. Before the call, the downloaded folder of each hf pin is linked at `HF_HOME/hub/models--<org>--<name>/snapshots/<revision>` and the revision is written to `refs/main`
- The folders of the pins are in the install folder of the method: the hf pin folder `hf/<pin index>/` (the first hf pin folder is that of the first hf pin), the git pin checkout `git/<pin index>/`, and the file pin folder `files/`
- For each call, the tool empties `drivers/` of the install folder of the method and writes a fixed Python script, the driver, to `drivers/ogw_<name>.py`. The file name must not equal the name of a module that the driver imports. The device is the first available of MPS, CUDA, CPU
- The standard test task gives random seed 42. `generation run` gives no random seed (`-1` to the driver), and a driver given `-1` draws one at random
- A driver (`ace-step`, `moss-sfx`, `qwen3-tts`) takes the model folder and a JSON file of items, one per output: it loads the model once and makes each item in order. It writes each output file under another name and renames it when it is made, so a call cut off leaves no output that looks made. For an item it cannot make, it writes the exception to `ogw-error.txt` in that item's out folder and to stderr, goes on with the next item, and ends with code 1. A standard test task and a `generation run` of one key give one item
- `generation run --batch <file>`: the file is a JSON array of `{"key", "prompt", "images", "out"}` (`images` optional; paths relative to the current folder), one item per resource key, each with its own out folder. A method with a driver makes them in one call; another method makes them one call after another, and an item whose call cannot be made fails while the others go on. The output files of the method and `ogw-error.txt` are removed from each out folder first. An item is `ok` when its out folder has the output files after the call, also after a call cut off at its time limit; otherwise it is `failed`, with the reason, or `timeout` when the call was cut off with no reason for it. The time limit is that of one call times the number of items, below the time limit of a background job. It prints `<method>: <n> of <items> ok in <ms>ms`, then `<key>: <result>, output <out>` per item, with `: <reason>` for an item that failed
- stage: for the standard test task, the stage under test; for `generation run`, the stage that `ogw generation methods` output for that method
- output length: when `spec` has `length`, the smaller of that value and the `durationMs` of the stage; otherwise the `durationMs` of the stage
- loop length: for a key whose `spec` has `loop` `true`, the output length + 8000 ms, so that the song goes on past the loop and its ending is not in the loop; otherwise the output length. The standard test task has no `spec`, so its loop length is the output length
- image size: `size` of `spec` scaled up or down so that its long side is the `resolution` of the stage (1024 when there is no stage), with each side rounded to a multiple of 16. Less than 16 becomes 16. Without `size`, a square of that `resolution`
- result: the calls run in order and stop when one fails. When all calls end with code 0 and all output files exist, it is `ok`. For a method whose output files are `none`, it is `ok` when the output folder is not empty. There is one time limit for all the calls together. When a call ends with `failed` or `timeout`, the last 20 lines of the stderr of that call, without the output that `/usr/bin/time` added, are recorded in the result `error` and also shown in the text output

## static check

What a static check reads, where its failure message alone does not say it.

- The DEV code reference check counts as references, in files outside DEV code (`client/dev/`), core (`client/core/`) and regression tests (`client/tests/`), a `class_name` inside `client/dev/` and `client/core/*/dev/` (including `client/dev/generated/`) and the strings `res://dev/` and `res://core/*/dev/`. On the server, it counts as a reference a file outside `server/dev/`, core (`server/core/`) and server regression tests (`server/tests/`) importing a file inside `server/dev/` or `server/core/*/dev/`. It reads no core file: `core diff` compares core files with the core release
- The option entry check and the gamepad input check read the `.gd` files of client content code outside `client/dev/` and `client/tests/`. A call is named by the names and members it is called on (`SoundCore.play_bgm` for `SoundCore.play_bgm(...)`), and a `SoundBus` element is the argument `SoundCore.SoundBus.<member>`. The input map is the `input/` keys of `client/project.godot` without the `ui_` actions; of the `events` of an action, an `InputEventKey` or `InputEventMouseButton` is a key or mouse button and an `InputEventJoypadButton` or `InputEventJoypadMotion` is a gamepad button or gamepad axis direction. A content positional player is a node of type `AudioStreamPlayer2D` or `AudioStreamPlayer3D` in a `.tscn` under `resource/scene/` or `resource/prefab/`, or an `AudioStreamPlayer2D.new()` or `AudioStreamPlayer3D.new()` call. A `cutscene_step` row has a `voice` when its `voice` cell is neither empty nor `null`. The modules the game uses are those of `## module` of [`core`](../skills/core/SKILL.md) with the core release of game settings `coreVersion`
- The `where` of a missing call or module is the line of what makes the entry required: the game settings value (for social login, the first `login-apple` or `login-google` adapter of `environments` that is not `null`), the data row, the action of `client/project.godot`, the first call or node that makes the bus played or the entry required, and `client/features:1` for the entries every game has and for the `Ui` bus
- The option entry check also fails on a `SoundCore.play`, `SoundCore.get_volume` or `SoundCore.set_volume` call whose `SoundBus` argument is not a `SoundBus` element, at the line of that call
- The gamepad input check, when game settings `gamepadSupported` is not `true`, fails at the line of each action other than the core actions whose `events` have a gamepad button or gamepad axis direction, and at the line of each name in content code of `InputCore.InputDevice.GAMEPAD`, `GameData.InputPromptFamily.GENERIC`, `GameData.InputPromptFamily.XBOX`, `GameData.InputPromptFamily.PLAY_STATION`, `GameData.InputPromptFamily.NINTENDO`, `InputCore.get_connected_gamepads`, `InputCore.get_pad_buttons`, `InputCore.set_pad_buttons`, `InputCore.reset_pad_buttons`, `InputCore.wait_pad_button` and `GamepadConnectionChangedEvent`
- The forbidden GDScript API check reads the global names of the pinned Godot from the `extension_api.json` that `godot --headless --dump-extension-api` writes: the `name` of each item of `classes`, `builtin_classes` and `global_enums` without a `.`. The UI prefab check asks the pinned Godot whether a node type is `Control` or inherits it with `ClassDB.is_parent_class()`
- The document format check reads the heading tables from `## brief`, `## design doc` and `## play guide` of [`game-design`](../skills/game-design/SKILL.md) of the harness. Its `where` of a missing heading is `<file>:1`, an absence failure
- The `where` of a UI prefab failure is the line of the value of `core.<key>`. A key that the merged core settings do not have is not checked
- A failure about a game settings value (option entry, game settings owner, UI prefab) points at the line of `settings.json` where that value starts, found by its path; when the value is absent, at the line where the nearest value that holds its place starts (`settings.json:1` for the whole file). In a `core.<key>` path, `<key>` is the longest core settings key that `core` holds as one key, and the rest of the path is below it

## time

The tool records where the time of each job goes, without a caller asking for it, and `ogw time` reports it.

- job span: the span of a job, from `startedAt` to `endedAt` of its job record, and to the current time while it runs. Its name is `ogw <command>`, and `ogw agent <role>` for an `ogw agent` job. Every job has it, also a job whose command recorded nothing else
- step span: a step that the command of a job names (`span` of `tools/src/lib/spans.ts`), in the step span that runs when it starts, else in the job span. A step span that ends by throwing is failed. A step that starts a job and waits for its end holds both, so that the job is in the span that waits for it
- wait: a take of a lock, slot or ledger that does not succeed at its first try, from the start of the take until it takes it or gives up, in the step span that runs, else in the job span. It is on the path that names what it waits for: the lock folder of `withLock` and `withLockWithin` (the git worktree lock and the job record locks among them), the base of a reader/writer lock (the writer lock, the readers a writer waits for, the waiting writers a reader lets go first, and the reader entry of the same process that another reader takes meanwhile), the slot folder of `withSlot`, the ledger folder of `withShare`. A take inside another take (the ledger lock of a share, the writer lock a reader takes) is part of the wait of the outer take
- spans file: `<id>.spans.jsonl` beside the job record in the jobs folder. The command process of a job appends a JSON line when a step span or wait starts, with `end` null, and again when it ends: `{"id": "<id>", "name": "<name>", "parent": <id or null>, "start": <unix ms>, "end": <unix ms or null>}` for a step span, with `"failed": true` when it threw, and `{"id": "<id>", "wait": "<path>", "parent": <id or null>, "start": <unix ms>, "end": <unix ms or null>}` for a wait. `parent` is the id of the step span it is in, null for the job span. Each line is one write to the file, which the process keeps open, without fsync, so a killed job keeps every line written before; a step span or wait without its end line ends at the end of its job. When a line cannot be written, no line is written after it, the steps, locks, slots and shares go on as in a process without a job, and the command fails with that error when it ends
- child job: a job started by the process of another job, or from inside an agent, records in its job record `parentJob`, the job of the process that started it, else its `agentJob`, and `parentSpan`, the step span of that job that ran when it started, null for the job span. Its job span is in that span
- `ogw time <job id>` reports the tree of the job: its job span with its step spans and waits, and the tree of each child job. `ogw time <game> --run <run> [--iteration <n>]` reports the tree of a run span over the run of the game, from its start to its close or the current time, or over iteration `<n>`, from the start of the first `ogw agent` job of the run with that iteration to the start of the first one with a later iteration, else to the close of the run or the current time. The run span holds the tree of each job of the run (`jobsOfRun` of `tools/src/lib/runstate.ts`) that started in it and that no other of those jobs started. A line of a spans file that is not a step span or wait line, and a line or child job whose parent span the spans file does not hold, fail the command
- The report prints, with each length its share of the wall time:
  - wall time: the length of the root span, its start and its end
  - critical path: the chain of spans whose ends decide the end of the root. It is the root and then, for each span on it, its deciding children, each followed by its own deciding children. The deciding children of a span are found from its end back: the child span (step span or child job span) that ended last at or before the cursor, after which the cursor moves to the start of that child, until no child that is not chosen yet ended at or before the cursor
  - largest self time: the 10 spans with the largest self time, the length of a span less the time its child spans cover
  - waits: the total of the waits on each path over the tree, with their count
  - flags, each of one job of the tree with its own wall time:
    - `wait`: the waits on one path of the job span and step spans of the job add up to at least harness settings `time.waitShare` of the wall time of the job
    - `idle`: in a job that has a step span, the wall time less the union of its child spans (step spans and child jobs) and of the waits of its job span is at least `time.idleShare` of the wall time: time in sleeps and polls that measure nothing
    - `outlier`: a job span or step span that ended lasts more than `time.outlierRatio` times the median of the last `time.history` spans of the same name for the same game on this host (the jobs folder) that ended at or before its start, when there are at least 5 of them. Those spans are the step spans that ended without failing and the job spans of the jobs that ended `done`
- `--json` gives the same as data: `root` (each span with `key`, `kind`, `job`, `name`, `parent`, `start`, `end`, `open`, `failed`, `waits` and `children`; `key` is `<job id>` for a job span, `<job id>/<span id>` for a step span and `run <run>` for a run span), `wallMs`, `criticalPath`, `selfTime`, `waits`, `flags` and `criteria`
